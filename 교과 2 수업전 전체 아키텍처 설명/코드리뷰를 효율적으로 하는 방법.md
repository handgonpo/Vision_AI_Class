# 1. 코드 리뷰를 얼마나 해야 하나?

생성형 AI 시대에는 다음과 같이 작업하기 쉽습니다.

```text
요구사항 작성
    ↓
생성형 AI가 코드 생성
    ↓
복사
    ↓
실행
    ↓
정상 동작
    ↓
다음 기능으로 이동
```

이 방법은 빠르지만 문제가 생기면 다음 상황에 부딪힐 수 있습니다.

```text
어디에서 입력이 들어오는지 모름
        ↓
어떤 함수가 핵심인지 모름
        ↓
변수가 어디에서 바뀌는지 모름
        ↓
오류가 나도 수정 위치를 찾기 어려움
        ↓
생성형 AI에게 다시 전체 코드를 맡김
```

따라서 목표는 모든 코드를 자세히 해석하는 것이 아닙니다.

**다음 다섯 가지를 설명할 수 있을 정도까지만 확인합니다.**

```text
① 이 코드는 무엇을 하는가?
② 무엇을 입력받고 무엇을 만들어내는가?
③ 주요 함수·클래스·객체는 각각 무슨 역할인가?
④ 데이터가 어떤 순서로 이동하는가?
⑤ 문제가 생기면 어느 단계부터 확인해야 하는가?
```

이 다섯 가지가 설명되면 일단 다음 작업으로 넘어가도 됩니다.

---

# 2. 모든 코드에 같은 깊이의 리뷰를 하지 않습니다

코드의 중요도에 따라 리뷰 깊이를 다르게 합니다.

| 코드 종류 | 확인 수준 | 예 |
|---|---|---|
| 이미 여러 번 사용한 단순 코드 | 빠른 확인 | `Path`, 단순 `print`, 폴더 생성 |
| 처음 보는 함수·파일 | 기본 리뷰 | `argparse`, 이미지 로딩, 전처리 함수 |
| 프로젝트 핵심 로직 | 반드시 흐름 확인 | 추론, 전처리, 후처리, 평가, 저장 |
| 오류가 발생한 코드 | 해당 구간 깊게 확인 | shape 오류, 파일 경로 오류, 모델 입력 오류 |
| 외부 장비·파일·모델과 연결되는 코드 | 입력·출력과 실패지점 확인 | Camera, ONNX, TensorRT, GPIO, API |

즉, **모든 줄을 공부하는 것이 아니라 프로젝트를 움직이는 핵심 코드에 시간을 씁니다.**

# 3. 가장 효율적인 기본 리뷰는 5단계입니다

코드를 받을 때마다 여러 개의 프롬프트로 하나씩 질문하지 않습니다.

먼저 **한 번의 통합 프롬프트**로 전체 구조를 확인하고, 이해되지 않는 부분만 추가 질문합니다.

```text
코드 받기
    ↓
STEP 1. 전체 목적과 입출력 확인
    ↓
STEP 2. 주요 함수·클래스·객체 역할 확인
    ↓
STEP 3. 데이터 흐름 확인
    ↓
STEP 4. 실행 결과와 실패지점 확인
    ↓
STEP 5. 앞뒤 코드와 연결 확인
```

이 다섯 단계가 기본 패턴입니다.

---

# 4. STEP 1 — 먼저 "이 코드가 왜 필요한가?"를 확인합니다

예제 코드를 보겠습니다.

```python
from __future__ import annotations

import argparse
from pathlib import Path

import cv2


def parse_args():
    parser = argparse.ArgumentParser()

    parser.add_argument(
        "--source",
        required=True,
        help="읽을 이미지 파일 경로",
    )

    return parser.parse_args()


def main() -> None:
    args = parse_args()

    image_path = Path(args.source)

    if not image_path.exists():
        raise FileNotFoundError(
            f"파일이 없습니다: {image_path}"
        )

    image = cv2.imread(str(image_path))

    if image is None:
        raise RuntimeError(
            f"OpenCV가 이미지를 읽지 못했습니다: {image_path}"
        )

    height, width = image.shape[:2]

    print(f"Image path : {image_path}")
    print(f"Width      : {width}")
    print(f"Height     : {height}")
    print(f"Channels   : {image.shape[2]}")
    print(f"Shape      : {image.shape}")
    print(f"DataType   : {image.dtype}")


if __name__ == "__main__":
    main()
```

처음부터 `ArgumentParser`, `Path`, `imread()`를 하나씩 분석하지 않습니다.

먼저 이 코드 전체를 다음처럼 이해합니다.

```text
목적

터미널에서 이미지 경로를 입력받아
이미지를 정상적으로 읽을 수 있는지 확인하고
이미지의 기본 정보를 출력한다.
```

그리고 입력과 결과를 확인합니다.

```text
입력
--source data/apple.jpg

        ↓

처리
경로 확인 → 이미지 읽기 → 이미지 정보 확인

        ↓

출력
Width / Height / Channels / Shape / DataType
```

## 생성형 AI에게 처음에는 이렇게 질문합니다

```text
아래 코드를 주니어 개발자가 빠르게 이해할 수 있도록 리뷰해줘.

한 줄씩 해설하지 말고 먼저 다음만 설명해줘.

1. 이 코드가 필요한 이유와 전체 목적
2. 입력과 최종 출력
3. 실제 실행 순서
4. 주요 함수·클래스·객체와 각각의 역할
5. 데이터가 이동하는 흐름
6. 오류가 날 수 있는 주요 지점
7. 이 코드가 프로젝트의 앞뒤 단계와 어떻게 연결되는지

라이브러리 내부 구현이나 중요하지 않은 문법은 설명하지 말아줘.

[코드 붙여넣기]
```

**이 프롬프트 하나가 기본 코드 리뷰의 출발점입니다.**

# 5. STEP 2 — 주요 함수·클래스·객체만 확인합니다

전체 목적을 알았다면 이제 코드의 큰 구성요소만 봅니다.

이 예제에서 중요한 구성요소는 다음 정도입니다.

| 구성요소 | 역할 | 결과 |
|---|---|---|
| `parse_args()` | 터미널 입력 처리 | `--source` 값이 들어 있는 결과 반환 |
| `ArgumentParser` 객체 | 명령행 옵션 관리 | `add_argument()`, `parse_args()` 사용 |
| `main()` | 이미지 읽기와 검사 흐름 실행 | 이미지 정보 출력 |
| `Path` 객체 | 파일 경로 관리 | 존재 여부 확인 가능 |
| `cv2.imread()` | 파일에서 이미지 읽기 | 이미지 배열 또는 실패 시 `None` |
| `if __name__ == "__main__"` | 이 파일을 직접 실행했을 때 시작 | `main()` 호출 |

여기서 중요한 것은 **메서드의 내부 구현을 아는 것**이 아닙니다.

예를 들어:

```python
parser = argparse.ArgumentParser()
```

를 보면 다음 정도만 알면 됩니다.

```text
무엇을 만들었나?
→ 명령행 입력을 처리하는 객체

어디에 저장했나?
→ parser

왜 필요한가?
→ --source 같은 실행 옵션을 등록하고 실제 입력값을 읽기 위해
```

그리고:

```python
parser.add_argument(...)
```

를 처음 봤다면 다음만 확인합니다.

```text
입력
→ 옵션 이름과 설정

역할
→ 터미널에서 받을 값을 등록

결과
→ --source 값을 받을 수 있게 됨
```

그 내부에서 `argparse`가 어떻게 구현되어 있는지는 지금 알 필요가 없습니다.

# 6. STEP 3 — 변수보다 "데이터 흐름"을 따라갑니다

프로그램을 이해하려면 변수 이름을 모두 외우는 것보다 **하나의 데이터가 어떻게 이동하는지** 보는 것이 훨씬 중요합니다.

이 예제에서는 이미지 경로가 다음처럼 이동합니다.

```text
터미널

--source data/apple.jpg
        ↓
parse_args()
        ↓
args.source
        ↓
"data/apple.jpg"
        ↓
Path(...)
        ↓
image_path
        ↓
cv2.imread(...)
        ↓
image
        ↓
image.shape
        ↓
Width / Height / Channels 출력
```

이 흐름을 설명할 수 있다면 코드의 핵심은 이미 이해한 것입니다.

## 생성형 AI에게 데이터 흐름이 잘 보이지 않을 때만 추가로 묻습니다

```text
아래 코드에서 핵심 데이터 하나를 선택해서
입력부터 최종 결과까지 어떤 변수와 함수를 거치는지
화살표 흐름으로 추적해줘.

각 단계에서 값의 형태도 가능하면 함께 적어줘.

[코드 붙여넣기]
```

예를 들어 이 코드에서는 다음처럼 볼 수 있습니다.

```text
문자열 경로
        ↓
Path 객체
        ↓
OpenCV 이미지 배열
        ↓
shape 정보
        ↓
출력 문자열
```

Vision AI 코드에서도 같은 방식으로 봅니다.

```text
이미지
    ↓
Resize
    ↓
Tensor
    ↓
Model
    ↓
Prediction
    ↓
BBox / Class / Score
    ↓
화면 또는 파일
```

# 7. STEP 4 — 실행 결과와 "어디서 실패할 수 있는지"를 확인합니다

코드를 실행해서 정상 결과가 나왔다고 바로 끝내지 않습니다.

결과가 무엇을 의미하는지 한 번 확인합니다.

예를 들어:

```text
Image path : data/apple.jpg
Width      : 1920
Height     : 1080
Channels   : 3
Shape      : (1080, 1920, 3)
DataType   : uint8
```

라면 최소한 다음 정도는 읽을 수 있어야 합니다.

```text
이미지를 정상적으로 읽었다.
크기는 1920 × 1080이다.
3채널 이미지다.
배열 구조는 Height × Width × Channel이다.
픽셀 자료형은 uint8이다.
```

그리고 **실패할 수 있는 위치**를 확인합니다.

이 코드에서는 크게 두 곳입니다.

```text
1. image_path.exists()

파일 자체가 없음
        ↓
FileNotFoundError


2. cv2.imread(...)

파일은 있지만 OpenCV가 읽지 못함
        ↓
image is None
        ↓
RuntimeError
```

이것을 알고 있으면 문제가 발생했을 때 처음부터 전체 코드를 다시 보지 않아도 됩니다.

```text
"파일이 없습니다"
→ 경로와 파일 배치 확인

"OpenCV가 이미지를 읽지 못했습니다"
→ 파일 형식, 손상 여부, 실제 이미지 여부 확인

shape 관련 오류
→ 이미지가 정상적으로 읽혔는지부터 확인
```

## 오류가 발생했을 때는 전체 코드를 다시 설명해 달라고 하지 않습니다

다음처럼 질문합니다.

```text
이 코드는 원래 [기대 결과]가 나와야 하는데
현재 아래 오류가 발생했다.

전체 코드를 새로 작성하지 말고,

1. 오류가 발생한 단계
2. 그 단계의 입력값
3. 확인해야 할 변수
4. 가장 가능성이 높은 원인
5. 최소 수정 방법

순서로 진단해줘.

[코드]
[실행 명령]
[오류 메시지]
```

이 방식이 디버깅 역량을 만드는 데 더 도움이 됩니다.

# 8. STEP 5 — "이 코드가 어디에 연결되는가?"를 확인합니다

한 파일만 이해하고 끝내면 프로젝트 전체 구조는 잘 보이지 않을 수 있습니다.

현재 코드가 전체 작업에서 어느 위치인지 확인합니다.

예를 들어 이미지 검사 프로젝트가 다음처럼 이어진다고 가정합니다.

```text
이미지 경로 입력
        ↓
[현재 코드]
이미지 로딩 확인
Width / Height / Shape 확인
        ↓
전처리
Resize / Gray / Blur
        ↓
특징 추출 또는 모델 추론
        ↓
판정
        ↓
결과 저장
```

현재 코드는 **이미지가 정상적으로 준비되었는지 확인하는 입력 단계**라는 것을 알 수 있습니다.

여러 파일이 있는 프로젝트라면 파일별로 다음 정도만 먼저 파악합니다.

```text
capture.py
→ 입력 수집

preprocess.py
→ 전처리

infer.py
→ 모델 추론

postprocess.py
→ 결과 정리

main.py
→ 전체 실행 순서 연결
```

## 여러 파일의 연결이 보이지 않을 때 사용합니다

```text
아래 프로젝트 파일들을 한 줄씩 설명하지 말고
실제 실행 흐름 중심으로 연결해줘.

다음만 알려줘.

- 시작 파일
- 파일별 역할
- 어떤 함수가 어떤 함수를 호출하는지
- 데이터가 파일 사이에서 어떻게 이동하는지
- 최종 결과가 만들어지는 위치

가능하면

입력 → 파일 → 함수 → 파일 → 함수 → 결과

형태로 정리해줘.

[관련 파일 붙여넣기]
```

# 9. 여기까지 했으면 다음 코드로 넘어가도 됩니다

코드를 받을 때마다 모든 문법을 완벽하게 설명할 필요는 없습니다.

다음 질문에 답할 수 있다면 기본 리뷰는 끝입니다.

```text
이 코드는 왜 필요한가?
        ↓
무엇이 들어오는가?
        ↓
어떤 주요 함수·객체가 처리하는가?
        ↓
데이터가 어떤 순서로 이동하는가?
        ↓
무엇이 나오는가?
        ↓
문제가 생기면 어디부터 볼 것인가?
        ↓
다음 단계와 어떻게 연결되는가?
```

이 흐름을 설명할 수 있다면 계속 개발을 진행합니다.

# 10. 모든 코드에서 "직접 수정"까지 할 필요는 없습니다

코드를 이해했는지 확인하기 위해 매번 새로운 기능을 추가하면 오히려 개발 속도가 떨어질 수 있습니다.

따라서 직접 수정은 **새로운 패턴을 처음 배웠거나 프로젝트 핵심 코드일 때만** 합니다.

예를 들어 다음 중 하나만 해봅니다.

```text
입력값을 바꿔본다.
파라미터 하나를 바꿔본다.
일부러 잘못된 경로를 넣어 오류를 확인한다.
출력 항목 하나를 추가해본다.
```

이런 작은 변경을 통해 다음을 확인합니다.

> **내가 어느 부분을 바꾸면 어떤 결과가 달라지는지 알고 있는가?**

그렇다면 코드를 전부 새로 작성하지 못하더라도 실제 수정과 디버깅에 필요한 기본 이해는 갖춘 것입니다.

# 11. 리뷰 시간을 줄이는 3단계 기준

매번 같은 시간으로 리뷰하지 않습니다.

## A. 빠른 확인

이미 알고 있는 패턴이거나 단순 보조 코드입니다.

```text
목적
→ 입력
→ 출력
→ 다음 연결
```

이 정도만 확인하고 넘어갑니다.

예:

```python
output_dir.mkdir(parents=True, exist_ok=True)
```

이 코드를 여러 번 사용했다면 매번 `mkdir()`의 모든 옵션을 다시 공부할 필요는 없습니다.

---

## B. 기본 리뷰

처음 보는 함수나 파일, 새로운 라이브러리를 사용하는 코드입니다.

```text
목적
→ 주요 함수·객체
→ 데이터 흐름
→ 실행 결과
→ 실패 지점
→ 다음 연결
```

대부분의 실습 코드는 이 수준으로 리뷰합니다.

# 12. Vision AI에서는 특히 이 네 구간을 놓치지 않습니다

Vision AI 코드에서는 모든 줄보다 **데이터가 형태를 바꾸는 지점**이 중요합니다.

```text
① 입력
이미지 / 영상 / 카메라

        ↓

② 전처리
Resize / Color / Normalize / Tensor 변환

        ↓

③ 핵심 처리
OpenCV 알고리즘 / Model Inference

        ↓

④ 후처리와 결과
BBox / Keypoint / Class / Score / Rule / 저장
```

오류가 발생할 때도 대부분 이 경계에서 확인할 것이 생깁니다.

예를 들어:

```text
이미지를 못 읽음
→ 입력 단계

shape가 맞지 않음
→ 전처리 단계

모델이 실행되지 않음
→ 추론 입력과 모델 단계

BBox가 이상함
→ 후처리 단계

Accuracy가 이상함
→ 평가 데이터와 평가 단계
```

따라서 Vision AI 코드를 리뷰할 때는 **데이터가 어떤 형태로 다음 단계에 넘어가는가**를 우선 확인합니다.

# 13. 주니어용 기본 통합 프롬프트

매번 여러 번 질문하지 않고 아래 프롬프트 하나로 시작합니다.

```text
나는 생성형 AI와 함께 이 코드를 개발하고 있는 주니어 개발자야.

이 코드를 한 줄씩 강의하듯 설명하지 말고,
내가 계속 개발하고 문제가 생겼을 때 수정할 수 있을 정도의
최소 코드 리뷰를 해줘.

다음 순서로 설명해줘.

1. 이 코드의 목적을 한 문장으로
2. 입력과 최종 결과
3. 실제 실행 순서
4. 주요 함수·클래스·객체의 역할
5. 핵심 데이터가 이동하고 변하는 흐름
6. 처음 보는 핵심 API가 있다면
   "입력 → 역할 → 결과"만 설명
7. 오류가 발생할 가능성이 높은 지점과 그때 먼저 확인할 것
8. 이 코드가 이전 단계와 다음 단계에 어떻게 연결되는지

중요하지 않은 Python 문법,
라이브러리 내부 구현,
현재 사용하지 않는 옵션은 설명하지 말아줘.

[코드 붙여넣기]
```

이 답변을 읽고 이해되는 부분은 그대로 넘어갑니다.

이해되지 않는 **특정 함수나 한두 줄만** 다시 질문합니다.

---

# 14. 특정 코드가 이해되지 않을 때만 사용하는 추가 프롬프트

예를 들어 다음 코드가 이해되지 않는다면:

```python
parser = argparse.ArgumentParser()
```

전체 코드를 다시 질문하지 않습니다.

```text
아래 한 줄만 설명해줘.

parser = argparse.ArgumentParser()

다음 세 가지면 충분해.

1. 무엇이 만들어지는가?
2. 왜 만드는가?
3. 만들어진 객체를 이후 어디에서 사용하는가?

내부 구현은 설명하지 말아줘.
```

또는:

```python
image = cv2.imread(str(image_path))
```

라면:

```text
이 한 줄에서

1. 입력값
2. 처리
3. 반환값
4. 실패했을 때 반환되는 값

만 설명해줘.

OpenCV 내부 구현은 설명하지 말아줘.
```

이 방식으로 **모르는 부분에만 시간을 씁니다.**

# 15. 오류가 났을 때는 "전체 재생성"보다 "단계 진단"을 먼저 합니다

생성형 AI를 사용할 때 흔히 다음처럼 해결하려고 할 수 있습니다.

```text
오류 발생
    ↓
전체 코드 붙여넣기
    ↓
"고쳐줘"
    ↓
새 코드 전체 복사
```

이 방식만 반복하면 코드 구조를 파악하기 어렵습니다.

대신 다음 흐름을 사용합니다.

```text
오류 발생
    ↓
어느 단계인지 확인
    ↓
그 단계의 입력 확인
    ↓
출력 또는 중간값 확인
    ↓
원인 후보 좁히기
    ↓
필요한 부분만 수정
```

이 습관이 있어야 프로젝트가 커져도 문제 위치를 빠르게 찾을 수 있습니다.

# 16. 최소 코드 리뷰 체크

코드를 실행한 뒤 다음 항목만 확인합니다.

- [ ] 입력과 출력이 무엇인지 알고 있다.
- [ ] 주요 함수·클래스·객체의 역할을 알고 있다.
- [ ] 핵심 데이터가 어디에서 들어와 어디로 이동하는지 설명할 수 있다.

- [ ] 문제가 생기면 가장 먼저 확인할 지점을 알고 있다.
- [ ] 이 코드가 프로젝트의 이전·다음 단계와 어떻게 연결되는지 알고 있다.

# 17. 최종 원칙

생성형 AI를 사용한다고 해서 모든 코드를 처음부터 직접 작성해야 하는 것은 아닙니다.

반대로 실행된다는 이유만으로 아무것도 확인하지 않고 넘어가서도 안 됩니다.

가장 효율적인 기준은 다음입니다.

```text
생성형 AI가 코드 생성
        ↓
전체 목적 확인
        ↓
주요 함수·객체 역할 확인
        ↓
핵심 데이터 흐름 확인
        ↓
실행 결과 확인
        ↓
실패 지점 확인
        ↓
앞뒤 연결 확인
        ↓
다음 기능 개발
```

그리고 다음 상황에서만 더 깊게 들어갑니다.

```text
처음 보는 핵심 기술이다.
        OR
오류가 발생했다.
        OR
결과가 예상과 다르다.
        OR
직접 수정해야 한다.
        OR
프로젝트의 핵심 알고리즘이다.
```

> **모든 코드를 깊게 이해하는 것이 목표가 아니라,  
> 현재 코드의 역할과 데이터 흐름을 파악하고 문제가 발생했을 때 확인할 위치를 스스로 찾을 수 있는 상태를 만드는 것이 목표입니다.**
