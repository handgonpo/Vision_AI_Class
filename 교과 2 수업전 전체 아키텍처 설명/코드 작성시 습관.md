그래서 앞으로 코드를 공부한다면 다음 습관을 들이는 것이 좋습니다.

1. **코드를 요청하기 전에 먼저 문제를 글로 정의하세요.**  
    `무엇을 입력받는가 → 무엇을 처리하는가 → 무엇을 출력하는가 → 실패하면 어떻게 할 것인가`를 먼저 적습니다.
    
2. **처음부터 전체 코드를 달라고 하지 않는 습관을 들이세요.**  
    먼저 `"코드를 작성하지 말고 구조부터 설계해줘"`라고 요청하세요. 예를 들어 `Camera → Pose → Feature → Buffer → Model → Stabilizer → Result`처럼 구조를 이해한 뒤 코드를 받는 것입니다.
    
3. **AI가 만든 코드를 반드시 설명할 수 있어야 합니다.**  
    모든 문법을 암기할 필요는 없지만 최소한 `"이 함수는 왜 존재하는가?"`, `"이 변수에는 무엇이 들어가는가?"`, `"이 코드를 삭제하면 무엇이 깨지는가?"`에는 답할 수 있어야 합니다.
    
4. **실행되는 코드보다 테스트 가능한 코드를 중요하게 생각하세요.**  
    `"돌아간다"`와 `"올바르게 동작한다"`는 다릅니다. 정상 입력, 잘못된 입력, 경계값, 파일 없음, 네트워크 끊김 같은 상황을 테스트하는 습관이 중요합니다.
    
5. **오류를 바로 AI에게 던지기 전에 3분 정도 직접 추론해보세요.**  
    `어디에서 발생했는가 → 입력값은 무엇인가 → 내가 예상한 값은 무엇인가 → 실제 값은 무엇인가`를 생각한 뒤 AI에게 질문하세요. 이 습관이 개발 실력을 엄청나게 키웁니다.
    
6. **AI 코드에 작은 변경을 직접 해보세요.**  
    예를 들어 AI가 만든 코드가 있다면 `threshold를 설정 파일로 빼기`, `함수 분리하기`, `CSV 로그 추가하기`, `예외 처리 추가하기`, `CLI 인자 추가하기` 같은 작은 변경은 직접 해보는 것입니다.
    
7. **코드보다 데이터 흐름을 볼 줄 아는 사람이 되세요.**  
    특히 AI 개발에서는 이것이 중요합니다.  
    `Raw Data → Preprocessing → Feature → Model → Prediction → Post-processing → Evaluation → Deployment`를 이해한다면 모델이나 프레임워크가 바뀌어도 살아남습니다.
    
8. **AI에게 정답만 묻지 말고 리뷰어 역할을 시키세요.**  
    `"이 코드를 더 만들어줘"`보다 `"이 설계에서 깨질 수 있는 지점을 찾아줘"`, `"production에서 위험한 부분을 찾아줘"`, `"테스트 케이스를 만들어줘"`, `"내 설계의 잘못된 가정을 찾아줘"` 같은 사용법이 훨씬 중요해질 것입니다.
    

제가 특히 추천하는 학습 방식은 **AI → 나 → AI의 왕복 구조**입니다.

이것이 앞으로의 프로그래밍 공부에 굉장히 좋은 방식입니다.

그리고 **문법 공부에 대한 생각도 바꿀 필요가 있습니다.**

예전처럼 Python API나 C++ 함수 이름을 전부 외우려고 할 필요는 점점 줄어들 것입니다.

Claude가 Python을 짜든 GPT가 C++을 짜든 Gemini가 JavaScript를 짜든 이 개념은 거의 그대로 남습니다.

---

그리고 AGI에 대해서는 누구도 지금 정확한 시점이나 형태를 장담할 수 없습니다.

하지만 아주 극단적인 상황을 가정해 보겠습니다.

```
미래 AI

"산업용 안전 감지 시스템 만들어줘."

        ↓

AI가

Camera 연결
Dataset
Model
Training
API
Dashboard
Docker
Edge Deployment
Tests

모두 만들어줌
```

그렇다고 사람의 일이 완전히 사라지는 것은 아닙니다.

여전히 누군가는 결정해야 합니다.

```
무엇을 위험행동으로 볼 것인가?

False Positive를 얼마나 허용할 것인가?

사람을 잘못 감지하면 어떻게 할 것인가?

카메라가 끊어졌을 때 어떻게 할 것인가?

현장 작업자의 개인정보는 어떻게 할 것인가?

GPU가 없는 공장에서 어떻게 돌릴 것인가?

Latency가 500ms여도 되는가?

안전 시스템이 잘못 판단했을 때 책임은 누구에게 있는가?

이 시스템이 실제 현장에 쓸 만한가?
```

이것들은 단순히 코드를 생성한다고 해결되는 문제가 아닙니다.

그래서 미래의 좋은 개발자는 점점 이런 형태가 될 가능성이 큽니다.

```
과거 개발자

코드를 많이 작성하는 사람
████████████████████

미래 개발자

문제 정의        █████████
시스템 설계      █████████
AI 활용          █████████
코드 이해        █████
코드 작성        ███
테스트 / 검증    █████████
도메인 이해      █████████
```

따라서 **코드를 배우지 않는 것**과 **코드를 직접 전부 작성하지 않는 것**은 전혀 다른 이야기입니다.

저라면 앞으로의 개발 공부에서 목표를 이렇게 잡겠습니다.

> **"코드를 잘 타이핑하는 사람이 아니라, 코드가 왜 그렇게 되어 있는지 알고 AI에게 무엇을 만들라고 해야 하는지 아는 사람이 된다."**

그리고 한 단계 더 나아가면,

> **"AI가 만든 결과를 믿는 사람이 아니라 검증할 수 있는 사람이 된다."**

이것이 굉장히 중요합니다.

특히 AI가 아주 강력해지면 역설적으로 이런 사람이 더 위험해집니다.

```
AI가 이렇게 만들었습니다.
↓
그냥 맞겠죠.
```

반대로 가치가 높아지는 사람은 이런 사람입니다.

```
AI가 이렇게 만들었습니다.

그런데

Dataset Leakage가 있습니다.
이 설계에서는 장애 복구가 안 됩니다.
이 Threshold는 근거가 없습니다.
이 Benchmark는 잘못되었습니다.
이 API 구조라면 확장이 어렵습니다.
이 모델은 현장 Latency 기준을 못 맞춥니다.

그래서 이렇게 수정하겠습니다.
```

이 사람은 **AI 시대에도 엔지니어**입니다.

결국 앞으로 프로그래밍을 공부하면서 스스로에게 계속 물어야 할 질문은 하나입니다.

```
"내가 이 코드를 직접 쓸 수 있는가?"
```

보다

```
"나는 이 코드가 왜 이렇게 되어 있는지
설명하고, 검증하고, 수정하고,
더 나은 구조를 판단할 수 있는가?"
```

입니다.

그리고 저는 이것을 **AI 시대의 코드 문해력(Code Literacy)**이라고 생각합니다.

AI가 코드를 10배, 100배 더 잘 작성하게 되더라도 이 능력을 갖춘 사람과 그렇지 않은 사람의 차이는 오히려 더 커질 가능성이 있습니다.
