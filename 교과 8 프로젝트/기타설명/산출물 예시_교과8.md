# 1. 학습용 Dataset Version — 작성 예시

첫 번째 산출물은 
교과 7에서 넘겨받은 FINAL 900장을 
교과 8 모델 개발용 데이터와 교과 14 연결용 데이터로 구분하고, 
그 사용 계획까지 확정한 결과입니다.

여기서 가장 중요한 점은 **900장을 모두 교과 8의 Train / Validation / Test에 넣지 않는 것**입니다.

교과 7에서는 900장을 모두 검수했지만, 
교과 8에서는 일부 데이터를 모델 학습·튜닝 과정에서 완전히 제외하여

Bridge Holdout이란 교과 8에서 학습이나 성능개선에 사용하지 않고 따로 남겨 두었다가, 교과 14에서 모델이 처음 보는 데이터에도 잘 동작하는지 확인하기 위해 사용하는 데이터입니다.

## 왜 Bridge Holdout을 따로 남기나요?

Bridge Holdout은 교과 8에서 성능을 올리기 위해 반복해서 보는 데이터가 아닙니다.

```text
Train
→ 모델이 실제로 학습하는 데이터

Validation
→ Baseline과 개선 모델을 비교하는 데이터

Frozen Test
→ Final Model을 선택한 뒤
   교과 8의 최종 성능을 한 번 확인하는 데이터

Bridge Holdout
→ 교과 8 학습·튜닝·모델 선택에 사용하지 않음
→ 교과 14에서 Final Model의 연결 성능을 확인하기 위해 보존
```

즉 교과 8에서 좋은 성능을 만들기 위해 900장을 모두 사용해버리면,  
교과 14에서 **“교과 8에서 만든 모델이 보지 않은 데이터에서도 잘 동작하는가?”**를 
확인할 독립 데이터가 사라집니다.

### `2. split_manifest.csv` 작성 예시

#### 이 파일은 무엇인가요?

`split_manifest.csv`는 **900장 전체의 사용 역할을 기록하는 가장 중요한 기준표**입니다.

한 장마다 다음 내용을 기록합니다.

```text
이 이미지는 어디에서 왔는가?
기존에는 train인가 validation인가?
어떤 scene_type인가?
비슷한 촬영 묶음은 무엇인가?
교과 8에서는 어떤 역할로 사용할 것인가?
현재 Dataset Version은 무엇인가?
```

즉 `train.csv`, `val.csv`, `test.csv`, `bridge_holdout.csv`를 만들기 위한 **Master Manifest**입니다.

#### ==실제 작성 예시==

```csv
image_path,label_path,source_dataset,original_split,scene_type,capture_group,split,dataset_version
<실제파일명1>.jpg,<실제파일명1>.txt,dataset1,train,kimchi_with_target,<그룹값>,train,kimchi_v1
250410_144403911987.jpg,250410_144403911987.txt,dataset2,train,kimchi_with_target,<그룹값>,train,kimchi_v1
<실제파일명2>.jpg,<실제파일명2>.txt,dataset2,validation,normal_kimchi,<그룹값>,val,kimchi_v1
<실제파일명3>.jpg,<실제파일명3>.txt,dataset1,train,object_only,<그룹값>,test,kimchi_v1
<실제파일명4>.jpg,<실제파일명4>.txt,dataset2,train,kimchi_with_target,<그룹값>,bridge_holdout,kimchi_v1
```

#### 각 항목의 의미

| 항목 | 의미 |
|---|---|
| `image_path` | 이미지 파일 |
| `label_path` | 같은 이름의 YOLO TXT |
| `source_dataset` | 교과 7에서 보존한 Dataset 1 / Dataset 2 출처 |
| `original_split` | 원래 `train / validation` 중 어디에 있었는지 |
| `scene_type` | `kimchi_with_target`, `normal_kimchi`, `object_only` 등 |
| `capture_group` | 같은 촬영 묶음·유사 장면을 함께 관리하기 위한 값 |
| `split` | `train / val / test / bridge_holdout` 중 확정된 역할 |
| `dataset_version` | 이번 Dataset 버전 |

#### 왜 `capture_group`을 기록하나요?

거의 같은 이미지가 Train과 Test에 동시에 들어가면 모델 성능이 실제보다 좋게 보일 수 있습니다.

따라서:

```text
같은 촬영 묶음 G001

일부 → Train
일부 → Test
일부 → Bridge Holdout

X
```

가능하면 같은 `capture_group`은 하나의 역할에만 들어가도록 합니다.

이 문서에서 `split_manifest.csv`는 900장 전체를 한 행씩 기록하는 Master Manifest이지만, 실제로는 **코드로 기본 행을 자동 생성한 뒤 사람이 필요한 항목만 검토·보정**하는 방식으로 작성합니다. 

`split_manifest.csv`가 900장 전체 Master Manifest이고, 이후 `train.csv`, `val.csv`, `test.csv`, `bridge_holdout.csv`를 여기서 필터링해 만드는 구조입니다.

작성흐름 예시

```
교과 7 FINAL
JPG 900장 + TXT 900개
        ↓
Python 코드로 파일 목록 자동 수집
        ↓
image_path
label_path
source_dataset
original_split
scene_type
등 기본 정보 자동 작성
        ↓
capture_group 확인
split 역할 결정
        ↓
split_manifest.csv 900행 생성
        ↓
split 값으로 자동 필터링
        ↓
train.csv
val.csv
test.csv
bridge_holdout.csv
자동 생성
```

직접 입력해야 하는 부분과 자동화할 수 있는 부분을 구분하면

- `image_path`, `label_path` → 거의 완전히 자동 생성 가능
- `source_dataset`, `original_split` → 원래 폴더 구조나 교과 7 Manifest에 정보가 있으면 자동 생성 가능
- `scene_type` → 교과 7 Manifest에 이미 있으면 그대로 가져올 수 있음
- `dataset_version` → 코드에서 `kimchi_v1`처럼 한 번 지정하여 전체 자동 입력 가능
- `split` → Split 정책을 정한 뒤 코드로 일괄 배정 가능
- `capture_group` → 가장 주의가 필요한 항목으로, 파일명·촬영시간·연속촬영 정보 등을 이용해 자동 초안을 만들고 사람이 검토하는 방식이 좋습니다.

900장 Manifest는 사람이 900줄을 직접 입력하는 것이 아니라, 
Python으로 파일정보를 자동 수집하여 초안을 만들고, 
사람은 `capture_group`과 최종 Split이 올바른지 검토·확정합니다. 
이후 train/val/test/bridge_holdout CSV는 Master Manifest에서 자동으로 분리합니다.

#### 확인할 것

- [ ] 900장 각각에 행이 하나씩 있다.
- [ ] 모든 이미지에 `split` 값이 있다.
- [ ] `train / val / test / bridge_holdout` 이외의 임의 상태값을 사용하지 않는다.
- [ ] 같은 `capture_group`이 여러 역할에 섞이지 않았는지 확인한다.
- [ ] 전체 데이터 수가 900장인지 확인한다.

`split_manifest.csv`에서:

### 5. `manifests/test.csv`

#### 이 파일은 무엇인가요?

`test.csv`는 **Final Model을 선택한 뒤 마지막에 성능을 확인하는 Frozen Test 데이터 목록**입니다.

Frozen Test는 Validation과 역할이 다릅니다.

```text
Validation
→ 개발 중 여러 번 사용 가능

Frozen Test
→ Final Model을 선택한 뒤 마지막에 평가
```

`split_manifest.csv`에서:

```text

```

인 행만 모아서 만듭니다.

#### ==실제 작성 예시==


#### 왜 Frozen이라고 하나요?

Final Model을 결정하기 전에는 Test 결과를 보고 모델을 계속 수정하지 않기 때문입니다.

```text
Baseline / Improved 비교
        ↓
Validation으로 Final Model 선택
        ↓
Final Model 확정
        ↓
그 다음 Frozen Test 사용
```

Test 결과가 낮더라도 그 Test를 반복해서 보면서 모델을 맞추지 않습니다.

> **쉽게 기억하기**  
> `test.csv` = 교과 8 Final Model의 마지막 시험 목록

#### 확인할 것

- [ ] `split`이 모두 `test`이다.
- [ ] Train·Validation과 겹치지 않는다.
- [ ] Final Model 선택 전에 Test를 모델 선택에 사용하지 않는다.
- [ ] Bridge Holdout 데이터가 들어가 있지 않다.

### 7. `docs/split_policy.md`

#### 이 파일은 무엇인가요?

`split_policy.md`는 **900장을 왜 이렇게 나누었는지 그 기준과 이유를 설명하는 문서**입니다.

CSV는 결과만 보여줍니다.

```text
img_001 → train
img_002 → val
img_003 → test
img_004 → bridge_holdout
```

하지만 이것만 보면 왜 그렇게 나눴는지 알 수 없습니다.

그래서 `split_policy.md`에는 다음을 적습니다.

```text
왜 나누었는가?
어떤 기준으로 나누었는가?
Data Leakage를 어떻게 막았는가?
Train / Validation / Frozen Test의 역할은 무엇인가?
Bridge Holdout은 왜 남겼는가?
최종 수량은 어떻게 되었는가?
```

#### ==실제 작성 예시==

```markdown
# Dataset Split Policy

## 1. 전체 데이터

교과 7 FINAL Dataset: 900장

원본 출처:
- Dataset 1 / train
- Dataset 2 / train
- Dataset 2 / validation

## 2. 데이터 사용 원칙

900장을 모두 교과 8 모델 개발에 사용하지 않습니다.

일부 데이터는 Bridge Holdout으로 별도 보존하여
교과 14에서 사용할 수 있도록 합니다.

## 3. 교과 8 개발용 데이터

Train
- 모델 학습에 사용

Validation
- Baseline과 Improved Model 비교에 사용

Frozen Test
- Final Model 선택 후 최종 성능 확인에 사용

## 4. Bridge Holdout

교과 8 학습·튜닝·모델 선택에 사용하지 않습니다.

교과 14에서 Final Model의 연결 성능을 확인하기 위해 보존합니다.

## 5. Data Leakage 방지

- 동일 이미지가 서로 다른 역할에 중복되지 않도록 확인
- 매우 유사한 이미지 확인
- 연속 촬영 이미지 확인
- 같은 capture_group은 가능한 한 한 역할에만 배정

## 6. 최종 구성

Dataset Version: kimchi_v1

- Train: [실제 수량]장
- Validation: [실제 수량]장
- Frozen Test: [실제 수량]장
- Bridge Holdout: [실제 수량]장

총합: 900장

Split 상태: FROZEN
Bridge Holdout 상태: RESERVED FOR SUBJECT 14
```

**팀이 확정한 Split 정책과 결과에 따라 몇 군데를 반드시 자기 팀 값으로 수정해야 합니다.** 산출물 1의 `docs/split_policy.md`는 900장을 왜 그렇게 나누었는지 설명하는 문서이므로, 팀마다 완전히 같으면 안됩니다.

다음 항목은 반드시 팀의 실제 결과에 맞게 수정합니다.

```
원본 출처
→ 실제로 어떤 Dataset / original_split에서 왔는지 확인

Data Leakage 방지 기준
→ 실제로 어떤 기준으로 capture_group을 묶었는지 기록

Dataset Version
→ 팀에서 확정한 버전명 기록

Train / Validation / Frozen Test / Bridge Holdout
→ 실제 확정된 수량 기록

Split 상태
→ 최종 확정 후 FROZEN으로 변경
```

Audit은 **데이터를 본격적으로 나누거나 학습하기 전에, 현재 데이터 상태를 먼저 점검하는 과정**입니다.

쉽게 말하면:

> 900장의 데이터가 빠짐없이 있는지, 이미지와 라벨이 맞는지, 중복·유사 이미지가 있는지, Class와 장면 분포가 어떤지 확인하는 사전 점검입니다.

교과 8에서는 Audit 결과를 보고 Train / Validation / Frozen Test / Bridge Holdout을 어떻게 나눌지 결정합니다.

예를 들어 Audit 결과가 실제로 다음과 같다면:

```
Train          610장
Validation      70장
Frozen Test     70장
Bridge Holdout 150장
총합           900장
```

문서에는 그대로 실제 수량을 입력합니다.

```markdown

- Train: 610장
```

```markdown
- 연속 촬영 파일은 같은 capture_group으로 묶었습니다.
- 같은 capture_group이 Train과 Test에 동시에 들어가지 않도록 확인했습니다.
- Bridge Holdout과 교과 8 개발 데이터가 겹치지 않는지 확인했습니다.
```

> **쉽게 기억하기**  
> `split_policy.md` = “왜 이렇게 나눴는지” 설명하는 문서

#### 확인할 것

- [ ] 전체 900장을 기준으로 작성했다.
- [ ] 네 역할을 구분했다.
- [ ] Data Leakage 방지 기준이 있다.

# 2. Baseline Model — 작성 예시

Baseline Model은 **개선하기 전에 처음 정식으로 학습한 기준 모델**입니다.

교과 8에서는 이후 Failure Analysis와 Improved Model을 진행하므로, 
처음 만든 모델의 Weight만 남기는 것이 아니라 
**어떤 Dataset Version과 어떤 학습조건으로 학습했는지, 
Validation 성능이 얼마였는지까지 함께 기록**해야 합니다.

- **Failure Analysis**  
	→ Baseline Model이 **어떤 이미지에서, 어떤 이유로 틀리는지 
	FP·FN·Class·BBox 오류를 실제 사례로 분석하는 과정**입니다.

- **Improved Model**  
	→ Failure Analysis에서 찾은 문제를 근거로 **주요 변수 하나를 바꾸어 
	다시 학습한 개선 모델**입니다.

Smoke Test에서 일부 데이터로 잠깐 학습한 모델은 Baseline이 아닙니다.

```text
Smoke Test
→ Dataset과 학습 코드가 정상적으로 연결되는지 확인하는 시험

Baseline Model
→ 확정된 Train Dataset 전체를 사용해
   공통 학습조건으로 처음 정식 학습한 비교 기준 모델
```

## 실제 작업 흐름

```text
산출물 1

        ↓

        ↓

        ↓

        ↓

        ↓

        ↓

        ↓

        ↓

```

산출물 1이란 아래의 `학습용 Dataset Version`을 뜻합니다.

### 1. `models/baseline/baseline_best.pt`

#### 이 파일은 무엇인가요?

`baseline_best.pt`는 **Train Dataset 전체로 처음 정식 학습한 Baseline Model의 Weight 파일**입니다.

YOLO11을 학습하면 학습 결과 폴더에 여러 파일이 생성됩니다.

그중 `weights/best.pt`는 Validation 성능을 기준으로 학습 과정에서 가장 좋은 Weight를 저장한 파일입니다.

교과 8에서는 이 파일을 그대로 두지 않고 Baseline 모델임을 알 수 있도록 별도 위치에 복사하여 보관합니다.

```text
YOLO11 Baseline 학습
        ↓
runs/baseline_v1/
        ↓
weights/best.pt 생성
        ↓
Baseline용으로 별도 보관
        ↓
models/baseline/baseline_best.pt
```

#### 실제 파일 위치 예시

```text
runs/
└── baseline_v1/
    └── weights/
        ├── best.pt
        └── last.pt

        ↓ best.pt 복사

models/
└── baseline/
    └── baseline_best.pt
```

#### 왜 이름을 바꾸어 보관하나요?

나중에는 Improved Model과 Final Model도 만들어집니다.

모두 파일명이 `best.pt`이면 어떤 모델인지 구분하기 어렵습니다.

```text
best.pt
best.pt
best.pt

→ 어떤 실험에서 나온 모델인지 구분하기 어려움
```

따라서 다음처럼 역할이 보이도록 정리합니다.

```text
baseline_best.pt
→ 개선 전 기준 모델

exp001_best.pt
→ 개선 실험 모델

final_best.pt
→ 최종 선택 모델
```

> **쉽게 기억하기**  
> `baseline_best.pt` = 앞으로 모든 개선 결과와 비교할 **첫 기준 모델**

Baseline Model은 **확정된 Train 600장 전체를 사용해서 처음 정식으로 학습한 모델**입니다.

#### 600(학습데이터) / 75(검증데이터) / 75(테스트데이터)라고 가정하면:

```
전체 교과 8 개발 데이터

Train
600장
→ 모델이 실제로 학습하는 데이터

Validation
75장
→ Baseline과 Improved를 비교하는 데이터

Frozen Test
75장
→ Final Model을 고른 뒤 마지막에만 평가하는 데이터
```

그리고 별도로 Bridge Holdout은 교과 14용으로 남겨 둡니다.

### 1. Smoke Test

Smoke Test는 **성능 좋은 모델을 만드는 단계가 아닙니다.**

예를 들어:

```
Train 30~50장
Validation 5~10장
Epoch 1~3

목적
→ 코드가 실행되는가?
→ Dataset 경로가 맞는가?
→ 학습이 시작되는가?
→ best.pt가 생성되는가?
→ Prediction이 되는가?
```

Smoke Test에서는 성능 숫자를 참고 정도로 볼 수 있지만,

> “Recall이 낮으니 개선해야겠다”

처럼 본격적인 모델 판단을 하면 안 됩니다.

### 2. Baseline Model

Smoke Test가 통과했다면 이제 **정식 Baseline**을 만듭니다.

```
Train
600장 전체

↓ 학습

Epoch
예: 50 / 100 / 150
→ 팀이 Smoke Test와 GPU·수업시간을 보고 결정

↓

Validation
75장 전체

↓

Baseline 성능
Precision
Recall
mAP50
mAP50-95
FP / FN
```

즉:

```
600장 전체 Train
        ↓
정식 학습
        ↓
75장 Validation 평가
        ↓
baseline_best.pt
```

입니다.

### 3. Failure Analysis

Baseline을 75장 Validation에서 평가했더니 예를 들어:

```
작은 플라스틱을 자주 놓침
→ FN 증가
→ Recall이 낮음
```

이런 문제가 발견됩니다.

그러면 실제 Validation 이미지를 보고:

```
무엇을 틀렸는가?
        ↓
왜 틀렸을 가능성이 있는가?
        ↓
무엇 하나를 바꿔볼 것인가?
```

를 결정합니다.

### 4. Improved Model

여기서도 **같은 Train 600장**을 사용합니다.

예를 들어 Baseline이:

```
Train = 600장
Validation = 75장
imgsz = 640
Epoch = 150
Model = YOLO11n
Seed = 42
```

이었다면 Improved는 가능하면:

```
Train = 600장          ← 동일
Validation = 75장      ← 동일
Model = YOLO11n        ← 동일
Epoch = 150            ← 동일
Seed = 42              ← 동일

imgsz = 960            ← 이것 하나만 변경
```

처럼 해야 합니다.

그래야:

> “Image Size를 변경했더니 작은 객체 FN이 실제로 감소했다.”

라고 설명할 수 있습니다.

### 5. 여기서 Final Model을 선택합니다

이 부분이 중요합니다.

```
Baseline
600장 학습
→ Validation 75장 평가

vs

Improved
600장 학습
→ 같은 Validation 75장 평가
```

비교한 뒤:

```
Precision
Recall
mAP
FP / FN
```

을 보고 **둘 중 하나를 Final Model로 선택합니다.**

### 6. Frozen Test 75장은 맨 마지막

Final Model을 선택한 다음에야 처음으로:

```
Frozen Test
75장
```

을 사용합니다.

```
Final Model 확정
        ↓
Frozen Test 75장
        ↓
Precision
Recall
mAP
Class별 성능
        ↓
실제 최종 성능과 한계 기록
```

Frozen Test 결과가 마음에 안 든다고:

```
Epoch 200으로 다시 학습
→ Test 다시 평가
→ 또 수정
```

하면 안 됩니다.

그렇게 하면 Test가 Validation처럼 되어버립니다.

### 기억하면 되는 핵심

```
Smoke Test
30~50장 정도
→ "잘 돌아가나?"

Baseline
Train 600장 전체
→ 첫 정식 기준 모델

Validation
75장
→ Baseline의 문제 발견
→ Improved와 비교

Improved
같은 Train 600장 전체
→ 한 변수만 변경하여 다시 학습

Validation
같은 75장
→ Baseline vs Improved 비교

Final Model
→ 둘 중 최종 선택

Frozen Test
75장
→ 최종 선택 후 딱 마지막 성능 확인
```

#### 확인할 것

- [ ] Smoke Test에서 만든 Weight가 아니다.
- [ ] 확정된 Train Dataset 전체로 학습한 모델이다.
- [ ] Dataset Version을 확인할 수 있다.
- [ ] `models/baseline/baseline_best.pt`로 별도 보관했다.
- [ ] 파일을 다시 Load하여 Prediction이 가능한지 확인했다.

### 2. `reports/baseline_metrics.csv`

#### 이 파일은 무엇인가요?

`baseline_metrics.csv`는 **Baseline Model의 대표 Validation 성능을 한 줄로 요약한 파일**입니다.

Ultralytics의 `results.csv`에는 Epoch별 학습 결과가 많이 들어 있습니다.

하지만 프로젝트 전체를 비교할 때는 Baseline의 최종 대표 성능만 빠르게 확인할 수 있는 요약 파일이 필요합니다.

```text
runs/baseline_v1/results.csv
→ Epoch마다 기록된 상세 학습 결과

reports/baseline_metrics.csv
→ Baseline의 대표 Validation 결과만 요약
```

#### 실제 작성 예시

```csv
model_version,dataset_version,split,imgsz,batch,epochs,seed,precision,recall,map50,map50_95
baseline_v1,kimchi_v1,val,640,8,50,42,[실제값],[실제값],[실제값],[실제값]
```

성능값은 학습 전에 임의로 작성하지 않습니다.

실제 Baseline 학습과 Validation이 끝난 뒤 측정된 값을 입력합니다.

#### 각 항목은 무엇을 의미하나요?

| 항목 | 의미 |
|---|---|
| `model_version` | Baseline 모델 이름 |
| `dataset_version` | 산출물 1에서 확정한 Dataset Version |
| `split` | 성능을 측정한 데이터, 여기서는 `val` |
| `imgsz` | 학습에 사용한 입력 이미지 크기 |
| `batch` | 한 번에 학습하는 이미지 수 |
| `epochs` | 전체 Train Dataset을 반복 학습한 횟수 |
| `seed` | 실험 재현을 위한 난수 기준값 |
| `precision` | 모델이 검출했다고 한 것 중 실제로 맞은 정도 |
| `recall` | 실제 이물을 얼마나 놓치지 않았는지 |
| `map50` | IoU 0.50 기준 객체검출 종합 성능 |
| `map50_95` | 더 엄격한 여러 IoU 기준을 평균한 성능 |

#### 왜 Validation 결과를 기록하나요?

Baseline은 이후 Improved Model과 비교하기 위한 기준입니다.

따라서 둘은 같은 Validation에서 비교해야 합니다.

```text
Baseline
→ 같은 Validation
→ Precision / Recall / mAP 기록

Improved Model
→ 같은 Validation
→ Precision / Recall / mAP 기록

        ↓

Baseline vs Improved 비교
```

> **쉽게 기억하기**  
> `baseline_metrics.csv` = Baseline의 **성적표 요약**

#### 확인할 것

- [ ] 실제 Validation 결과를 기록했다.
- [ ] Precision을 기록했다.
- [ ] Recall을 기록했다.
- [ ] mAP50을 기록했다.
- [ ] mAP50-95를 기록했다.
- [ ] Dataset Version과 Baseline 모델 버전이 기록되어 있다.
- [ ] 임의의 성능 숫자를 넣지 않았다.

#### 이 파일은 무엇인가요?

`baseline_training_condition.md`는 **Baseline을 어떤 조건으로 학습했는지 사람이 읽기 쉽게 정리한 문서**입니다.

Baseline과 Improved Model의 성능을 비교하려면:

```text
어떤 Model을 사용했는가?
어떤 Dataset Version인가?
Image Size는 얼마인가?
Batch는 얼마인가?
Epoch는 얼마인가?
Seed는 무엇인가?
Pretrained Weight를 사용했는가?
Optimizer와 Learning Rate는 무엇인가?
어떤 GPU와 Ultralytics 버전에서 실행했는가?
```

를 다시 확인할 수 있어야 합니다.

#### 실제 작성 예시

```markdown
# Baseline Training Condition

## Model
- Model: YOLO11n
- Pretrained: True

## Environment
- GPU: [실제 GPU]
- Python: [실제 버전]
- PyTorch: [실제 버전]
- Ultralytics: [실제 버전]

## Output
- Run Name: baseline_v1
- Best Weight: models/baseline/baseline_best.pt
```

위의 `640`, `8`, `50`, `42`는 **작성 형식을 보여주는 예시값**입니다.

실제로 사용한 값을 기록해야 합니다.

#### 왜 학습조건을 따로 남기나요?

나중에 Improved Model에서 성능이 달라졌을 때 무엇이 달라졌는지 확인해야 하기 때문입니다.

예:

```text
Baseline
Image Size = 640

Improved
Image Size = 960

나머지 주요 조건 유지

        ↓

Image Size 변경이 성능에 어떤 영향을 주었는지 비교 가능
```

Baseline 학습조건이 기록되지 않았다면:

```text
Baseline이 어떤 조건이었지?
Batch가 몇이었지?
Seed가 같았나?
Dataset이 같았나?

→ 공정한 비교가 어려움
```

이 됩니다.

> **쉽게 기억하기**  
> `baseline_training_condition.md` = Baseline을 **어떤 조건으로 만들었는지 기록한 실험 레시피**

#### 확인할 것

- [ ] Model 이름을 적었다.
- [ ] Dataset Version을 적었다.
- [ ] `configs/dataset.yaml`을 사용했다는 것을 확인했다.
- [ ] Image Size / Batch / Epoch / Seed를 기록했다.
- [ ] Optimizer / Learning Rate의 실제 사용값을 기록했다.
- [ ] GPU와 주요 실행환경 버전을 기록했다.
- [ ] Baseline Weight 위치를 기록했다.

### 4. `runs/baseline_v1/results.csv`

#### 이 파일은 무엇인가요?

`results.csv`는 **YOLO 학습 과정에서 Epoch별로 기록되는 상세 학습 결과 파일**입니다.

직접 성능값을 하나씩 입력해서 만드는 파일이 아니라, Baseline 학습을 실행한 결과로 
생성되는 학습 로그입니다.

```text
Baseline 학습 실행
        ↓
Epoch 1
Epoch 2
Epoch 3
...
Epoch 50
        ↓
각 Epoch의 Loss와 Validation 성능 기록
        ↓
runs/baseline_v1/results.csv
```

#### 내용은 어떤 형태인가요?

Ultralytics 버전에 따라 컬럼명은 조금 달라질 수 있지만, 일반적으로 
다음과 같은 학습 기록이 포함됩니다.

```csv
epoch,train/box_loss,train/cls_loss,metrics/precision,metrics/recall,metrics/mAP50,metrics/mAP50-95,...
1,[실제값],[실제값],[실제값],[실제값],[실제값],[실제값],...
2,[실제값],[실제값],[실제값],[실제값],[실제값],[실제값],...
3,[실제값],[실제값],[실제값],[실제값],[실제값],[실제값],...
```

이 파일의 컬럼명을 임의로 바꾸거나 새로운 값을 만들어 넣을 필요가 없습니다.

학습 결과를 그대로 보존합니다.

#### 이 파일로 무엇을 확인할 수 있나요?

```text
Epoch가 진행되면서
        ↓
Train Loss가 어떻게 변했는가?
        ↓
Validation Precision은 어떻게 변했는가?
        ↓
Recall은 어떻게 변했는가?
        ↓
mAP50 / mAP50-95는 어떻게 변했는가?
        ↓
best.pt가 어떤 학습 과정에서 만들어졌는가?
```

를 확인할 수 있습니다.

즉 `baseline_metrics.csv`가 **최종 대표 성적표**라면:

```text
results.csv
→ 학습 과정 전체 기록

baseline_metrics.csv
→ 그중 프로젝트 비교에 사용할 대표 결과 요약
```

입니다.

> **쉽게 기억하기**  
> `results.csv` = Baseline이 **Epoch마다 어떻게 학습되었는지 남은 전체 학습 기록**

#### 확인할 것

- [ ] Baseline 학습 결과 폴더의 `results.csv`를 보존했다.
- [ ] 다른 실험의 `results.csv`와 섞이지 않는다.
- [ ] `baseline_v1` Run 결과임을 확인할 수 있다.
- [ ] 임의로 성능값을 수정하지 않았다.
- [ ] `baseline_metrics.csv`의 대표 값이 실제 학습 결과와 연결된다.

```text
best.pt 생성
        ↓

        ↓

        ↓
2. reports/baseline_metrics.csv
→ Precision / Recall / mAP 결과 요약
        ↓

        ↓
다음 단계

```

# 3. Failure Analysis — 작성 예시

Failure Analysis는 **2번 산출물에서 만든 Baseline Model이 Validation 데이터에서 어디에서 틀리는지 찾아내고, 다음 개선 실험의 근거를 만드는 단계**입니다.

단순히 다음처럼 적는 것은 실패분석이 아닙니다.

```text
mAP가 낮다.
Recall이 낮다.
```

왜 낮은지 **실제 실패 이미지와 기록을 보고 구체적으로 찾아야 합니다.**

```text
Baseline Model
        ↓
Validation Prediction 확인
        ↓
FP / FN / Class / BBox 오류 찾기
        ↓
반복되는 실패 패턴 확인
        ↓
실패 원인 가설 작성
        ↓
다음 개선 실험에서 바꿀 변수 1개 결정
```

> **중요**
>
> Failure Analysis는 **Validation 데이터**를 사용합니다.  
> 이 단계에서 Frozen Test와 Bridge Holdout을 보고 모델을 개선하지 않습니다.

---

## 먼저 실패 유형을 이해합니다

```text
FP (False Positive)
→ 실제 이물이 없는데 모델이 있다고 잘못 검출

FN (False Negative)
→ 실제 이물이 있는데 모델이 놓침

Class Error
→ 객체는 찾았지만 다른 Class로 잘못 예측

BBox Error
→ 객체는 찾았지만 BBox 위치나 크기가 많이 틀림

Small Object Failure
→ 작은 이물을 반복적으로 놓침

Scene Failure
→ 특정 scene_type에서 반복적으로 실패
```

조각김치 이물검출 프로젝트에서는 **실제 이물을 놓치는 FN**이 중요하므로 Recall과 함께 확인합니다.

---

## 실제 제출하는 3번 산출물

```text
1. reports/failure_analysis.csv

2. demo/failure_analysis/
   ├── fn_*.jpg
   ├── fp_*.jpg
   ├── class_*.jpg
   └── bbox_*.jpg

3. reports/failure_hypothesis.md
```

> `failure_hypothesis.md`는 기존 산출물의 **“실패 원인 가설과 다음 실험 근거”**를  
> 실제 제출할 수 있도록 파일명까지 명확하게 정한 것입니다.

이제 위 3개 산출물을 **순서대로 무엇을 만들고 어떻게 작성하는지** 확인합니다.

---

### 1. `reports/failure_analysis.csv`

#### 이 파일은 무엇인가요?

`failure_analysis.csv`는 **Baseline Model이 Validation 이미지에서 실패한 사례를 한 건씩 기록하는 분석표**입니다.

단순히 실패 이미지 이름만 기록하지 않습니다.

각 실패 사례에 대해 다음 내용을 함께 기록합니다.

```text
어떤 이미지인가?
        ↓
어떤 장면(scene_type)인가?
        ↓
무슨 실패인가? FP / FN / Class / BBox
        ↓
실제 정답은 무엇인가?
        ↓
모델은 무엇이라고 예측했는가?
        ↓
왜 실패했다고 생각하는가?
        ↓
다음에 무엇을 바꿔볼 것인가?
```

#### ==실제 작성 예시==

```csv
image,source_dataset,scene_type,failure_type,ground_truth,prediction,confidence,suspected_cause,evidence,next_action
<실제파일명1>.jpg,dataset2,kimchi_with_target,FN,plastic,none,,small_object,"작은 플라스틱이 여러 이미지에서 반복적으로 누락됨","imgsz 변경 검토"
<실제파일명2>.jpg,dataset2,normal_kimchi,FP,none,leaf,0.61,background_confusion,"정상 김치 영역을 잎으로 반복 오검출","정상 장면 FP 비교"
<실제파일명3>.jpg,dataset1,object_only,CLASS,branch,leaf,0.58,class_similarity,"나뭇가지와 잎 형태를 혼동함","Class별 오류 비교"
<실제파일명4>.jpg,dataset2,kimchi_with_target,BBOX,plastic,plastic,0.72,localization_error,"객체는 찾았지만 BBox가 실제 객체보다 크게 표시됨","BBox 오류 사례 비교"
```

실제 수업에서는 `<실제파일명>` 부분에 Validation에서 확인한 실제 이미지 파일명을 입력합니다.

---

#### 각 컬럼의 의미

| 항목 | 의미 |
|---|---|
| `image` | 실패가 발생한 실제 이미지 |
| `source_dataset` | Dataset 1 / Dataset 2 중 어디에서 온 데이터인지 |
| `scene_type` | `kimchi_with_target`, `normal_kimchi`, `object_only` 등 |
| `failure_type` | `FP`, `FN`, `CLASS`, `BBOX` 등 실패 유형 |
| `ground_truth` | 실제 정답 Class |
| `prediction` | 모델이 예측한 Class 또는 `none` |
| `confidence` | 모델 예측 신뢰도 |
| `suspected_cause` | 실패한 것으로 추정되는 원인 |
| `evidence` | 왜 그렇게 판단했는지 실제 관찰 근거 |
| `next_action` | 다음 개선 실험에서 확인할 내용 |

---

#### 어떻게 작성하나요?

먼저 Baseline Model을 **Validation 데이터**에 적용합니다.

```text
models/baseline/baseline_best.pt
        ↓
Validation 이미지 Prediction
        ↓
GT와 Prediction 비교
        ↓
실패 이미지 찾기
        ↓
failure_analysis.csv에 한 줄씩 기록
```

예를 들어 실제 이미지에 플라스틱이 있는데 모델이 아무것도 찾지 못했다면:

```text
실제 정답
→ plastic 있음

모델 Prediction
→ 없음

판정
→ FN

CSV 기록
→ failure_type = FN
```

정상 김치 이미지인데 모델이 나뭇잎이라고 검출했다면:

```text
실제 정답
→ 이물 없음

모델 Prediction
→ leaf 0.61

판정
→ FP

CSV 기록
→ failure_type = FP
```

---

#### 몇 건을 기록하나요?

모든 오류를 보고서에 길게 설명할 필요는 없습니다.

먼저 전체 Validation Prediction을 확인한 뒤, **반복되는 패턴을 보여주는 대표 실패 사례 10~20건 정도**를 수집합니다.

예:

```text
FN 6건
FP 5건
Class Error 4건
BBox Error 3건

총 대표 사례 18건
```

이 숫자는 고정값이 아닙니다. 실제 Baseline 결과에서 의미 있는 대표 사례를 선택합니다.

> **쉽게 기억하기**  
> `failure_analysis.csv` = 모델이 **어디에서 어떻게 틀렸는지 한 건씩 기록한 실패 장부**

#### 확인할 것

- [ ] Baseline Validation 결과를 기준으로 작성했다.
- [ ] Frozen Test를 개선용 실패분석에 사용하지 않았다.
- [ ] Bridge Holdout을 열어보고 개선하지 않았다.
- [ ] 대표 FP를 포함했다.
- [ ] 대표 FN을 포함했다.
- [ ] 필요한 경우 Class / BBox 오류도 기록했다.
- [ ] 실제 이미지 파일명이 기록되어 있다.
- [ ] `evidence`와 `next_action`이 단순 추측이 아니라 실제 사례와 연결되어 있다.

### 2. `demo/failure_analysis/` 대표 실패 이미지

그래서 대표 실패 이미지에는 **정답(GT)과 모델 Prediction을 비교해서 볼 수 있는 결과 이미지**를 함께 남깁니다.

```text
demo/
```

```text
1. 실제 정답 GT
2. 모델 Prediction
3. 실패 유형 FP / FN / CLASS / BBOX
```

> **쉽게 기억하기**

### 3. `reports/failure_hypothesis.md`

#### 이 파일은 무엇인가요?

`failure_hypothesis.md`는 **CSV와 대표 실패 이미지를 보고 반복되는 문제를 정리한 뒤, 다음 개선 실험에서 무엇을 한 가지 바꿀지 결정하는 문서**입니다.

이 파일이 중요한 이유는 Failure Analysis가 단순한 오류 수집으로 끝나지 않고 **4번 Improved Model로 연결되어야 하기 때문**입니다.

```text
실패 사례 수집
        ↓
반복 패턴 발견
        ↓
원인 가설 작성
        ↓
근거 확인
        ↓
다음 실험 변수 1개 결정
        ↓
4번 Improved Model로 연결
```

---

#### ==실제 작성 예시==

```markdown
# Failure Analysis Hypothesis

- Weight: models/baseline/baseline_best.pt
- Dataset Version: kimchi_v1

- 대표 이미지: demo/failure_analysis/fn_small_plastic_02.jpg

근거:
- 대표 이미지: demo/failure_analysis/fp_normal_kimchi_01.jpg

선택:
- 작은 플라스틱 객체의 FN

- 조각김치 이물검출에서는 실제 이물을 놓치는 FN이 중요합니다.

## 5. 다음 개선 실험

Baseline:
- imgsz = 640

Improved Experiment:
- imgsz = [실제 변경값]

유지할 조건:

- 같은 Train / Validation
- 같은 Model 계열
- 같은 Seed
- 같은 평가 방법

- Image Size 하나만 변경

- Validation Recall 변화

- mAP50 / mAP50-95 변화
```

초보자가 가장 헷갈리기 쉬운 부분입니다.

##### 관찰

실제 결과에서 무엇을 보았는지를 적습니다.

```text
작은 플라스틱을 여러 번 놓쳤다.
```

##### 근거

어디에서 그렇게 확인했는지를 적습니다.

```text
+
failure_analysis.csv
+
대표 실패 이미지
```

##### 가설

왜 그런 일이 발생했을 것이라고 생각하는지 적습니다.

```text
작은 객체인데 입력 Image Size가 충분하지 않을 수 있다.
```

가설은 아직 확정된 사실이 아닙니다.

따라서:

```text
원인은 Image Size 때문이다.
```

라고 단정하기보다:

```text
Image Size가 영향을 주었을 가능성이 있다고 가정한다.
```

처럼 작성하는 것이 맞습니다.

##### 다음 실험

가설을 확인하기 위해 다음 단계에서 실제로 바꿔볼 변수를 정합니다.

```text

imgsz = 640

        ↓

Improved
imgsz = [새 값]

나머지 주요 조건 유지
```

> **쉽게 기억하기**  
> `failure_hypothesis.md` = **무엇이 반복적으로 문제였고, 그래서 다음에 무엇 하나를 바꿔볼 것인지 정리한 문서**

##### 확인할 것

- [ ] Baseline Validation을 분석 대상으로 명시했다.
- [ ] 가장 중요한 반복 실패 패턴을 적었다.
- [ ] 실제 CSV와 대표 이미지가 근거로 연결되어 있다.
- [ ] 관찰과 가설을 구분했다.
- [ ] 다음 개선 실험에서 바꿀 변수 하나를 정했다.
- [ ] 나머지 주요 조건은 유지하도록 작성했다.
- [ ] 4번 Improved Model과 바로 연결될 수 있다.

```text
Failure Analysis 산출물 확정
        ↓
다음 단계
4. Improved / Final Model
```

---

## 산출물 3 최종 제출 체크리스트

- [ ] **1. `reports/failure_analysis.csv`** — Baseline Validation의 대표 FP / FN / Class / BBox 오류를 기록했다.
- [ ] **2. `demo/failure_analysis/*.jpg`** — GT와 Prediction을 비교할 수 있는 대표 실패 이미지를 준비했다.
- [ ] **3. `reports/failure_hypothesis.md`** — 반복되는 실패 패턴과 근거, 원인 가설, 다음 개선 변수 1개를 정리했다.

> **산출물 3의 핵심**
>
> Baseline Model을 Validation에서 평가하고 
> → `failure_analysis.csv`에 실제 실패를 기록하고 
> → 대표 실패 이미지로 눈으로 확인한 뒤 
> → `failure_hypothesis.md`에서 반복되는 원인 가설과 다음 
> 개선 실험의 변수 하나를 결정합니다.

# 4. Improved / Final Model — 작성 예시

Improved Model은 **3번 Failure Analysis에서 찾은 실패 원인을 바탕으로, 주요 변수 하나를 바꾸어 다시 학습한 모델**입니다.

Final Model은 Baseline Model과 Improved Model을 **같은 Validation 데이터에서 비교한 뒤 최종적으로 선택한 모델**입니다.

두 개념을 먼저 구분합니다.

```text
Baseline Model
→ 개선 전 기준 모델

Improved Model
→ 실패분석 근거를 바탕으로
   주요 변수 하나를 바꾸어 다시 학습한 모델

Final Model
→ Baseline과 Improved를 같은 Validation에서 비교한 뒤
   최종적으로 선택한 모델
```

교과 8에서는 단순히 더 높은 mAP의 Weight를 고르는 것이 아니라,

```text
Failure Analysis 근거
+
같은 Validation 성능 비교
+
대표 FP / FN 변화
```

를 함께 보고 Final Model을 선택합니다.

> **중요**
>
> Final Model은 **Frozen Test를 보기 전에 먼저 선택**합니다.  
> Frozen Test 결과를 보고 다시 모델을 바꾸는 방식으로 사용하지 않습니다.

---

## 실제 제출하는 4번 산출물

```text
1. models/improved/exp001_best.pt

2. reports/improvement_experiment.md

3. models/final/final_best.pt

4. reports/final_model_selection.md
```

> `exp001_best.pt`의 `EXP001`은 첫 번째 개선 실험이라는 뜻입니다.  
> 개선 실험이 여러 개라면 `exp002_best.pt`, `exp003_best.pt`처럼 구분할 수 있습니다.

이제 위 4개 파일을 **순서대로 무엇을 만들고 어떻게 작성하는지** 확인합니다.

---

### 1. `models/improved/exp001_best.pt`

#### 이 파일은 무엇인가요?

`exp001_best.pt`는 **3번 Failure Analysis에서 정한 개선 변수 하나를 바꾸어 다시 학습한 Improved Model의 Weight 파일**입니다.

예를 들어 3번 산출물에서 다음과 같은 가설을 세웠다고 하겠습니다.

```text
관찰
→ 작은 플라스틱 FN이 반복적으로 발생

가설
→ 입력 Image Size가 작은 객체를 표현하기에 부족할 수 있음

다음 실험
→ Image Size만 변경
```

그러면 4번에서는 실제로 그 변수 하나만 바꾸어 다시 학습합니다.

```text
Baseline
imgsz = 640

        ↓

Improved EXP001
imgsz = 960

나머지 주요 조건 유지
```

`960`은 작성 예시입니다. 실제 수업에서는 팀이 선택한 값을 사용합니다.

---

#### 실제 학습 흐름

```text
3번 failure_hypothesis.md
        ↓
개선 변수 1개 선택
        ↓
Baseline 학습조건 확인
        ↓
한 변수만 변경
        ↓
YOLO11 다시 학습
        ↓
Validation 수행
        ↓
best.pt 생성
        ↓
models/improved/exp001_best.pt로 별도 보관
```

#### 실제 파일 위치 예시

```text
runs/
└── exp001/
    └── weights/
        ├── best.pt
        └── last.pt

        ↓ best.pt 복사

models/
└── improved/
    └── exp001_best.pt
```

#### 왜 `best.pt`를 그대로 두지 않나요?

Baseline과 Improved를 구분해야 하기 때문입니다.

```text
models/baseline/baseline_best.pt
→ 개선 전 기준 모델

models/improved/exp001_best.pt
→ 첫 번째 개선 실험 모델
```

파일명만 보아도 어떤 역할의 모델인지 알 수 있게 합니다.

> **쉽게 기억하기**  
> `exp001_best.pt` = Failure Analysis에서 정한 **개선 가설을 실제로 시험한 모델**

##### 확인할 것

- [ ] 3번 Failure Analysis의 가설과 연결된 실험이다.
- [ ] 한 번에 주요 변수 하나만 바꾸었다.
- [ ] Dataset Version은 Baseline과 같다.
- [ ] Train / Validation Split은 Baseline과 같다.
- [ ] 나머지 주요 학습조건을 가능한 한 동일하게 유지했다.
- [ ] `models/improved/exp001_best.pt`로 별도 보관했다.
- [ ] Frozen Test를 사용하지 않았다.

---

### 2. `reports/improvement_experiment.md`

#### 이 파일은 무엇인가요?

`improvement_experiment.md`는 **왜 이 변수를 바꾸었고, Baseline과 무엇이 다르며, 무엇을 비교하려는 실험인지 기록하는 문서**입니다.

Improved Model의 Weight만 남기면 나중에 다음 내용을 알기 어렵습니다.

```text
왜 이 실험을 했지?
무엇을 바꿨지?
Baseline과 어떤 조건이 같았지?
무엇이 좋아지면 성공이라고 볼 거지?
```

따라서 실험 전에 개선 근거와 조건을 문서로 남깁니다.

---

#### 실제 작성 예시

```markdown
# Improvement Experiment

## 1. Experiment

- Experiment ID: EXP001
- Dataset Version: kimchi_v1
- Baseline Model: models/baseline/baseline_best.pt

## 2. Failure Analysis 근거

관찰:
- Validation에서 작은 플라스틱 객체의 FN이 반복적으로 발생했습니다.

- reports/failure_analysis.csv
- demo/failure_analysis/fn_small_plastic_01.jpg
- demo/failure_analysis/fn_small_plastic_02.jpg

가설:
- 입력 Image Size가 작은 객체의 특징을 충분히 표현하지 못했을 가능성이 있다고 판단했습니다.

## 3. 변경 변수

Baseline:
- imgsz = 640

EXP001:
- imgsz = 960

변경 변수:
- Image Size

## 4. 유지한 조건

- Dataset Version: kimchi_v1
- Train Split: 동일
- Validation Split: 동일
- Model: YOLO11n
- Seed: 42
- Epoch: 50
- Batch: 8
- 평가 방법: 동일

## 5. 확인할 결과

- Validation Precision
- Validation Recall
- Validation mAP50
- Validation mAP50-95
- 작은 플라스틱 FN 수
```

실제 값은 사용한 학습조건을 기록합니다.

---

#### 왜 한 변수만 바꾸나요?

여러 가지를 한꺼번에 바꾸면 무엇 때문에 결과가 달라졌는지 알 수 없습니다.

좋은 예:

```text
Baseline
imgsz = 640

        ↓

EXP001
imgsz = 960

나머지 주요 조건 동일
```

좋지 않은 예:

```text
Model 변경
+
Image Size 변경
+
Epoch 변경
+
Augmentation 변경
+
Dataset 변경
```

이 경우 성능이 좋아져도 무엇이 영향을 주었는지 설명하기 어렵습니다.

> **쉽게 기억하기**  
> `improvement_experiment.md` = **왜 무엇 하나를 바꾸었는지 기록한 실험 계획서**

##### 확인할 것

- [ ] Experiment ID가 있다.
- [ ] 3번 Failure Analysis의 실제 근거가 연결되어 있다.
- [ ] Baseline 값과 Improved 값을 함께 적었다.
- [ ] 변경 변수는 주요 변수 하나다.
- [ ] 유지한 조건을 적었다.
- [ ] 어떤 지표와 실패 사례를 비교할지 적었다.
- [ ] 실제 사용한 값을 기록했다.

### 3. `models/final/final_best.pt`

#### 이 파일은 무엇인가요?

`final_best.pt`는 **Baseline Model과 Improved Model을 같은 Validation에서 비교한 뒤 최종적으로 선택한 모델 Weight**입니다.

중요한 점은 `final_best.pt`가 반드시 Improved Model이어야 하는 것은 아니라는 것입니다.

예를 들어 Improved Model의 Recall이 좋아졌지만 Precision이 크게 떨어지고 FP가 급증했다면 Baseline을 Final Model로 선택할 수도 있습니다.

```text
Baseline
        +
Improved EXP001
        ↓
같은 Validation에서 비교
        ↓
성능지표 비교
+
대표 FP / FN 비교
        ↓
Final Model 선택
```

선택한 Weight를 다음 위치에 별도로 보관합니다.

```text
models/
└── final/
    └── final_best.pt
```

---

##### 예시 1 — Improved Model을 선택한 경우

```text
models/improved/exp001_best.pt
        ↓ 복사
models/final/final_best.pt
```

##### 예시 2 — Baseline을 선택한 경우

```text
models/baseline/baseline_best.pt
        ↓ 복사
models/final/final_best.pt
```

즉 `final_best.pt`는 **최종 선택 결과를 대표하는 고정된 파일명**입니다.

---

#### Final Model을 선택하는 순서

```text
Baseline Validation 결과
        +
Improved Validation 결과
        ↓
같은 Validation에서 비교
        ↓
Precision / Recall / mAP 비교
        ↓
대표 FP / FN 변화 비교
        ↓
Final Model 선택
        ↓
models/final/final_best.pt
        ↓
그 다음에만 Frozen Test 평가
```

> **쉽게 기억하기**  
> `final_best.pt` = 교과 8에서 **최종적으로 선택한 모델**

#### 확인할 것

- [ ] Baseline과 Improved를 같은 Validation에서 비교했다.
- [ ] Validation 성능만 보고 자동 선택하지 않고 대표 실패도 함께 확인했다.
- [ ] Frozen Test를 보기 전에 Final Model을 선택했다.
- [ ] 선택한 Weight를 `models/final/final_best.pt`로 별도 보관했다.
- [ ] 어떤 원본 Weight를 Final로 선택했는지 기록되어 있다.
- [ ] Final Model을 다시 Load할 수 있다.

---

### 4. `reports/final_model_selection.md`

#### 이 파일은 무엇인가요?

`final_model_selection.md`는 **Baseline과 Improved Model을 비교한 뒤 왜 이 모델을 Final Model로 선택했는지 설명하는 문서**입니다.

단순히 다음처럼 적으면 부족합니다.

```text
EXP001의 mAP가 높아서 선택했습니다.
```

교과 8에서는 다음을 함께 봅니다.

```text
Validation Precision
Validation Recall
mAP50
mAP50-95
대표 FP
대표 FN
Failure Analysis에서 문제였던 패턴이 실제로 줄었는가?
```

특히 조각김치 이물검출에서는 실제 이물을 놓치는 **FN과 Recall 변화**도 함께 확인합니다.

---

#### 실제 작성 예시

```markdown

Improved:
```

---

#### Baseline을 Final로 선택할 수도 있습니다

Improved Model이라고 해서 반드시 Final이 되는 것은 아닙니다.

예를 들어:


```markdown
- Baseline

Final Weight:
- models/final/final_best.pt

원본 Weight:
- models/baseline/baseline_best.pt
```

> **쉽게 기억하기**  
> `final_model_selection.md` = **왜 이 모델이 최종 모델이 되었는지 증명하는 선택 근거서**

- [ ] Precision / Recall / mAP를 비교했다.
- [ ] 3번 Failure Analysis의 핵심 오류 변화도 비교했다.
- [ ] 선택 이유가 실제 측정값과 이미지 근거에 연결된다.
- [ ] Final Model을 Frozen Test 전에 선택했다고 기록했다.
- [ ] `final_best.pt`의 원본 Weight가 무엇인지 기록했다.

# 5. 성능·실험 기록 — 작성 예시

5번 산출물은 **Baseline Model부터 Improved Model, Final Model까지 어떤 조건으로 실험했고 성능이 어떻게 달라졌는지 숫자와 그래프로 남기는 결과**입니다.

4번까지는 다음을 결정했습니다.

```text
Baseline Model
        ↓
Failure Analysis
        ↓
한 변수 개선
        ↓
Improved Model
        ↓
같은 Validation에서 비교
        ↓
Final Model 선택
```

5번에서는 이 과정을 다시 확인할 수 있도록 **성능값, 실험조건, 그래프, 비교 결과를 정리**합니다.

단순히 다음처럼 쓰는 것은 충분하지 않습니다.

```text
Final mAP가 높게 나왔습니다.
```

대신 다음을 함께 확인할 수 있어야 합니다.

```text
어떤 Dataset Version을 사용했는가?
        ↓
Baseline 성능은 얼마였는가?
        ↓
무엇을 한 가지 바꾸었는가?
        ↓
Improved 성능은 어떻게 달라졌는가?
        ↓
FP / FN은 실제로 줄었는가?
        ↓
어떤 모델을 Final로 선택했는가?
        ↓
Frozen Test에서 최종 성능은 얼마였는가?
```

교과 8에서는 Precision·Recall·mAP뿐 아니라 실제 FP/FN과 Class별 성능도 함께 확인합니다. 현재 산출물 기준에서도 5번은 **학습조건과 Baseline·개선 결과를 비교하는 성능·실험 기록**으로 정의되어 있습니다. fileciteturn17file0L47-L56

## 먼저 성능지표를 간단히 이해합니다

![[Pasted image 20261004214119.png]]

```text
Precision
→ AI가 이물이라고 검출한 것 중
   실제로 맞은 비율
→ FP와 관련

Recall
→ 실제 이물 중
   AI가 놓치지 않고 찾은 비율
→ FN과 관련

mAP50
→ IoU 0.50 기준에서 본
   객체검출 종합 성능

mAP50-95
→ 더 엄격한 여러 IoU 기준을 평균한 성능

Class별 성능
→ 어떤 이물 종류에서는 잘 찾고
   어떤 이물 종류에서는 약한지 확인

실제 FP / FN
→ 숫자만으로 보이지 않는
   실제 검출 실패를 확인
```

조각김치 이물검출 프로젝트에서는 특히 **실제 이물을 놓치는 FN과 Recall**을 함께 봅니다.

```text
4. reports/figures/
```

이제 위 5개 산출물을 **순서대로 무엇을 확인하고 어떻게 작성하는지** 알아봅니다.

---

### 1. `reports/baseline_metrics.csv`

#### 이 파일은 무엇인가요?

`baseline_metrics.csv`는 **개선 전 기준 모델인 Baseline의 Validation 대표 성능을 기록한 파일**입니다.

2번 산출물에서 이미 만들었지만, 5번에서는 Improved Model과 비교할 **출발점**으로 사용합니다.

```text
Baseline Validation
        ↓
Precision
Recall
mAP50
mAP50-95
        ↓
baseline_metrics.csv
```

#### ==실제 작성 예시==

```csv
model,dataset_version,split,precision,recall,map50,map50_95
baseline_v1,kimchi_v1,val,[실제값],[실제값],[실제값],[실제값]
```

`[실제값]`에는 Baseline을 실제 Validation에서 평가한 값을 기록합니다.

임의 숫자를 넣지 않습니다.

---

#### 왜 다시 제출하나요?

5번 산출물은 성능 비교 기록이므로 Baseline 결과가 반드시 함께 있어야 합니다.

```text
Baseline
→ 개선 전 성적

Improved
→ 개선 후 성적

둘을 비교
→ 실제로 좋아졌는지 판단
```

즉:

> **쉽게 기억하기**  
> `baseline_metrics.csv` = 개선 전 모델의 **기준 성적표**

#### 확인할 것

- [ ] 2번 산출물에서 만든 Baseline 성능 파일과 동일하다.
- [ ] 평가 Split이 `val`이다.
- [ ] Dataset Version이 기록되어 있다.
- [ ] Precision이 있다.
- [ ] Recall이 있다.
- [ ] mAP50이 있다.
- [ ] mAP50-95가 있다.
- [ ] 임의 숫자가 아니라 실제 Validation 결과다.

### 2. `reports/experiment_log.csv`

#### 이 파일은 무엇인가요?

`experiment_log.csv`는 **Baseline과 모든 개선 실험을 한 표에서 비교할 수 있도록 기록하는 실험 장부**입니다.

다음 질문에 답할 수 있어야 합니다.

```text
어떤 실험이었는가?
어떤 Dataset Version인가?
어떤 Model인가?
Image Size는 얼마인가?
Epoch / Batch / Seed는 얼마인가?
무엇을 바꾸었는가?
왜 바꾸었는가?
Validation 성능은 얼마인가?
이 실험을 유지할 것인가?
```

#### ==실제 작성 예시==

```csv
experiment_id,dataset_version,model,imgsz,epochs,batch,seed,changed_variable,reason,validation_precision,validation_recall,validation_map50,validation_map50_95,decision
BASELINE,kimchi_v1,yolo11n,640,50,8,42,none,baseline,[실제값],[실제값],[실제값],[실제값],BASELINE
EXP001,kimchi_v1,yolo11n,960,50,8,42,imgsz,small_object_fn,[실제값],[실제값],[실제값],[실제값],[KEEP 또는 REJECT]
```

위의 `640`, `960`, `50`, `8`, `42`는 작성 형식을 보여주는 예시입니다.

실제 수업에서는 팀이 실제로 사용한 값을 기록합니다.

---

#### 각 항목은 무엇을 의미하나요?

| 항목 | 의미 |
|---|---|
| `experiment_id` | `BASELINE`, `EXP001`처럼 실험을 구분하는 이름 |
| `dataset_version` | 사용한 Dataset Version |
| `model` | 사용한 모델 |
| `imgsz` | 입력 이미지 크기 |
| `epochs` | 학습 반복 횟수 |
| `batch` | 한 번에 학습할 이미지 수 |
| `seed` | 실험 재현을 위한 난수 기준값 |
| `changed_variable` | Baseline 대비 바꾼 핵심 변수 |
| `reason` | 왜 그 변수를 바꾸었는지 Failure Analysis 근거 |
| `validation_precision` | Validation Precision |
| `validation_recall` | Validation Recall |
| `validation_map50` | Validation mAP50 |
| `validation_map50_95` | Validation mAP50-95 |
| `decision` | `KEEP`, `REJECT`, `BASELINE` 등 실험 판단 |

---

#### 여러 실험을 했다면 어떻게 하나요?

실험마다 행을 하나씩 추가합니다.

예:

```csv
BASELINE,...
EXP001,...
EXP002,...
EXP003,...
```

하지만 교과 8의 핵심은 실험 개수를 많이 만드는 것이 아닙니다.

```text
Failure Analysis
        ↓
근거 있는 변수 선택
        ↓
한 번에 주요 변수 하나 변경
        ↓
결과 비교
```

가 중요합니다.

> **쉽게 기억하기**  
> `experiment_log.csv` = **무엇을 바꾸었고 결과가 어떻게 달라졌는지 한 줄씩 쌓는 실험 일지**

#### 확인할 것

- [ ] Baseline 행이 있다.
- [ ] Improved 실험 행이 있다.
- [ ] 각 실험의 Dataset Version이 기록되어 있다.
- [ ] 변경 변수를 확인할 수 있다.
- [ ] 변경 이유가 Failure Analysis와 연결된다.
- [ ] Validation Precision / Recall / mAP가 있다.
- [ ] 실제 결과를 보고 `KEEP / REJECT`를 기록했다.

### 3. `reports/final_metrics.csv`

#### 이 파일은 무엇인가요?

`final_metrics.csv`는 **4번에서 Final Model을 먼저 선택한 뒤, Frozen Test에서 처음 평가한 최종 성능을 기록하는 파일**입니다.

순서가 중요합니다.

```text
Baseline
+
Improved
        ↓
같은 Validation에서 비교
        ↓
Final Model 선택
        ↓
final_best.pt 확정
        ↓
그 다음에만 Frozen Test
        ↓
final_metrics.csv 작성
```

Frozen Test는 Final Model을 고르기 위한 데이터가 아닙니다.

**이미 선택이 끝난 Final Model의 마지막 성능을 확인하는 데이터**입니다.

#### ==실제 작성 예시== — 전체 성능

```csv
model,dataset_version,split,scope,class_id,class_name,precision,recall,map50,map50_95
final_best,kimchi_v1,test,overall,ALL,ALL,[실제값],[실제값],[실제값],[실제값]
```

#### Class별 성능도 함께 남기는 예시

Frozen Test에서 Class별 평가값을 확인할 수 있다면 같은 파일에 이어서 기록할 수 있습니다.

```csv
model,dataset_version,split,scope,class_id,class_name,precision,recall,map50,map50_95
final_best,kimchi_v1,test,overall,ALL,ALL,[실제값],[실제값],[실제값],[실제값]
final_best,kimchi_v1,test,class,0,leaf_paper,[실제값],[실제값],[실제값],[실제값]
final_best,kimchi_v1,test,class,1,plastic_stone_metal,[실제값],[실제값],[실제값],[실제값]
final_best,kimchi_v1,test,class,2,branch,[실제값],[실제값],[실제값],[실제값]
final_best,kimchi_v1,test,class,3,insect,[실제값],[실제값],[실제값],[실제값]
final_best,kimchi_v1,test,class,4,rubber_glove_unused,N/A,N/A,N/A,N/A
final_best,kimchi_v1,test,class,5,disease_browning,[실제값],[실제값],[실제값],[실제값]
final_best,kimchi_v1,test,class,6,green_onion_pepper,[실제값],[실제값],[실제값],[실제값]
```

Class 4가 실제 정답 Instance 0건이면 Recall이나 AP를 의미 있게 계산할 수 없으므로 다음처럼 기록합니다.

```text
Class 4
→ 미사용 Class
→ Test GT Instance = 0
→ Recall / AP = N/A
```

---

#### Frozen Test 결과가 예상보다 낮으면 어떻게 하나요?

다음처럼 사용하면 안 됩니다.

```text
Frozen Test 결과 확인
        ↓
성능이 낮음
        ↓
다시 모델 수정
        ↓
같은 Test로 다시 확인
        ↓
또 수정

X
```

이렇게 하면 Test가 사실상 Validation처럼 사용됩니다.

Frozen Test에서는:

```text
Final Model 확정
        ↓
Frozen Test 평가
        ↓
결과 기록
        ↓
현재 모델의 한계로 해석
```

합니다.

> **쉽게 기억하기**  
> `final_metrics.csv` = Final Model의 **마지막 시험 성적표**

#### 확인할 것

- [ ] Final Model을 선택한 뒤 Frozen Test를 평가했다.
- [ ] `split = test`로 기록했다.
- [ ] 전체 Precision / Recall / mAP를 기록했다.
- [ ] 가능하면 Class별 성능도 기록했다.
- [ ] Class 4 Instance가 0이면 `N/A` 등으로 명확하게 표시했다.
- [ ] Frozen Test를 반복 튜닝에 사용하지 않았다.
- [ ] 실제 측정값만 기록했다.

### 4. `reports/figures/*.png`

#### 이 산출물은 무엇인가요?

숫자만 보면 모델의 학습 과정이나 Class별 오류를 한눈에 파악하기 어렵습니다.

그래서 Ultralytics가 학습·평가 과정에서 생성한 주요 그래프를 **PNG 이미지 파일로 보존**합니다.

그래프 값을 임의로 그려서 만드는 것이 아니라, **실제 학습과 평가에서 나온 결과 그래프를 사용**합니다.

#### ==실제 제출== 파일 예시

```text
reports/
└── figures/
    ├── baseline_results.png
    ├── baseline_confusion_matrix.png
    ├── exp001_results.png
    ├── exp001_confusion_matrix.png
    └── final_test_confusion_matrix.png
```

Ultralytics 버전이나 실행 방법에 따라 실제 자동 생성 파일명은 조금 달라질 수 있습니다.

자동 생성 결과를 확인한 뒤 프로젝트 안에서는 역할이 보이도록 이름을 정리합니다.

---

##### 4-1. `baseline_results.png`

Baseline 학습 과정의 주요 변화가 보이는 그래프입니다.

일반적으로 다음과 같은 내용을 확인합니다.

```text
Epoch 진행
        ↓
Train Loss 변화
        ↓
Validation 성능 변화
        ↓
Precision / Recall / mAP 변화
```

> `baseline_results.png` = **Baseline이 학습되는 과정을 보여주는 그래프**

---

##### 4-2. `baseline_confusion_matrix.png`

Baseline이 어떤 Class를 다른 Class와 혼동했는지 확인하는 그래프입니다.

예를 들어:

```text
실제 branch
        ↓
모델이 leaf로 예측

→ Class 혼동 확인
```

3번 Failure Analysis의 Class Error를 해석할 때도 참고할 수 있습니다.

> `baseline_confusion_matrix.png` = **Baseline이 어떤 Class를 헷갈렸는지 보여주는 그림**

---

##### 4-3. `exp001_results.png`

Improved Model의 학습 과정과 Validation 성능 변화를 보여주는 그래프입니다.

Baseline 그래프와 비교하면:

```text
Baseline 학습
vs
EXP001 학습

→ 개선 실험이 안정적으로 학습되었는지 확인
```

할 수 있습니다.

---

##### 4-4. `exp001_confusion_matrix.png`

Improved Model이 Class별로 무엇을 잘 맞히고 무엇을 혼동했는지 확인합니다.

Baseline의 Confusion Matrix와 비교하여:

```text
Class 혼동이 줄었는가?
새로운 오류가 늘었는가?
```

를 확인할 수 있습니다.

---

##### 4-5. `final_test_confusion_matrix.png`

Final Model을 Frozen Test에서 평가했을 때의 Class별 최종 혼동 결과입니다.

이 결과는 **Final Model 선택 후** 만들어야 합니다.

```text
Final Model 확정
        ↓
Frozen Test
        ↓
Confusion Matrix
        ↓
final_test_confusion_matrix.png
```

> **쉽게 기억하기**  
> `reports/figures/` = **숫자로 기록한 성능을 실제 그래프로 확인하는 증빙 폴더**

#### 확인할 것

- [ ] 실제 학습·평가에서 생성된 그래프다.

### 5. `reports/baseline_vs_improved.md`

#### 이 파일은 무엇인가요?

`baseline_vs_improved.md`는 **Baseline과 Improved Model을 같은 Validation에서 직접 비교하여 실제로 무엇이 좋아지고 무엇이 나빠졌는지 정리하는 비교 문서**입니다.

`experiment_log.csv`가 여러 실험을 한 줄씩 기록하는 장부라면:

```text
experiment_log.csv
→ 실험 전체 기록

baseline_vs_improved.md
→ 핵심 Baseline vs Improved를 사람이 읽기 쉽게 비교
```

하는 역할입니다.

```markdown
- Precision: [개선/하락/유지]
- 작은 플라스틱 FN: [감소/증가/유지]
- 대표 FP: [감소/증가/유지]

## 5. 결론

EXP001은 [실제 결과를 근거로 작성]했습니다.

예:
- Recall이 개선되었습니다.
- 작은 플라스틱 FN이 감소했습니다.
- Precision은 크게 하락하지 않았습니다.

따라서 EXP001을 Final Model 후보로 판단했습니다.

또는 실제 결과가 좋지 않았다면:

- Recall 개선폭이 작았습니다.
- FP가 증가했습니다.
- Precision 하락이 컸습니다.

따라서 EXP001을 REJECT하고 Baseline을 유지했습니다.
```

# 6. Detection · Auto Label 결과 — 작성 예시

6번 산출물은 **5번에서 성능 검증까지 끝낸 Final Model을 실제 이미지에 적용해 보고, Detection 결과와 Auto Label 후보가 실제로 만들어지는지 확인하는 결과**입니다.

여기서는 두 가지를 구분해야 합니다.

```text
Detection
→ Final Model이 이미지에서
   BBox + Class + Confidence를 예측한 결과

Auto Label
→ Final Model의 예측 결과를
   YOLO TXT 후보 라벨로 저장한 결과
```

즉 6번 산출물은 단순히 `final_best.pt` 파일을 가지고 있다는 것을 보여주는 것이 아닙니다.

```text
Final Model
        ↓
새 이미지 또는 시연용 이미지 입력
        ↓
Detection 수행
        ↓
BBox + Class + Confidence 확인
        ↓
YOLO TXT 후보 생성
        ↓
교과 7 라벨링 프로그램에서 다시 Load
        ↓
Human Review
        ↓
수정 / 삭제 / 추가 / 승인
```

까지 실제로 연결되는 것을 보여주는 산출물입니다.

현재 교과 8 산출물 기준에서도 6번은 **새 이미지 Detection 결과와 자동 라벨 후보 생성 결과**를 남기는 단계로 정의되어 있습니다.

### 1. `demo/prediction_images/*.jpg`

#### 이 산출물은 무엇인가요?

원본 이미지만 저장하는 것이 아닙니다.

결과 이미지에는 다음이 보여야 합니다.

```text

→ 모델이 찾은 객체 위치

Class
→ 모델이 예측한 객체 종류

Confidence
→ 모델이 그 예측을 얼마나 확신하는지 나타내는 값
```

예를 들어 화면에는 다음처럼 보일 수 있습니다.

```text
└────────────┘

┌──────────┐
│ 금속     │
└──────────┘
```

```text
        ↓

        ↓
Inference
        ↓
BBox Prediction
        ↓
Class Prediction
        ↓
Confidence 확인
        ↓
Prediction 이미지 저장
```

#### 실제 파일 구조 예시

```text
demo/

    ├── predict_002.jpg
```

```text
predict_001.jpg
predict_002.jpg
predict_003.jpg
```

또는 실제 이미지명을 유지하고 싶다면:

```text

```

처럼 저장해도 됩니다.

```text
새 이미지
→ Final Model 실사용 확인에 가장 적합
```

별도의 새 이미지가 없다면, 교과 8의 Frozen Test 최종평가를 **모두 끝낸 뒤** Test 이미지 일부를 기능 시연용으로 복사하여 사용할 수 있습니다.

```text

Test 성능을 맞추는 데 사용 X
```

해야 합니다.

> **쉽게 기억하기**

### 2. `demo/auto_label/candidate_labels/*.txt`

#### 이 산출물은 무엇인가요?

`candidate_labels` 폴더에는 **Final Model이 이미지에서 예측한 BBox와 Class를 YOLO TXT 형식으로 자동 저장한 후보 라벨**을 넣습니다.

여기서 중요한 것은 이 TXT가 **최종 정답 라벨이 아니라 AI가 만든 후보 라벨**이라는 점입니다.

```text
Final Model Prediction
        ↓
BBox + Class 예측
        ↓
YOLO 형식으로 저장
        ↓
candidate_labels/*.txt
```

교과 7에서 사용한 YOLO TXT 형식과 동일합니다.

```text
class_id x_center y_center width height
```

예:

```text
1 0.512300 0.421700 0.083100 0.062500
6 0.721400 0.338900 0.041200 0.055800
```

각 줄은 객체 하나를 의미합니다.

#### 실제 파일 구조 예시

```text
demo/
└── auto_label/
    ├── images/
    │   ├── new_001.jpg
    │   └── new_002.jpg
    │
    └── candidate_labels/
        ├── new_001.txt
        └── new_002.txt
```

이미지와 TXT는 같은 기본 파일명을 사용합니다.

```text
new_001.jpg
new_001.txt

new_002.jpg
new_002.txt
```

---

#### 왜 후보 라벨이라고 하나요?

AI Prediction은 틀릴 수 있기 때문입니다.

예를 들어:

```text
실제 plastic
→ AI가 leaf로 예측

실제 객체 있음
→ AI가 놓침

실제 객체 없음
→ AI가 잘못 BBox 생성
```

할 수 있습니다.

따라서 `candidate_labels`의 TXT는 바로 최종 정답으로 사용하지 않습니다.

> **쉽게 기억하기**  
> `candidate_labels/*.txt` = AI가 먼저 작성한 **초안 라벨**

#### 확인할 것

- [ ] Final Model Prediction으로 생성한 TXT다.
- [ ] YOLO TXT 형식을 사용한다.
- [ ] 이미지와 TXT 기본 파일명이 같다.
- [ ] Class ID가 교과 7~8의 Class 체계와 같다.
- [ ] Candidate Label을 최종 정답으로 바로 사용하지 않는다.
- [ ] 사람이 다시 검수할 준비가 되어 있다.

### 3. `demo/auto_label/reviewed_labels/*.txt`

#### 이 산출물은 무엇인가요?

`reviewed_labels` 폴더에는 **AI가 만든 후보 라벨을 사람이 실제로 확인한 뒤 수정·삭제·추가·승인한 결과**를 저장합니다.

이 단계에서 교과 7의 라벨링 프로그램을 다시 사용합니다.

```text
candidate_labels/*.txt
        ↓
교과 7 라벨링 프로그램에서 Load
        ↓
사람이 이미지와 BBox 확인
        ↓
정확하면 승인
틀리면 수정
불필요하면 삭제
누락이면 추가
        ↓
reviewed_labels/*.txt
```

즉 교과 7과 교과 8이 실제로 연결되는 지점입니다.

```text
교과 7
→ 사람이 직접 라벨 검수

교과 8
→ AI가 후보 라벨 생성

        ↓

교과 7 라벨링 도구로 다시 Human Review
```

#### Human Review에서는 무엇을 확인하나요?

다음 네 가지를 확인합니다.

```text
1. Class가 맞는가?

2. BBox 위치가 맞는가?

3. 잘못 생성된 BBox가 있는가?

4. 놓친 객체가 있는가?
```

예:

```text
AI 후보
→ plastic Class 1
→ BBox 위치 정상

판단
→ 그대로 승인
```

다른 예:

```text
AI 후보
→ leaf Class 0

실제
→ branch Class 2

판단
→ Class 0 → Class 2 수정
```

또는:

```text
AI가 아무것도 검출하지 않음

실제
→ 작은 plastic 있음

판단
→ 새 BBox 추가
```

- [ ] BBox를 확인했다.

### 4. `reports/auto_label_review.csv`

#### 이 파일은 무엇인가요?

`auto_label_review.csv`는 **AI가 만든 후보 라벨을 사람이 검수하면서 몇 개를 그대로 승인했고, 몇 개를 수정·삭제·추가했는지 기록하는 요약표**입니다.

Candidate Label과 Reviewed Label 파일만 있어도 결과는 남지만, 이 CSV가 있으면 AI 자동 라벨링이 실제로 얼마나 도움이 되었는지 한눈에 볼 수 있습니다.

```text
AI 후보 생성
        ↓
Human Review
        ↓
그대로 승인 몇 개?
Class 수정 몇 개?
BBox 수정 몇 개?
삭제 몇 개?
누락 추가 몇 개?
REVIEW 몇 개?
        ↓
auto_label_review.csv
```

---

#### 실제 작성 예시 — 이미지별 기록

```csv
image,candidate_bbox_count,approved,class_modified,bbox_modified,deleted,added,review_status
new_001.jpg,3,2,1,0,0,0,PASS
new_002.jpg,2,1,0,1,0,1,PASS
new_003.jpg,4,2,0,0,2,0,REVIEW
```

#### 각 항목은 무엇을 의미하나요?

| 항목 | 의미 |
|---|---|
| `image` | 검수한 이미지 파일 |
| `candidate_bbox_count` | AI가 처음 만든 BBox 수 |
| `approved` | 수정 없이 그대로 승인한 BBox 수 |
| `class_modified` | Class를 수정한 수 |
| `bbox_modified` | BBox 위치·크기를 수정한 수 |
| `deleted` | 잘못된 BBox를 삭제한 수 |
| `added` | AI가 놓쳐 사람이 새로 추가한 BBox 수 |
| `review_status` | `PASS` 또는 추가 확인이 필요한 `REVIEW` |

---

#### 전체 통계를 함께 보고 싶다면

별도의 마지막 행 또는 요약 문서에서 다음처럼 정리할 수 있습니다.

```text
전체 대상 이미지 수: [실제 수]

AI 후보 BBox 수: [실제 수]

그대로 승인: [실제 수]

Class 수정: [실제 수]

BBox 수정: [실제 수]

삭제: [실제 수]

누락 추가: [실제 수]

REVIEW: [실제 수]
```

이 통계가 중요한 이유는:

```text
AI가 얼마나 잘 초안을 만들었는가?
        ↓
사람이 얼마나 수정해야 했는가?
        ↓
Auto Label이 실제 작업을 얼마나 보조했는가?
```

# 최종 제출 구조로 한 번에 확인하기

아래 구조는 **지금까지 1~8번에서 확정한 산출물의 실제 경로를 기준으로 정리한 최종 프로젝트 구조 예시**입니다.

중요한 점은 이 구조를 마지막 제출 때 새로 만드는 것이 아니라는 것입니다.

```text
수업 중 VSCode에서 실제로 작업한 프로젝트 폴더
        ↓
같은 폴더 구조에서 파일을 계속 생성·저장
        ↓
Git으로 Commit
        ↓
허용된 Git 저장소에 Push
        ↓
최종 제출 구조와 같은 상대경로 유지
```

즉 VSCode에서는

```text
reports/failure_analysis.csv
```

로 작업했는데, 마지막 제출할 때 임의로

```text

```

처럼 위치나 이름을 바꾸면 안 됩니다.

**VSCode에서 작업하는 프로젝트 Root와 Git 저장소 Root를 같은 기준으로 사용하고, 교재에 제시된 상대경로를 가능한 한 그대로 유지합니다.**

단, 기관 보안정책이나 실제 수업 프로젝트에서 이미 정한 폴더명이 있다면 **기존 VSCode·Git 저장소 구조를 우선**합니다.  
이 문서의 구조에 맞추기 위해 정상적으로 사용 중인 프로젝트 폴더를 마지막에 억지로 다시 재배치할 필요는 없습니다.

## VSCode 폴더와 Git 저장소는 어떻게 맞추나요?

별도의 “제출용 폴더”를 마지막에 새로 만드는 방식보다, 처음부터 하나의 프로젝트 Root에서 작업하는 것이 가장 이해하기 쉽습니다.

예:

```text
VSCode에서 연 프로젝트

subject8_kimchi_detection/
        ↓
여기서 코드 작성
여기서 reports/ 생성
여기서 models/ 생성
여기서 demo/ 생성
        ↓
같은 Root에서 Git 관리
        ↓
허용된 Git 저장소에 Push
```

따라서 다음 세 위치에서 **상대경로가 같아야 합니다.**

```text
VSCode에서 보는 경로
        =
로컬 Git 프로젝트 경로
        =
Git 저장소에서 보는 경로
```

예를 들어 VSCode에서:

```text
subject8_kimchi_detection/
└── reports/
    └── failure_analysis.csv
```

라면 Git 저장소에서도 추적이 허용된 파일은:

```text
reports/failure_analysis.csv
```

위치에 있어야 합니다.

이렇게 해야 README나 다른 문서에 작성한:

```text
reports/failure_analysis.csv
models/final/final_best.pt
docs/handoff_subject14.md
```

같은 경로가 실제 프로젝트와 일치합니다.

---

## 단, “VSCode에 존재하는 파일”과 “Git에 올리는 파일”은 같지 않을 수 있습니다

프로젝트 폴더 구조는 같게 유지하되, NDA 또는 대용량 파일은 `.gitignore`로 Git 추적에서 제외할 수 있습니다.

예:

```text
VSCode 로컬 프로젝트에는 존재
        ↓
data/
models/*.pt
실제 원본 JPG / YOLO TXT
민감한 Prediction 이미지
        ↓
.gitignore 또는 기관 보안정책에 따라
Git에는 업로드하지 않을 수 있음
```

즉:

```text
폴더 구조·상대경로
→ 프로젝트 전체에서 일관되게 유지

Git 업로드 여부
→ 파일의 보안등급·용량·기관정책에 따라 결정
```

## 실제 데이터 폴더는 별도로 이해합니다

산출물 1의 실제 학습 과정에서는 다음 데이터 구조가 필요합니다.

```text
data/
├── subject7_final/
│   └── 교과 7에서 인계받은 FINAL 데이터
│
├── yolo/
│   ├── images/
│   │   ├── train/
│   │   ├── val/
│   │   └── test/
│   └── labels/
│       ├── train/
│       ├── val/
│       └── test/
│
└── bridge_holdout/
    ├── images/
    └── labels/
```

하지만 이 폴더의 실제 JPG / TXT를 **외부 공개 Git 저장소에 올린다는 뜻은 아닙니다.**

`configs/dataset.yaml`, `manifests/*.csv`, README 등의 경로가 이 실제 데이터 구조와 맞도록 작성되어 있어야 합니다.
