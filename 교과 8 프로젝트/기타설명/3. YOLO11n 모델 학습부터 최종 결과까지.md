코드를 짜기 전에 먼저 
“어떤 데이터로 무엇을 학습시키고, 
어떤 Validation 결과를 기준으로 성공·실패를 판단할 것인가?”를 정합니다.

그다음 그 기준에 맞춰 입력 데이터 → 학습 조건 → 평가 지표 → 실패 시 수정할 항목 순서로 
코드를 설계합니다.

![[Pasted image 20261007080450.png]]

### ⚠️ 주의 : “Frozen Test를 보고 튜닝하지 말라”**는 뜻

```
Final Model 확정
final_best.pt
        ↓
Frozen Test 실행
        ↓
결과가 생각보다 낮음
        ↓
"점수를 올려야겠다"
        ↓
imgsz 변경
epochs 변경
batch 변경
augmentation 변경
모델 구조 변경
학습 데이터 수정
confidence 기준 변경
        ↓
다시 학습
        ↓
같은 Test로 다시 평가
        ↓
조금 더 좋게 나옴
```

이 과정을 하지 말라는 뜻입니다.

현업 관점에서 한 가지를 더 강조하고 싶습니다. 
Frozen Test를 한 번 보고 난 뒤 그 결과를 근거로 모델을 다시 수정하기 시작하면, 
그 Test는 다음 버전에서는 더 이상 진짜 ‘처음 보는 Test’가 아닙니다. 
프로젝트를 계속 개선한다면 새로운 독립 Test를 준비해야 합니다. 

왜냐하면 Test 결과를 보고 모델을 고치기 시작하면 
Test 데이터는 더 이상 “처음 보는 시험 문제”가 아니기 때문입니다.

그렇다면 올바른 흐름은 이렇습니다.

```
Train
→ 모델 학습

Validation
→ 성능 확인
→ 실패 분석
→ imgsz / epoch / 데이터 / augmentation 등 조정
→ 재학습
→ 다시 Validation
→ 필요하면 반복
→ Final Model 확정
        ↓
여기서 개발 종료
        ↓
Frozen Test
        ↓
최종 성능 그대로 기록
```

## 성능이 안 나왔을 때 어디로 돌아가야 하는가

Validation 성능이 낮다고 무조건 다시 학습을 하는건 아닙니다. 먼저 이렇게 판단해야 합니다.

![[Pasted image 20261007085305.png]]

- Prediction은 학습된 YOLO 모델이 이미지를 보고 스스로 예측한 결과로, 
  **예측한 Class와 BBox 위치**를 뜻합니다.  (모델이 이미지를 보고 자기가 찾은답)

- GT(Ground Truth)는 사람이 미리 라벨링해 둔 **정답 Class와 정답 BBox**이며, 
  Prediction과 비교해 모델이 맞았는지 틀렸는지 판단합니다. (이물은 여기에 있다라고 정답 Class와 BBox를 표시해 둔 것, 즉 정답지 )

## 특히 Label 문제가 발견되었을 때

이것은 일반적인 모델 튜닝과 조금 다르게 봐야 합니다.
