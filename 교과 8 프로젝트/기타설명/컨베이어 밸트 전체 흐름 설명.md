- **먼저 왼쪽의 교과 7 결과부터 보겠습니다.** 교과 7에서는 조각김치 4K 이미지 900장과 그 이미지에 대응하는 YOLO TXT 라벨을 사람이 검수했습니다. YOLO TXT에는 이물질의 종류인 Class와 이물질이 있는 위치를 나타내는 BBox 좌표가 들어 있습니다.
    
- 이미지와 TXT만 있는 것이 아닙니다. **어떤 Class를 어떤 번호로 사용할지, BBox를 어느 범위까지 그릴지에 대한 기준도 함께 확정했습니다.** 따라서 교과 8에서는 이 기준을 마음대로 바꾸지 않고 그대로 사용합니다.
    
- `Dataset Manifest`에는 각 이미지가 어느 Dataset에서 왔는지, 원래 train인지 validation인지, 어떤 장면 유형인지 같은 정보를 기록합니다. `source_dataset`, `original_split`, `scene_type`은 별도의 폴더가 아니라 **Manifest 안에 기록하는 데이터 정보**입니다. `QA Summary`는 교과 7에서 전체 데이터를 검수하면서 발견하고 수정한 오류를 정리한 기록입니다.
    
- **교과 7에서는 900장을 모두 검수하지만, 원본 폴더를 하나로 합치지는 않습니다.** Dataset 1과 Dataset 2, 기존 train과 validation 구조는 그대로 보존합니다. 그리고 교과 8에서 실제 모델 개발에 사용할 데이터와 이후 교과 14 연결을 위해 보존할 데이터를 구분할 수 있습니다.
    
- 이제 가운데의 **교과 8**로 넘어갑니다. 교과 8의 목적은 교과 7에서 만든 정답 데이터를 이용해서 **AI가 새로운 김치 이미지에서 이물질의 위치와 종류를 스스로 찾게 만드는 것**입니다.
    
- 첫 번째로 교과 7의 결과를 확인합니다. 같은 팀이 이어서 하는 프로젝트이기 때문에 900장을 처음부터 다시 라벨링하는 것은 아닙니다. 다만 이미지 수와 TXT 수가 맞는지, Class가 어떻게 분포되어 있는지, 정상 김치와 이물 이미지가 어느 정도 있는지처럼 **학습하기에 적절한 데이터인지 다시 확인**합니다. 이것이 `Dataset Audit`입니다.
    
- 그다음 **Dataset Split 정책을 정합니다.** 어떤 데이터로 학습할지 Train을 정하고, 학습 중 모델을 비교할 Validation을 정하고, 마지막까지 보지 않을 Frozen Test를 따로 둡니다. 중요한 것은 단순히 70:15:15 숫자를 맞추는 것이 아니라 **서로 매우 비슷한 사진이 Train과 Test에 동시에 들어가지 않도록 Data Leakage를 막는 것**입니다.
    
- 그리고 필요하다면 일부 데이터는 **교과 14 연결용 Bridge Holdout**으로 따로 보존합니다. 이 데이터는 교과 8의 학습이나 튜닝에는 사용하지 않고, 나중에 교과 14로 넘어갈 때 교과 8 Final Model이 낯선 데이터에서도 동작하는지 확인하는 용도로 사용할 수 있습니다.
    
- Split이 확정되면 YOLO가 이해할 수 있도록 `images/train`, `images/val`, `images/test`와 `labels` 폴더를 구성하고 `dataset.yaml`을 만듭니다. `dataset.yaml`에는 **데이터가 어디에 있고 어떤 Class를 사용하는지**를 적습니다.
    
- 처음부터 전체 데이터를 오래 학습하지 않습니다. 먼저 Train 30~40장, Validation 5~10장 정도의 작은 데이터로 **Smoke Test**를 합니다. 여기서는 성능을 높이는 것이 목적이 아니라, 데이터 읽기부터 학습, Weight 생성, Prediction까지 **전체 과정이 한 번 끝까지 정상적으로 연결되는지 확인**합니다. 작은 End-to-End 테스트라고 이해하면 됩니다.
    
- Smoke Test가 성공하면 전체 Train 데이터로 **Baseline Model**을 학습합니다. Baseline은 앞으로 개선된 모델과 비교하기 위한 첫 번째 기준 모델입니다. 따라서 Baseline은 나중에 지우지 않고 계속 보관합니다.
    
- Baseline 학습이 끝나면 Validation 데이터로 성능을 평가합니다. 여기에서 `Precision`, `Recall`, `mAP` 같은 값을 봅니다. 하지만 숫자가 높다고 무조건 좋은 모델이라고 판단하지 않고 **실제 이미지에서 무엇을 맞히고 무엇을 놓치는지도 함께 봅니다.**
    
- 다음은 **Failure Analysis**, 즉 실패 분석입니다. 프로그램이 FP와 FN이 많이 발생한 이미지들을 먼저 찾아주고, 사람은 그중 대표적인 사례를 직접 확인합니다. 실제 이물이 있는데 놓친 것은 FN이고, 이물이 없는데 있다고 검출한 것은 FP입니다. Class를 잘못 예측했는지, BBox가 이물질을 제대로 감싸지 못했는지도 확인합니다.
    
- 실패 원인을 찾은 뒤에는 한꺼번에 여러 조건을 바꾸지 않습니다. 예를 들어 작은 이물을 자주 놓친다면 이미지 입력 크기 `640 → 960`처럼 **한 가지 주요 변수만 바꾸어 다시 학습**합니다. 그래야 성능이 좋아졌을 때 무엇 때문에 좋아졌는지 설명할 수 있습니다.
    
- 개선 모델이 만들어지면 **Baseline과 Improved Model을 같은 Validation 데이터에서 비교**합니다. Precision·Recall·mAP뿐 아니라 실제 실패 이미지도 함께 비교해서 정말 개선되었는지 판단합니다. 교과 8에서는 모든 실패 원인을 여러 번 반복해서 없애는 것이 필수는 아니고, **대표적인 실패 원인 하나를 선정해서 통제된 개선 실험을 제대로 수행하는 것**이 핵심입니다.
    
- 그 결과를 바탕으로 가장 적절한 모델을 **Final Model**로 확정합니다. Final Model을 정한 다음에야 지금까지 학습과 개선에 사용하지 않았던 Frozen Test를 처음 열어 최종 성능을 측정합니다. Test 결과가 마음에 들지 않는다고 다시 Test를 보면서 튜닝하면 공정한 최종평가가 아니므로 Frozen Test는 마지막 한 번의 평가용이라고 생각하면 됩니다.
    
- Final Model이 만들어지면 새로운 이미지에 모델을 실행해서 실제 Detection 결과를 확인합니다. 별도의 복잡한 GUI를 만드는 것이 아니라 모델이 만든 **BBox, Class, Confidence가 표시된 결과 이미지**를 저장하고 사람이 직접 확인합니다.
    
- 그다음이 **Auto Label**입니다. 라벨이 없는 새로운 이미지를 Final Model에 넣으면 AI가 먼저 “이 위치에 플라스틱이 있는 것 같습니다”처럼 BBox와 Class 후보를 만들어 줍니다. 이 후보를 YOLO TXT로 저장할 수 있지만, 아직 정답은 아닙니다.
    
- 그래서 Auto Label 결과를 다시 교과 7에서 만든 라벨링 도구로 불러옵니다. 사람이 AI가 만든 BBox와 Class를 보고 틀린 것은 수정하고, 잘못 찾은 것은 삭제하고, 놓친 것은 추가합니다. 즉 **AI가 먼저 라벨 후보를 만들고 사람이 최종 확인하는 방식**입니다.
    
- 마지막으로 Dataset Version, Baseline, Improved Model, Final Model, 성능 결과, 실패 사례, Auto Label 결과, README 등을 문서화합니다. 다른 사람이 README를 보고 모델을 다시 실행할 수 있어야 교과 8 프로젝트가 제대로 끝난 것입니다.
    
- 이제 오른쪽의 **교과 14**로 연결됩니다. 교과 8에서 만든 Final Model과 학습 경험을 그대로 가져가지만, 교과 14에서는 실제 컨베이어, 조명, Daheng 카메라, Jetson 환경을 사용하기 때문에 실제 장비에서 추가로 촬영한 데이터로 성능을 확인하고 필요하면 다시 Fine-tuning합니다.
    
- 교과 9에서 배우는 OpenCV 규칙검사도 교과 14에서 필요하면 함께 사용할 수 있습니다. 이것은 교과 8 Weight와 교과 9 Weight를 합쳐 하나의 모델을 만든다는 뜻이 아닙니다. **AI 객체검출과 사람이 정한 OpenCV 검사 규칙을 하나의 제조검사 Pipeline 안에서 적절히 함께 사용하는 것**입니다.
    
- 교과 14에서는 모델을 ONNX나 TensorRT 등으로 최적화하고 Jetson에 배포합니다. 카메라가 촬영한 이미지가 Jetson으로 들어오면 모델이 이물질을 추론하고, 그 결과를 바탕으로 OK 또는 NG를 판정합니다.
    
- 실제 장비가 현재처럼 제품 위치를 맞춘 뒤 Trigger로 사진 한 장을 촬영하는 구조라면 그것도 충분히 실시간 제조검사입니다. **제품 위치 맞춤 → 촬영 → Jetson 추론 → OK/NG 판정 → 결과 표시**가 짧은 시간 안에 이루어지면 됩니다.
    
- FastAPI를 사용한다면 Jetson에서 나온 검사 결과를 HTTP로 전달해서 브라우저 Dashboard에 최근 촬영 이미지, BBox, Class, Confidence, OK/NG, 누적 통계 등을 보여줄 수 있습니다. 다만 FastAPI 자체가 교과 14의 필수 기술이라기보다, **검사 결과를 웹에서 보기 좋게 보여주기 위한 구현 방법 중 하나**라고 이해하면 됩니다.
    
- 그래서 이 그림 전체를 한 문장으로 정리하면 **교과 7에서는 사람이 믿을 수 있는 정답 데이터를 만들고, 교과 8에서는 그 정답으로 AI 객체검출 모델을 학습·평가·개선하며, 교과 14에서는 그 경험과 모델을 실제 컨베이어·카메라·Jetson 환경에 연결하여 제조검사 시스템으로 완성하는 과정**입니다.
