## 1.3 이미지에는 서로 다른 장면 유형이 섞여 있습니다

실제 폴더를 확인하면 모든 이미지가 똑같은 형태는 아닙니다.

![[Pasted image 20260928132227.png|149]]![[Pasted image 20260928132243.png|153]]![[Pasted image 20260928132301.png|154]]![[Pasted image 20260928132322.png|123]]![[Pasted image 20260928132341.png|149]]![[Pasted image 20260928132354.png|140]]

## 이미지 유형에 따라 무엇을 확인해야 하나요?

제공된 900장의 이미지를 살펴보면 크게 다음 세 가지 형태가 있습니다.

```text
A. 김치 + 검출 대상 객체
   → 김치 사이에 이물질 또는 학습 대상 객체가 보이는 이미지

B. 정상 김치
   → 검출 대상 객체가 보이지 않는 이미지

C. 검출 대상 객체 단독 이미지
   → 김치가 거의 없고 대상 객체가 단순한 배경 위에 보이는 이미지
```

세 유형 모두 제공 데이터의 일부이므로 임의로 삭제하지 않습니다.

### A. 김치와 검출 대상 객체가 함께 있는 이미지

이 경우에는 **이미지에 보이는 검출 대상 객체의 BBox와 Class가 맞는지 확인**합니다.

예를 들어 이미지에 나뭇가지와 플라스틱 조각이 있다면,

```
나뭇가지
→ 해당 Class의 BBox 확인

플라스틱 조각
→ 해당 Class의 BBox 확인
```

처럼 처리합니다.

김치는 원래 검출 대상 Class가 아니므로 별도의 BBox를 만들지 않습니다.

즉, 이번 프로젝트에서는 **제공된 Class 기준에 해당하는 객체만 라벨링하고 검수합니다.**

작업자가 JPG와 TXT를 탐색기에서 매번 따로 찾아 열 필요는 없습니다.

라벨링 프로그램이 다음과 같이 처리하도록 만듭니다.

```
이미지 열기
        ↓
같은 이름의 TXT 자동 찾기
        ↓
기존 BBox와 Class를 이미지 위에 표시
        ↓
작업자가 실제 이미지와 비교하여 확인
```

기존 라벨이 맞으면 `PASS`, 틀리면 수정하고, 빠진 객체가 있으면 BBox를 추가합니다.

---

### B. 정상 김치 이미지

정상 김치 이미지에는 **검출 대상 객체가 없을 수 있습니다.**

이 경우에는 BBox가 하나도 없는 것이 정상일 수 있습니다.

```
이미지 확인
        ↓
검출 대상 객체가 없음
        ↓
BBox 없음
        ↓
정상 데이터
```

이때 TXT가 비어 있다면 바로 오류라고 판단하지 않습니다.

라벨링 프로그램에서 이미지와 TXT를 함께 불러온 뒤 사람이 확인합니다.

```
빈 TXT
        ↓
이미지 확인
        ↓

정말 이물이 없음
→ PASS

이물이 있는데 BBox가 없음
→ 누락된 BBox 추가
→ EDITED
```

따라서 900개의 TXT를 메모장으로 하나씩 열어 확인하는 작업이 아닙니다.

**프로그램이 TXT를 읽고 화면에 BBox를 표시하며, 작업자는 이미지와 표시 결과를 비교하여 검수합니다.**

---

### C. 검출 대상 객체만 보이는 이미지

일부 이미지에는 김치가 없고 이물질이나 학습 대상 객체만 단순한 배경 위에 보입니다.

이 이미지도 그대로 검수합니다.

예를 들어 이미지에 나뭇가지 하나만 있다면,

```
이미지
→ 나뭇가지 확인

기존 TXT
→ 나뭇가지 BBox와 Class 확인

정확함
→ PASS

BBox 위치 또는 Class가 틀림
→ 수정

BBox가 없음
→ 새 BBox 추가
```

즉 **김치가 없다고 해서 라벨링하지 않는 것이 아닙니다.**

이미지 안에 이번 프로젝트의 검출 대상 Class가 있으면 그 객체의 BBox와 Class를 확인합니다.

다만 이런 이미지는 실제 김치 위에서 촬영한 이미지와 배경이 다르므로, 교과 7에서는 삭제하거나 임의로 분리하지 않고 출처를 기록하여 그대로 보존합니다.

교과 8에서 객체검출 모델을 학습할 때

```
김치 + 대상 객체 이미지
정상 김치 이미지
대상 객체 단독 이미지
```

가 각각 얼마나 포함되어 있는지 다시 확인하여 학습데이터 구성을 결정합니다.

> 정리하면: 
> 
> 학생이 900개의 TXT 숫자를 직접 편집하는 것이 아니라, 
> 라벨링 프로그램이 JPG와 TXT를 함께 불러와 기존 BBox를 보여주고, 
> 
> 학생은 화면을 보면서 
> 	- 맞으면 PASS, 
> 	- 틀리면 수정, 
> 	- 빠졌으면 추가
> 하는 방식으로 작업합니다.

## 1.4 Class와 이미지 유형을 구분합니다

이번 프로젝트에서 **Class**란  
이미지 안에서 BBox로 표시하고 학습할 **객체의 종류**를 뜻합니다.

예를 들어 이번 프로젝트의 Class는 다음과 같습니다.

```text
Class 0 = 나뭇잎·종이류
Class 1 = 플라스틱류·돌·금속 등
Class 2 = 나뭇가지류
Class 3 = 벌레류
Class 4 = 고무장갑
Class 5 = 병해·갈변
Class 6 = 파·고추
```

즉,

```
이미지 안에서 무엇을 찾아야 하는가?
        ↓
그 객체의 종류가 Class
```

입니다.

### 그런데 이미지 자체도 형태가 여러 가지입니다

제공된 이미지에는 다음과 같은 형태가 섞여 있을 수 있습니다.

```
A. 김치 + 검출 대상 객체

B. 정상 김치

C. 검출 대상 객체만 단독으로 있는 이미지
```

이 세 가지는 **Class가 아닙니다.**

왜냐하면 이 말들은  
이미지 안의 객체 종류를 나타내는 것이 아니라  
**이미지 전체가 어떤 형태인지 설명하는 말**이기 때문입니다.

예를 들어,

```
김치 + 벌레가 있는 이미지
```

라면

```
이미지 유형
→ 김치 + 검출 대상 객체

BBox로 표시할 Class
→ 벌레류(Class 3)
```

입니다.

또,

```
정상 김치 이미지
```

라면

```
이미지 유형
→ 정상 김치

BBox로 표시할 Class
→ 없음
```

입니다.

또,

```
단순한 배경에 나뭇가지 하나만 있는 이미지
```

라면

```
이미지 유형
→ 검출 대상 객체 단독 이미지

BBox로 표시할 Class
→ 나뭇가지류(Class 2)
```

입니다.

---

### 따라서 Class는 새로 만들지 않습니다

다음처럼 만들지 않습니다.

```
잘못된 예

Class 7 = 정상 김치
Class 8 = 이물질 단독 이미지
```

이번 프로젝트에서 사용하는 Class는  
**회사에서 제공한 Class ID 0~6 기준만 사용합니다.**

---

### 이미지 유형은 별도로 기록할 수 있습니다

이미지 유형은 라벨 Class와는 별도로  
Manifest에서 데이터 분석용 정보로 기록할 수 있습니다.

예:

```
scene_type

kimchi_with_target
→ 김치 + 검출 대상 객체

normal_kimchi
→ 정상 김치

object_only
→ 검출 대상 객체 단독 이미지

other_review
→ 바로 구분하기 어려운 이미지
```

이 정보는 교과 8에서

```
정상 김치가 몇 장인지

김치 + 이물 이미지가 몇 장인지

이물만 단독으로 찍힌 이미지가 몇 장인지
```

확인할 때 사용할 수 있습니다.

> **정리**
> 
> `Class` = BBox로 표시할 객체의 종류  
> `이미지 유형` = 이미지 전체가 어떤 형태인지 설명하는 정보

## 1.5 데이터의 성격

본 데이터는 실제 산업현장에서 사용되는 데이터의 분포 구조를 교육 목적으로 재현한 **100% 가상 생성 데이터**입니다.

따라서 프로젝트 발표나 포트폴리오에서 실제 생산라인에서 취득한 원본 데이터라고 표현하지 않습니다.

포트폴리오에는 다음 의미가 드러나도록 작성합니다.

> **본 프로젝트는 AI캠퍼스 교육을 위해 실제 산업데이터와 유사한 분포 구조로 100% 가상 생성된 조각김치 이물검출 학습데이터를 활용하여 수행하였습니다.**

## 1.6 NDA와 외부 유출 금지

이 데이터는 교육생의 NDA(비밀유지계약) 서명을 전제로 사용합니다.

허용 목적은 다음과 같습니다.

- AI 학습
- AI 테스트
- 교육 프로젝트 수행
- 허용된 범위의 포트폴리오 제작

다음 행동은 하지 않습니다.

- 원본 JPG 또는 TXT를 공개 저장소에 업로드
- 데이터 압축파일을 외부인에게 전달
- 공개 파일공유 서비스에 원본 데이터를 업로드
- 공개 Git 저장소에 원본 데이터 폴더 포함
- 개인 클라우드에 임의 백업
- 메신저·커뮤니티에 원본 데이터를 배포

소스코드를 버전관리할 때도 **데이터와 소스코드를 분리**합니다.

> **시작 전 확인**
>
> 데이터가 무엇인지, 기존 TXT가 무엇인지, 왜 원본 폴더와 split 정보를 보존해야 하는지, RAW를 왜 직접 수정하면 안 되는지를 팀원 모두가 설명할 수 있어야 합니다.

## 2.2 어디까지 만들면 프로젝트가 끝난 것인가요?

다음 상태가 되어야 프로젝트가 완료된 것으로 봅니다.

| 영역 | 완료 기준 |
|---|---|
| 프로그램 | 기존 YOLO TXT를 읽고 BBox·Class를 표시·추가·삭제·변경할 수 있음 |
| 탐색 | 이전/다음 이미지 이동과 4K 이미지 Zoom/Pan이 안정적으로 동작함 |
| 좌표 | 저장 후 다시 불러와도 BBox가 같은 위치에 나타남 |
| 저장 | RAW는 보존하고 WORK에 YOLO TXT를 안전하게 저장함 |
| 진행관리 | 900장의 작업자·검수자·상태를 확인할 수 있음 |
| 자동 QA | Pair, TXT 형식, Class, 좌표 등의 오류를 찾을 수 있음 |
| Human QA | 수정·신규·REVIEW 데이터가 다른 사람에게 검수됨 |
| 최종 데이터 | Critical Error와 미처리 REVIEW 없이 FINAL이 확정됨 |
| 문서 | Class/BBox 기준, QA 결과, README, 테스트 결과가 정리됨 |
| 인계 | 교과 8에서 FINAL 데이터를 바로 사용할 수 있음 |

다음 상태는 완료가 아닙니다.

```text
GUI 창이 실행됨
또는
BBox 하나가 그려짐
또는
900장을 한 번씩 열어봄
```

> **완료 = 프로그램 + 검수된 데이터 + QA 기록 + 문서 + 교과 8 인계**

### 2~5일차

그날의 수행가이드만 먼저 읽습니다.

```text
BBox가 화면에서 어긋남
→ 좌표 기준 찾아보기

기존 TXT가 이상함

```

## 2.5 코딩은 어떤 생각으로 시작하나요?

이번 프로젝트에서는 완성 코드를 한 번에 작성하지 않습니다.

라벨링 프로그램은 다음 패턴으로 만듭니다.

```text
작은 기능 하나 정하기
        ↓
그 기능의 입력과 결과 생각하기
        ↓
구현하기
        ↓
직접 실행하기
        ↓
정상인지 확인하기
        ↓
오류가 있으면 그 기능만 수정하기
        ↓
통과하면 다음 기능 연결
```

### 기능 하나를 만들기 전에 네 가지를 먼저 적어봅니다

| 질문 | 예 |
|---|---|
| 입력은 무엇인가? | JPG 경로, TXT 경로, 마우스 좌표 |
| 무엇을 해야 하는가? | 이미지 읽기, BBox 생성, Class 연결 |
| 결과는 무엇인가? | 화면 이미지, BBox 목록, TXT |
| 실패했는지 어떻게 알 수 있는가? | 파일 없음, 좌표 불일치, 저장 실패 |

이것이 여러분의 **코딩 설계 패턴**입니다.

### 라벨링 프로그램을 만드는 권장 순서

```text
1. JPG 한 장 읽기
        ↓
2. 화면에 이미지 표시
        ↓
3. 같은 이름의 TXT 찾기
        ↓
4. TXT 읽기
        ↓
5. 기존 BBox를 화면에 표시
        ↓
6. 새 BBox 한 개 작성
        ↓
7. BBox에 Class 연결
        ↓
8. WORK에 YOLO TXT 저장
        ↓
9. 프로그램 종료 후 다시 Load
        ↓
10. 같은 위치에 BBox가 복원되는지 확인
```

여기까지가 **가장 작은 End-to-End**입니다.

이것이 성공한 뒤에만 다음 기능을 붙입니다.

```text
이전 / 다음
        ↓
다중 BBox
        ↓
삭제 / Class 변경
        ↓
Zoom / Pan
        ↓
저장 유실 방지
        ↓
작업상태 관리
        ↓
Validation
```

> **코딩 핵심**
>
> `작은 기능 → 실행 → 확인 → 다음 기능`
>
> 이 순서를 반복합니다.

## 3.2 실제 제공 데이터를 확인합니다

## 3.3 YOLO TXT가 무엇인지 실제 샘플로 확인합니다

TXT 한 줄은 객체 하나를 의미합니다.

```text
class_id x_center y_center width height
```

예:

```text
6 0.8006198347 0.6231481481 0.0340909091 0.0537037037
```

좌표는 Pixel이 아니라 이미지 크기에 대한 **0~1 정규화 비율값**입니다.

학생이 TXT 숫자를 메모장에서 직접 고치는 방식으로 작업하지 않습니다.

```text
JPG + 기존 TXT
        ↓
프로그램에서 함께 Load
        ↓
BBox / Class 화면 표시
        ↓
이미지와 비교
        ↓
맞음 → 그대로 유지
틀림 → 수정
누락 → 추가
불필요 → 삭제
애매함 → REVIEW
```

## 3.4 Class 기준서를 작성합니다 — 5번 산출물

팀원마다 같은 객체를 다른 Class로 판단하지 않도록 기준을 먼저 맞춥니다.

사용 Class:

```text
0 = 나뭇잎·종이류
1 = 플라스틱류·돌·금속류
2 = 나뭇가지류
3 = 벌레류
4 = 고무장갑 — 현재 사용하지 않음
5 = 병해·갈변
6 = 파·고추
```

Class 번호를 보기 좋게 다시 매기지 않습니다.

Class 4가 기존 TXT에서 발견되면 자동 삭제하지 않고 `REVIEW`로 보냅니다.

오늘 다음 파일을 작성합니다.

```text
docs/class_guide.md
```

문서에는 각 Class의 다음 기준을 정리합니다.

```text
대상
포함
제외
애매한 경우 처리
```

## 3.5 BBox 기준서를 작성합니다 — 6번 산출물

BBox는 작업자마다 크기가 달라지지 않도록 같은 기준을 사용합니다.

공통 원칙:

- 객체 전체를 포함합니다.
- 가능한 한 객체 외곽에 밀착합니다.
- 불필요한 배경은 최소화합니다.
- 서로 다른 객체는 각각 BBox를 만듭니다.
- 겹쳐 있어도 구분 가능하면 각각 작성합니다.
- 작아도 Class를 판단할 수 있으면 누락하지 않습니다.
- 경계가 애매하면 임의로 정하지 않고 REVIEW 처리합니다.

오늘 다음 파일을 작성합니다.

```text
docs/bbox_guide.md
```

## 4.7 검수 상태를 기록할 수 있게 합니다

초보자가 가장 헷갈리기 쉬운 부분이 **작업 상태와 QA 상태**입니다. 두 값을 구분합니다.

산출물 예시처럼 화면에서는 다음 의미를 보여줄 수 있습니다.

```text
PASS
→ 현재 작업자가 기존 라벨이 맞다고 판단하여 수정 없이 확인 완료

EDITED
→ BBox 또는 Class를 수정·추가·삭제함

REVIEW
→ 판단이 어려워 다른 사람 확인이 필요함
```

### Dataset Manifest에 저장하는 상태

`manifests/dataset_manifest.csv`에서는 용어를 다음처럼 통일합니다.

```text
status = DONE
→ 화면에서 PASS로 처리한 데이터
→ 수정 없이 1차 검수 완료

status = EDITED
→ 수정·추가·삭제 후 저장 완료

status = REVIEW
→ 추가 확인이 필요한 상태
```

그리고 **QA 완료 여부는 별도 컬럼**으로 기록합니다.

```text
qa_status = PASS
→ 교차검수 또는 최종 QA까지 완료

qa_status = WAIT
→ 아직 QA가 끝나지 않음
```

즉 화면의 `PASS`와 Manifest의 `qa_status = PASS`를 같은 의미로 혼동하지 않습니다.

```text
화면 PASS
→ 1차 작업 결과
→ Manifest status = DONE

최종 QA PASS
→ Manifest qa_status = PASS
```

이 정보는 3일차부터 `Dataset Manifest`에 본격적으로 기록합니다.

## 5.1 자동 Validation을 완성합니다

Validation은 사람이 보기 전에 기계적으로 확인할 수 있는 오류를 찾습니다.

필수 확인:

- JPG는 있는데 TXT가 없는가?
- TXT는 있는데 JPG가 없는가?
- TXT 한 줄 형식이 올바른가?
- Class ID가 허용 범위인가?
- YOLO 좌표가 정상 범위인가?
- Width / Height가 정상인가?
- 이미지와 TXT의 기본 파일명이 맞는가?

`Empty TXT`는 무조건 오류로 확정하지 않습니다.

```text
Empty TXT 발견
        ↓

실제 대상 없음 → 정상 가능
대상 있음 → 누락 라벨
판단 어려움 → REVIEW
```

# 8. 필요할 때 찾아보는 기준 — 좌표

이 장은 처음부터 외우지 않습니다.

BBox가 화면에서 어긋나거나 Zoom/Pan을 구현할 때 다시 봅니다.

## 8.1 가장 중요한 원칙

> **정답 BBox 상태는 항상 원본 이미지 기준으로 관리합니다.**

화면 좌표는 표시용입니다.

```text
원본 이미지 좌표
        ↓
화면 크기에 맞게 변환
        ↓
Zoom / Pan
        ↓
Canvas 표시
```

마우스로 새 BBox를 만들면 반대로 처리합니다.

```text
Canvas 마우스 좌표
        ↓
Zoom / Pan 영향 제거
        ↓
원본 Pixel 좌표
        ↓
YOLO 정규화 좌표
        ↓
TXT 저장
```

## 8.2 Round-trip 확인

```text
기존 YOLO TXT
        ↓
원본 Pixel
        ↓
화면 표시
        ↓
다시 YOLO 저장
        ↓
프로그램 종료
        ↓
재실행
        ↓
같은 위치에 BBox
```

같은 위치에 돌아오지 않으면 본 라벨링을 중단합니다.

# 9. 필요할 때 찾아보는 기준 — Human QA와 REVIEW

자동 Validation을 통과해도 의미가 틀릴 수 있습니다.

예:

- 이물이 있는데 BBox 없음
- 잘못된 김치 조각에 BBox
- Class가 틀림
- BBox가 너무 큼
- 객체 일부가 잘림

Human QA 체크:

- 실제 이물 누락
- 불필요한 BBox
- Class 의미
- BBox 크기
- 작은 객체
- 겹친 객체
- 가장자리 객체
- REVIEW 사유 해결 여부

애매하면 추측하지 않습니다.

```text
애매함
→ REVIEW
→ 다른 작업자 확인
→ 2인 이상 합의
→ 최종 결정·기록
```

# 10. 필요할 때 찾아보는 기준 — 정상 이미지, Empty Label, 대상 객체 단독 이미지, Class 4

## 10.1 정상 이미지와 Empty Label

TXT가 비어 있다고 바로 오류는 아닙니다.

실제 데이터에는 정상 김치 이미지가 섞여 있을 수 있습니다.

```text
Empty TXT
        ↓
이미지 직접 확인
        ↓
대상 객체가 정말 없음
→ 정상 Negative Sample
→ Empty TXT 유지 가능
→ PASS

대상 객체가 보임
→ 라벨 누락
→ BBox + Class 추가
→ EDITED

판단 어려움
→ REVIEW
```

정상 이미지는 객체검출 모델이 **“검출하지 않아야 할 상황”**을 배우는 데 중요합니다.

따라서 “BBox가 없으니 학습에 쓸 수 없다”고 삭제하지 않습니다.

---

## 10.2 대상 객체 단독 이미지

단순한 배경 위에 대상 객체만 보이는 이미지도 데이터셋에 포함될 수 있습니다.

이 경우:

```text
대상 객체 존재
→ Class 확인
→ BBox 확인
→ 필요 시 수정
```

김치 배경이 없다는 이유로 교과 7에서 임의 삭제하지 않습니다.

다만 교과 8에서는 실제 제조환경과 배경 분포가 다르므로 별도 그룹으로 통계를 확인하여 학습·검증 용도를 판단합니다.

Manifest의 `scene_type = object_only`를 활용합니다.

---

## 10.3 장면 유형과 Class를 혼동하지 않습니다

```text
normal_kimchi
object_only
kimchi_with_target
```

은 이미지의 장면 유형입니다.

YOLO Class는 아닙니다.

Class ID `0~6` 체계에 새로운 ID를 추가하지 않습니다.

---

## 10.4 Class 4

`4 = 고무장갑`은 이번 프로젝트에서 사용하지 않는 항목입니다.

기존 TXT에서 발견하면:

1. 자동 삭제하지 않음
2. REVIEW
3. 이미지와 BBox 확인
4. 2인 이상 확인
5. 처리 근거 기록

# 11. 프로젝트 중단 신호 — 이 문제가 보이면 대량작업을 멈춥니다

다음 문제는 “나중에 고치자”고 넘기지 않습니다.

- 저장 후 BBox 위치가 바뀜
- Zoom 전후 BBox가 객체에서 벗어남
- 재실행 후 BBox가 사라짐
- Class ID가 저장 과정에서 변경됨
- 다른 이미지 TXT를 덮어씀
- RAW가 수정됨
- 저장하지 않은 수정이 자주 유실됨
- TXT가 빈 파일 또는 깨진 파일이 됨
- 다음 이미지에 이전 BBox가 남음

대응:

```text
대량작업 중지
→ 문제 재현
→ 영향 범위 확인
→ RAW와 WORK 비교
→ 기능 수정
→ Golden Sample 재시험
→ Pilot 재시험
→ 통과 후 재개
```

> 교과 7에서 기존 `validation` 폴더를 임의로 train에 섞지 않습니다.

또한 대상 객체 단독 이미지에서 높은 성능이 나온다고 해서 실제 김치 배경에서도 같은 성능이 보장되는 것은 아닙니다.

따라서 교과 8에서는 가능하면 다음 관점도 구분하여 평가합니다.

```text
김치 배경 + 대상 객체
정상 김치
대상 객체 단독
```
