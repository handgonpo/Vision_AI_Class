## 1.3 이미지에는 서로 다른 장면 유형이 섞여 있습니다

실제 폴더를 확인하면 모든 이미지가 똑같은 형태는 아닙니다.

![[Pasted image 20260928132227.png|149]]![[Pasted image 20260928132243.png|153]]![[Pasted image 20260928132301.png|154]]![[Pasted image 20260928132322.png|123]]![[Pasted image 20260928132341.png|149]]![[Pasted image 20260928132354.png|140]]

## 이미지 유형에 따라 무엇을 확인해야 하나요?

제공된 900장의 이미지를 살펴보면 크게 다음 세 가지 형태가 있습니다.

```text
A. 김치 + 검출 대상 객체
   → 김치 사이에 이물질 또는 학습 대상 객체가 보이는 이미지

B. 정상 김치
   → 검출 대상 객체가 보이지 않는 이미지

C. 검출 대상 객체 단독 이미지
   → 김치가 거의 없고 대상 객체가 단순한 배경 위에 보이는 이미지
```

세 유형 모두 제공 데이터의 일부이므로 임의로 삭제하지 않습니다.

### A. 김치와 검출 대상 객체가 함께 있는 이미지

이 경우에는 **이미지에 보이는 검출 대상 객체의 BBox와 Class가 맞는지 확인**합니다.

예를 들어 이미지에 나뭇가지와 플라스틱 조각이 있다면,

```
나뭇가지
→ 해당 Class의 BBox 확인

플라스틱 조각
→ 해당 Class의 BBox 확인
```

처럼 처리합니다.

김치는 원래 검출 대상 Class가 아니므로 별도의 BBox를 만들지 않습니다.

즉, 이번 프로젝트에서는 **제공된 Class 기준에 해당하는 객체만 라벨링하고 검수합니다.**

작업자가 JPG와 TXT를 탐색기에서 매번 따로 찾아 열 필요는 없습니다.

라벨링 프로그램이 다음과 같이 처리하도록 만듭니다.

```
이미지 열기
        ↓
같은 이름의 TXT 자동 찾기
        ↓
기존 BBox와 Class를 이미지 위에 표시
        ↓
작업자가 실제 이미지와 비교하여 확인
```

기존 라벨이 맞으면 `PASS`, 틀리면 수정하고, 빠진 객체가 있으면 BBox를 추가합니다.

---

### B. 정상 김치 이미지

정상 김치 이미지에는 **검출 대상 객체가 없을 수 있습니다.**

이 경우에는 BBox가 하나도 없는 것이 정상일 수 있습니다.

```
이미지 확인
        ↓
검출 대상 객체가 없음
        ↓
BBox 없음
        ↓
정상 데이터
```

이때 TXT가 비어 있다면 바로 오류라고 판단하지 않습니다.

라벨링 프로그램에서 이미지와 TXT를 함께 불러온 뒤 사람이 확인합니다.

```
빈 TXT
        ↓
이미지 확인
        ↓

정말 이물이 없음
→ PASS

이물이 있는데 BBox가 없음
→ 누락된 BBox 추가
→ EDITED
```

따라서 900개의 TXT를 메모장으로 하나씩 열어 확인하는 작업이 아닙니다.

**프로그램이 TXT를 읽고 화면에 BBox를 표시하며, 작업자는 이미지와 표시 결과를 비교하여 검수합니다.**

---

### C. 검출 대상 객체만 보이는 이미지

일부 이미지에는 김치가 없고 이물질이나 학습 대상 객체만 단순한 배경 위에 보입니다.

이 이미지도 그대로 검수합니다.

예를 들어 이미지에 나뭇가지 하나만 있다면,

```
이미지
→ 나뭇가지 확인

기존 TXT
→ 나뭇가지 BBox와 Class 확인

정확함
→ PASS

BBox 위치 또는 Class가 틀림
→ 수정

BBox가 없음
→ 새 BBox 추가
```

즉 **김치가 없다고 해서 라벨링하지 않는 것이 아닙니다.**

이미지 안에 이번 프로젝트의 검출 대상 Class가 있으면 그 객체의 BBox와 Class를 확인합니다.

다만 이런 이미지는 실제 김치 위에서 촬영한 이미지와 배경이 다르므로, 교과 7에서는 삭제하거나 임의로 분리하지 않고 출처를 기록하여 그대로 보존합니다.

교과 8에서 객체검출 모델을 학습할 때

```
김치 + 대상 객체 이미지
정상 김치 이미지
대상 객체 단독 이미지
```

가 각각 얼마나 포함되어 있는지 다시 확인하여 학습데이터 구성을 결정합니다.

> 정리하면: 
> 
> 학생이 900개의 TXT 숫자를 직접 편집하는 것이 아니라, 
> 라벨링 프로그램이 JPG와 TXT를 함께 불러와 기존 BBox를 보여주고, 
> 
> 학생은 화면을 보면서 
> 	- 맞으면 PASS, 
> 	- 틀리면 수정, 
> 	- 빠졌으면 추가
> 하는 방식으로 작업합니다.

## 1.4 Class와 이미지 유형을 구분합니다

이번 프로젝트에서 **Class**란  
이미지 안에서 BBox로 표시하고 학습할 **객체의 종류**를 뜻합니다.

예를 들어 이번 프로젝트의 Class는 다음과 같습니다.

```text
Class 0 = 나뭇잎·종이류
Class 1 = 플라스틱류·돌·금속 등
Class 2 = 나뭇가지류
Class 3 = 벌레류
Class 4 = 고무장갑
Class 5 = 병해·갈변
Class 6 = 파·고추
```

즉,

```
이미지 안에서 무엇을 찾아야 하는가?
        ↓
그 객체의 종류가 Class
```

입니다.

### 그런데 이미지 자체도 형태가 여러 가지입니다

제공된 이미지에는 다음과 같은 형태가 섞여 있을 수 있습니다.

```
A. 김치 + 검출 대상 객체

B. 정상 김치

C. 검출 대상 객체만 단독으로 있는 이미지
```

이 세 가지는 **Class가 아닙니다.**

왜냐하면 이 말들은  
이미지 안의 객체 종류를 나타내는 것이 아니라  
**이미지 전체가 어떤 형태인지 설명하는 말**이기 때문입니다.

예를 들어,

```
김치 + 벌레가 있는 이미지
```

라면

```
이미지 유형
→ 김치 + 검출 대상 객체

BBox로 표시할 Class
→ 벌레류(Class 3)
```

입니다.

또,

```
정상 김치 이미지
```

라면

```
이미지 유형
→ 정상 김치

BBox로 표시할 Class
→ 없음
```

입니다.

또,

```
단순한 배경에 나뭇가지 하나만 있는 이미지
```

라면

```
이미지 유형
→ 검출 대상 객체 단독 이미지

BBox로 표시할 Class
→ 나뭇가지류(Class 2)
```

입니다.

---

### 따라서 Class는 새로 만들지 않습니다

다음처럼 만들지 않습니다.

```
잘못된 예

Class 7 = 정상 김치
Class 8 = 이물질 단독 이미지
```

이번 프로젝트에서 사용하는 Class는  
**회사에서 제공한 Class ID 0~6 기준만 사용합니다.**

---

### 이미지 유형은 별도로 기록할 수 있습니다

이미지 유형은 라벨 Class와는 별도로  
Manifest에서 데이터 분석용 정보로 기록할 수 있습니다.

예:

```
scene_type

kimchi_with_target
→ 김치 + 검출 대상 객체

normal_kimchi
→ 정상 김치

object_only
→ 검출 대상 객체 단독 이미지

other_review
→ 바로 구분하기 어려운 이미지
```

이 정보는 교과 8에서

```
정상 김치가 몇 장인지

김치 + 이물 이미지가 몇 장인지

이물만 단독으로 찍힌 이미지가 몇 장인지
```

확인할 때 사용할 수 있습니다.

> **정리**
> 
> `Class` = BBox로 표시할 객체의 종류  
> `이미지 유형` = 이미지 전체가 어떤 형태인지 설명하는 정보

## 1.5 데이터의 성격

본 데이터는 실제 산업현장에서 사용되는 데이터의 분포 구조를 교육 목적으로 재현한 **100% 가상 생성 데이터**입니다.

따라서 프로젝트 발표나 포트폴리오에서 실제 생산라인에서 취득한 원본 데이터라고 표현하지 않습니다.

포트폴리오에는 다음 의미가 드러나도록 작성합니다.

> **본 프로젝트는 AI캠퍼스 교육을 위해 실제 산업데이터와 유사한 분포 구조로 100% 가상 생성된 조각김치 이물검출 학습데이터를 활용하여 수행하였습니다.**

## 1.6 NDA와 외부 유출 금지

이 데이터는 교육생의 NDA(비밀유지계약) 서명을 전제로 사용합니다.

허용 목적은 다음과 같습니다.

- AI 학습
- AI 테스트
- 교육 프로젝트 수행
- 허용된 범위의 포트폴리오 제작

다음 행동은 하지 않습니다.

- 원본 JPG 또는 TXT를 공개 저장소에 업로드
- 데이터 압축파일을 외부인에게 전달
- 공개 파일공유 서비스에 원본 데이터를 업로드
- 공개 Git 저장소에 원본 데이터 폴더 포함
- 개인 클라우드에 임의 백업
- 메신저·커뮤니티에 원본 데이터를 배포

소스코드를 버전관리할 때도 **데이터와 소스코드를 분리**합니다.

> **시작 전 확인**
>
> 데이터가 무엇인지, 기존 TXT가 무엇인지, 왜 원본 폴더와 split 정보를 보존해야 하는지, RAW를 왜 직접 수정하면 안 되는지를 팀원 모두가 설명할 수 있어야 합니다.

# 2. 프로젝트를 시작할 때 가장 먼저 알아야 할 것

처음 프로젝트를 하면 가장 어려운 질문은 대개 비슷합니다.

```text
무엇을 만들어야 하지?
        ↓
어디까지 만들면 끝난 거지?
        ↓
오늘은 무엇부터 해야 하지?
        ↓

        ↓

        ↓
무엇을 기록해야 하지?
        ↓
그 기록은 나중에 어디에 쓰이지?
```

이 가이드는 이 질문을 **5일 동안 순서대로 해결하도록 구성**되어 있습니다.

처음부터 문서 전체를 외울 필요가 없습니다.

## 2.2 어디까지 만들면 프로젝트가 끝난 것인가요?

다음 상태가 되어야 프로젝트가 완료된 것으로 봅니다.

| 영역 | 완료 기준 |
|---|---|
| 프로그램 | 기존 YOLO TXT를 읽고 BBox·Class를 표시·추가·삭제·변경할 수 있음 |
| 탐색 | 이전/다음 이미지 이동과 4K 이미지 Zoom/Pan이 안정적으로 동작함 |
| 좌표 | 저장 후 다시 불러와도 BBox가 같은 위치에 나타남 |
| 저장 | RAW는 보존하고 WORK에 YOLO TXT를 안전하게 저장함 |
| 진행관리 | 900장의 작업자·검수자·상태를 확인할 수 있음 |
| 자동 QA | Pair, TXT 형식, Class, 좌표 등의 오류를 찾을 수 있음 |
| Human QA | 수정·신규·REVIEW 데이터가 다른 사람에게 검수됨 |
| 최종 데이터 | Critical Error와 미처리 REVIEW 없이 FINAL이 확정됨 |
| 문서 | Class/BBox 기준, QA 결과, README, 테스트 결과가 정리됨 |
| 인계 | 교과 8에서 FINAL 데이터를 바로 사용할 수 있음 |

다음 상태는 완료가 아닙니다.

```text
GUI 창이 실행됨
또는
BBox 하나가 그려짐
또는
900장을 한 번씩 열어봄
```

> **완료 = 프로그램 + 검수된 데이터 + QA 기록 + 문서 + 교과 8 인계**

## 2.4 이 가이드는 어떻게 읽나요?

### 프로젝트 시작 직후

먼저 `0~2장`만 읽습니다.

목표는 세 가지입니다.

```text
무엇을 만드는지 이해
        ↓
데이터와 보안 규칙 이해
        ↓
5일 동안 어떻게 진행하는지 이해
```

### 1일차

`3. 1일차 수행가이드`를 따라갑니다.

Class, BBox, YOLO 형식, 기준선 등은 **1일차에 실제 데이터를 확인하면서 이해**합니다.

처음부터 모든 세부 규칙을 외우지 않습니다.

### 2~5일차

그날의 수행가이드만 먼저 읽습니다.

작업 중 필요한 규칙이 나오면 뒤쪽의 `필요할 때 찾아보는 기준`을 확인합니다.

예:

```text
Class가 헷갈림
→ Class 기준 찾아보기

BBox를 얼마나 크게 그릴지 애매함
→ BBox 기준 찾아보기

BBox가 화면에서 어긋남
→ 좌표 기준 찾아보기

기존 TXT가 이상함
→ Validation / REVIEW 기준 찾아보기
```

## 2.5 코딩은 어떤 생각으로 시작하나요?

이번 프로젝트에서는 완성 코드를 한 번에 작성하지 않습니다.

라벨링 프로그램은 다음 패턴으로 만듭니다.

```text
작은 기능 하나 정하기
        ↓
그 기능의 입력과 결과 생각하기
        ↓
구현하기
        ↓
직접 실행하기
        ↓
정상인지 확인하기
        ↓
오류가 있으면 그 기능만 수정하기
        ↓
통과하면 다음 기능 연결
```

### 기능 하나를 만들기 전에 네 가지를 먼저 적어봅니다

| 질문 | 예 |
|---|---|
| 입력은 무엇인가? | JPG 경로, TXT 경로, 마우스 좌표 |
| 무엇을 해야 하는가? | 이미지 읽기, BBox 생성, Class 연결 |
| 결과는 무엇인가? | 화면 이미지, BBox 목록, TXT |
| 실패했는지 어떻게 알 수 있는가? | 파일 없음, 좌표 불일치, 저장 실패 |

이것이 여러분의 **코딩 설계 패턴**입니다.

### 라벨링 프로그램을 만드는 권장 순서

```text
1. JPG 한 장 읽기
        ↓
2. 화면에 이미지 표시
        ↓
3. 같은 이름의 TXT 찾기
        ↓
4. TXT 읽기
        ↓
5. 기존 BBox를 화면에 표시
        ↓
6. 새 BBox 한 개 작성
        ↓
7. BBox에 Class 연결
        ↓
8. WORK에 YOLO TXT 저장
        ↓
9. 프로그램 종료 후 다시 Load
        ↓
10. 같은 위치에 BBox가 복원되는지 확인
```

여기까지가 **가장 작은 End-to-End**입니다.

이것이 성공한 뒤에만 다음 기능을 붙입니다.

```text
이전 / 다음
        ↓
다중 BBox
        ↓
삭제 / Class 변경
        ↓
Zoom / Pan
        ↓
저장 유실 방지
        ↓
작업상태 관리
        ↓
Validation
```

> **코딩 핵심**
>
> `작은 기능 → 실행 → 확인 → 다음 기능`
>
> 이 순서를 반복합니다.

## 2.6 잘 만든 기능인지 어떻게 검증하나요?

프로젝트에서는 “실행됐으니 끝”이라고 판단하지 않습니다.

검증도 단계별로 커집니다.

```text
1단계
기능 하나 직접 실행
        ↓
2단계
1장 End-to-End
        ↓
3단계
Golden Sample 10~20장
        ↓
4단계

        ↓
5단계
900장 전체 Validation + Human QA
        ↓
6단계

```

각 단계에서 실패하면 다음 단계로 넘어가지 않습니다.

## 2.7 무엇을 기록하고, 왜 기록하나요?

기록은 보고서를 예쁘게 만들기 위한 것이 아닙니다.

기록이 있어야

```text
누가 작업했는지
무엇을 수정했는지
어떤 오류가 있었는지
어디까지 검수했는지
어떤 데이터가 아직 위험한지
```

를 알 수 있습니다.

| 기록 | 언제 만들기 시작하나? | 나중에 어디에 쓰나? |
|---|---|---|
| 프로젝트 기준선 | 1일차 | 팀이 같은 규칙으로 개발·라벨링하는 기준 |
| 데이터 조사표 | 1일차 | 실제 파일 수·구조·문제 확인 |
| Class/BBox 기준서 | 1일차 | 작업자와 검수자가 같은 판단을 하기 위한 기준 |
| Issue 기록 | 1일차부터 계속 | 오류 재현·수정·재검증 |
| Dataset Manifest | 3일차부터 본격 사용 | 900장 작업 배분·상태·review 관리 |
| Pilot Test 결과 | 3일차 | 본 작업을 시작해도 되는지 판단 |
| QA Summary | 4~5일차 | 라벨 품질과 오류 처리 결과 확인 |
| Test Report | 2~5일차 | Golden/Pilot/Acceptance 결과 정리 |
| README | 개발 중 갱신, 5일차 확정 | 다른 사람이 프로그램을 실행하기 위한 설명 |
| 교과 8 Handoff | 5일차 | 다음 객체검출 프로젝트에 데이터 인계 |

> **기록은 현재 작업을 관리하고, 다음 사람이 결과를 신뢰할 수 있게 만드는 증거입니다.**

## 3.2 2단계 — 실제 데이터 구조를 조사합니다

코딩하기 전에 **실제 제공된 폴더 구조와 분포를 먼저 조사**합니다.

현재 확인된 구조는 다음과 같습니다.

```text
Dataset 1
└── train
    ├── images
    └── labels

Dataset 2
├── train
│   ├── images
│   └── labels
└── validation
    ├── images
    └── labels
```

학생들은 폴더 이름만 보고 끝내지 말고 실제 개수를 조사합니다.

### 데이터셋·split별로 기록할 항목

- `dataset1 / train` JPG 수
- `dataset1 / train` TXT 수
- `dataset2 / train` JPG 수
- `dataset2 / train` TXT 수
- `dataset2 / validation` JPG 수
- `dataset2 / validation` TXT 수
- 전체 JPG 수
- 전체 TXT 수
- 같은 기본 이름의 JPG-TXT Pair 수
- JPG만 있고 TXT가 없는 파일
- TXT만 있고 JPG가 없는 파일
- 실제로 등장하는 Class ID
- Empty TXT 수
- 이미지별 BBox 개수 분포
- Class별 BBox 수

### 장면 유형도 표본 조사합니다

샘플 이미지를 보면서 다음 유형이 어느 정도 존재하는지 기록합니다.

```text
kimchi_with_target
→ 김치 배경 + 검출 대상 객체

normal_kimchi
→ 김치 배경 + 검출 대상 객체 없음

object_only
→ 단순 배경 + 대상 객체

other_review
→ 위 기준으로 바로 판단하기 어려움
```

장면 유형은 YOLO Class가 아니라 **데이터 구성과 분포를 이해하기 위한 보조 정보**입니다.

### 중요한 원칙

기존 `train / validation` 구조를 교과 7에서 임의로 섞지 않습니다.

또 Dataset 1과 Dataset 2를 하나의 폴더로 단순 복사하여 파일 출처를 잃지 않습니다.

가능하면 다음 정보가 계속 추적되게 합니다.

```text
source_dataset
original_split
relative_path
file_name
```

### 남길 기록

## 3.3 3단계 — YOLO TXT와 기존 라벨의 의미를 실제 샘플로 확인합니다

이번 프로젝트에서는 이미지와 함께 기존 TXT가 이미 제공됩니다.

TXT 한 줄은 객체 하나를 의미합니다.

```text
Class_ID   X_center   Y_center   Width   Height
```

예:

```text
6 0.8006198347 0.6231481481 0.0340909091 0.0537037037
```

좌표는 Pixel이 아니라 이미지 크기에 대한 **정규화 비율값**입니다.

### 중요한 이해

TXT는 라벨링을 하기 위한 보조 메모가 아니라 **현재 이미지에 대해 이미 작성되어 있는 라벨 결과**입니다.

따라서 교과 7의 기본 작업은 다음과 같습니다.

```text
기존 JPG + 기존 TXT
        ↓
프로그램에서 함께 Load
        ↓
TXT의 BBox와 Class를 화면에 표시
        ↓
사람이 실제 이미지와 비교
        ↓
정상 → PASS
오류 → 수정
누락 → BBox 추가
불필요 → 삭제
Class 오류 → Class 변경
애매함 → REVIEW
        ↓
WORK에 보정된 TXT 저장
```

즉, **900장을 모두 빈 상태에서 처음부터 다시 그리는 작업이 아닙니다.**

다만 기존 TXT가 있다고 해서 모두 정확하다고 가정하지 않습니다.  
900장의 이미지는 사람이 확인해야 하며, 필요한 경우에만 라벨을 보정합니다.

### 정상 이미지의 TXT

이미지를 자세히 확인했는데 검출 대상 객체가 없다면 BBox가 없어도 됩니다.

```text
정상 김치 이미지
        ↓
검출 대상 객체 없음
        ↓
BBox 없음
        ↓
빈 TXT가 정상 정답일 수 있음
```

따라서 Empty TXT를 발견하면 자동 오류 처리하지 않습니다.

```text
Empty TXT
        ↓
이미지 확인
        ↓
실제로 대상 없음 → NORMAL / PASS
대상이 있는데 라벨 없음 → 누락 오류 / EDITED
판단 어려움 → REVIEW
```

### 대상 객체 단독 이미지

김치 배경이 거의 없고 단순한 배경에 대상 객체만 있는 이미지도 확인합니다.

```text
대상 객체 존재
        ↓
제공된 Class에 해당
        ↓
BBox + Class 검수
```

이 이미지를 “김치가 없으므로 필요 없다”고 임의 삭제하지 않습니다.

교과 8에서 학습·검증 데이터로 어떻게 사용할지는 별도의 데이터 분포 검토를 통해 결정합니다.

---

## 3.4 4단계 — 샘플 약 30장을 먼저 봅니다

처음부터 900장을 모두 확인하지 않습니다.

샘플은 한 폴더의 앞부분에서만 고르지 않고 **데이터셋·split·장면 유형이 섞이도록** 선택합니다.

예를 들어 다음 출처를 모두 포함하도록 합니다.

- Dataset 1 / train
- Dataset 2 / train
- Dataset 2 / validation

가능하면 다음 장면 유형도 섞습니다.

- 김치 + 대상 객체
- 정상 김치
- 대상 객체 단독 이미지
- BBox 1개 이미지
- BBox 여러 개 이미지
- 작은 객체
- 이미지 가장자리 객체
- 서로 다른 Class
- Empty TXT 이미지

샘플마다 다음 질문에 답합니다.

1. JPG와 TXT가 정확히 Pair인가?
2. TXT 줄 수와 표시되는 BBox 수가 맞는가?
3. BBox가 실제 객체 위치에 맞는가?
4. Class가 맞는가?
5. BBox가 지나치게 크거나 작은가?
6. 대상 객체가 있는데 누락된 BBox가 있는가?
7. Empty TXT라면 실제로 정상 이미지인가?
8. 대상 객체 단독 이미지도 라벨이 정확한가?
9. 원본 `train / validation` 정보가 유지되고 있는가?

### 샘플 조사 결과에서 꼭 구분할 것

```text
정상 김치
→ "라벨이 없는 오류 데이터"가 아니라
   "객체 없음"이라는 정상 Negative Sample일 수 있음

대상 객체 단독 이미지
→ "김치가 없는 잘못된 데이터"가 아니라
   대상 형태를 포함한 Positive Sample일 수 있음

김치 + 대상 객체
→ 실제 제조환경과 가장 유사한 장면 유형 중 하나
```

이 단계에서 어떤 유형을 삭제하거나 재분할하지 않습니다.

**먼저 데이터가 어떻게 구성되어 있는지 이해하고 기록하는 것이 목적**입니다.

---

## 3.5 5단계 — Class 기준을 Freeze합니다

이번 프로젝트에서는 제공된 Class ID를 그대로 유지합니다.

| Class ID | 이물 종류 | 사용 기준 |
|---:|---|---|
| **0** | 나뭇잎·종이류 | 사용 |
| **1** | 플라스틱류·돌·금속 등 | 사용 |
| **2** | 나뭇가지류 | 사용 |
| **3** | 벌레류 | 사용 |
| **4** | 고무장갑 | **사용하지 않음** |
| **5** | 병해·갈변 | 사용 |
| **6** | 파·고추 | 사용 |

Class를 보기 좋게 다시 `0~5`로 바꾸지 않습니다.

```text
잘못된 예
5 → 4
6 → 5

올바른 원칙
0, 1, 2, 3, 4, 5, 6 유지
```

기존 TXT에서 Class 4가 발견되면 자동 삭제하지 않고 `REVIEW`로 보냅니다.

---

## 3.6 6단계 — BBox 공통 기준을 Freeze합니다

팀원마다 사각형을 다르게 그리면 데이터 품질이 흔들립니다.

공통 원칙:

- 객체 전체 포함
- 가능한 한 객체 경계에 가깝게
- 불필요한 배경 최소화
- 객체 일부를 잘라내지 않음
- 서로 다른 객체는 각각 BBox
- 구분 가능한 겹친 객체는 각각 BBox
- 아주 작아도 Class를 판단할 수 있으면 누락하지 않음
- 애매하면 추측하지 않고 REVIEW

```text
너무 큼
객체 + 넓은 배경
→ 수정

적절함
객체 전체 + 최소 배경
→ PASS

너무 작음
객체 일부 잘림
→ 수정
```

## 3.7 7단계 — 프로젝트 기준선(Baseline)을 확정합니다

기준선은 **팀 전체가 같은 방향으로 작업하기 위한 공통 약속**입니다.

### 이미 정해져 있는 기준

팀이 바꾸지 않습니다.

- JPG 900장 + YOLO TXT 900개

- Class ID 0~6 유지
- RAW 수정 금지
- WORK에서 수정
- QA가 끝난 결과만 FINAL
- 원본 이미지 기준으로 BBox 관리

| Git | Branch / Commit / Merge 방식 |

| 작업자    | **작업자 선택/표시**              | 누가 작업했는지 기록                | 필수       |
| 작업자    | **검수자 선택/표시**              | 누가 교차검수했는지 기록              | 권장       |
| 데이터    | **Scene Type 선택**          | 정상 김치 / 김치+대상 / 객체 단독 등 기록 | 권장       |
| 저장     | **저장**                     | YOLO TXT + CSV 상태 저장       | 필수       |
| 저장     | **저장 후 다음**                | 저장하고 자동으로 다음 이미지 이동        | 매우 권장    |
| 저장     | **미저장 경고**                 | 수정 후 저장하지 않고 이동할 때 경고      | 필수       |
| QA     | **Validation 실행**          | TXT 형식·좌표·Class 오류 검사      | 필수       |
| QA     | **REVIEW만 보기**             | 검수 필요한 이미지만 모아보기           | 권장       |
| QA     | **EDITED만 보기**             | 수정된 이미지만 재검수               | 권장       |
| 편의     | **Undo**                   | 마지막 작업 취소                  | 권장       |
| 편의     | **단축키**                    | 다음/이전/저장 등을 빠르게 처리         | 선택       |
| 편의     | **BBox 색상 구분**             | Class별로 BBox 색상을 달리 표시     | 권장       |

## 4.1 1단계 — 어제 만든 것을 다른 사람이 다시 실행합니다

만든 사람이 옆에서 설명하지 않아도

- 이미지가 열리는가?
- 기존 BBox가 보이는가?
- 저장 후 다시 열면 같은가?

를 확인합니다.

실패하면 오늘 새 기능을 만들기 전에 먼저 고칩니다.

---

## 4.2 2단계 — 이미지 탐색을 완성합니다

필요 기능:

- 이미지 목록 읽기
- 이전
- 다음
- 첫/마지막 경계 처리
- 파일명
- 현재 번호 / 전체 수

### 검증

20장 이상 연속으로 이동합니다.

- 프로그램이 멈추지 않는가?
- 이전 이미지의 BBox가 다음 이미지에 남지 않는가?

---

## 4.3 3단계 — 기존 YOLO TXT를 여러 이미지에서 표시합니다

여러 줄의 TXT가 있는 이미지에서 모든 BBox가 보여야 합니다.

확인:

- TXT 줄 수 = BBox 표시 수인가?
- Class가 구분되는가?
- 이미지마다 BBox 위치가 맞는가?

이 단계가 틀리면 새 BBox 기능으로 넘어가지 않습니다.

---

## 4.4 4단계 — 새 BBox와 Class를 연결합니다

사용 흐름:

```text
이물 발견
        ↓
BBox 작성
        ↓
Class 지정
        ↓
화면에서 확인
        ↓
저장
```

한 이미지에 여러 BBox를 작성해 봅니다.

확인:

- 아주 작은 실수 드래그가 BBox가 되지 않는가?
- 이미지 밖으로 BBox가 만들어지지 않는가?
- Class가 없는 BBox가 저장되지 않는가?

---

## 4.5 5단계 — 잘못된 라벨을 고칠 수 있게 합니다

가장 단순하고 안정적인 수정:

```text
잘못된 BBox
→ 선택
→ 삭제
→ 필요하면 다시 작성
```

Class만 틀린 경우에는 Class만 변경할 수 있게 합니다.

복잡한 Drag 이동이나 Resize Handle은 필수 기능이 아닙니다.

---

## 4.6 6단계 — 4K 이미지를 위한 Zoom / Pan을 완성합니다

작은 이물을 확인하려면 필수입니다.

- Fit to Window
- Zoom In
- Zoom Out
- Pan
- 현재 배율 확인
- 확대 상태에서 BBox 작성

### 가장 중요한 검증

```text
확대
→ BBox 작성
→ 원래 배율
→ 같은 객체 위치 유지
```

Zoom/Pan 후 BBox가 움직이면 본 작업을 시작할 수 없습니다.

---

## 4.7 7단계 — Save / Reload / 저장 유실 방지를 확인합니다

시나리오 1:

```text
BBox 수정
→ 저장
→ 다음 이미지
→ 이전 이미지
→ 수정 내용 유지
```

시나리오 2:

```text
BBox 수정
→ 저장하지 않음
→ Next 또는 Exit
→ 작업 유실 방지 확인
```

원칙:

- RAW에 저장하지 않음
- WORK에 저장
- 저장 성공 후 이동
- 저장 실패는 오류로 남김

---

## 4.8 8단계 — Golden Sample 10~20장으로 기능을 시험합니다

Golden Sample은 모델 평가 데이터가 아닙니다.

**라벨링 프로그램이 좌표와 Class를 망가뜨리지 않는지 확인하는 기능시험용 샘플**입니다.

권장 순서:

1. 기존 라벨을 사람이 먼저 확인
2. 문제가 없는 10~20장을 Reference로 지정
3. 프로그램으로 Load / Save / 일부 수정
4. 다시 Load
5. BBox 위치와 Class가 유지되는지 확인

---

## 4.9 2일차에 무엇을 기록하나요?

- 핵심 기능 테스트 결과
- Golden Sample 목록
- Save/Reload 결과
- Zoom/Pan 좌표 문제 여부
- 발생한 오류
- 해결된 오류
- 아직 남은 오류

3일차 Pilot Test에서 이 기록을 다시 사용합니다.

## 5.2 2단계 — Dataset Manifest를 시작합니다

900장은 사람의 기억으로 관리하지 않습니다.

이번 데이터는 Dataset 1·Dataset 2와 기존 `train / validation` 구조가 있으므로, 작업상태뿐 아니라 **데이터의 출처와 장면 유형도 함께 기록**합니다.

최소 필드:

| 항목 | 의미 |
|---|---|
| image_name | 이미지 파일명 |
| label_name | TXT 파일명 |
| source_dataset | `dataset1` / `dataset2` |
| original_split | `train` / `validation` |
| relative_path | 원본 폴더 안의 상대경로 |
| scene_type | `kimchi_with_target / normal_kimchi / object_only / other_review` |
| assignee | 1차 작업자 |
| reviewer | 검수자 |
| status | 현재 상태 |
| original_bbox_count | 원본 BBox 수 |
| final_bbox_count | 최종 BBox 수 |
| issue | 발견된 문제 |
| note | 판단·수정 기록 |

상태:

```text
PENDING
WORKING
PASS
EDITED
REVIEW
REVIEWED
FINAL
```

### scene_type은 Class가 아닙니다

예:

```text
scene_type = normal_kimchi
```

라고 기록했다고 해서 YOLO TXT에 새로운 Class를 추가하지 않습니다.

`scene_type`은 교과 8에서 데이터 분포를 확인하기 위한 메타데이터입니다.

### Manifest가 나중에 사용되는 곳

```text
교과 7
→ 작업 배분
→ Cross Review
→ QA 통계

교과 8
→ Dataset 1 / 2 출처 확인
→ 기존 train / validation 확인
→ 정상·객체 단독·김치 배경 비율 확인
→ 최종 split 정책 검토
```

Manifest는 단순한 행정 파일이 아니라 **900장 데이터의 provenance(출처), 작업상태, 검수이력을 이어주는 중심 기록**입니다.

- Dataset 2 / validation

- 여러 Class

# 6. 4일차 — 900장 전수 검수 · 필요한 라벨 보정 · Cross Review

## 6.0 오늘은 여기까지만 집중합니다

![[Pasted image 20260928144329.png]]

4일차는 새로운 기능을 만드는 날이 아닙니다.

> **오늘은 기존 900장의 라벨을 전수 확인하고 필요한 부분만 보정하여 데이터 품질을 확정하는 날입니다.**

프로그램에서 Critical 오류가 없다면 기능을 건드리지 않고 900장 처리에 집중합니다.

---

## 6.1 1단계 — 현재 작업량을 확인합니다

Manifest에서 확인:

- 전체 900장
- 완료
- PENDING
- EDITED
- REVIEW
- REVIEWED
- 팀원별 남은 수량

불균형하면 재배분합니다.

같은 이미지를 두 사람이 동시에 수정하지 않습니다.

---

## 6.2 2단계 — 기존 라벨을 전수 검수하고 필요한 경우만 보정합니다

### 기존 라벨이 정상

```text
이미지 전체 확인
→ 기존 BBox 확인
→ Class 확인
→ 누락 없음
→ PASS
```

### 수정 필요

```text
오류 발견
→ BBox / Class 수정
→ EDITED
→ 수정 이유 기록
→ Cross Review
```

### 판단 어려움

```text
애매함
→ REVIEW
→ 추측하지 않음
→ 다른 작업자와 재확인
```

---

## 6.2.1 장면 유형에 따라 확인 방법을 구분합니다

### 김치 + 대상 객체

```text
이미지 전체 확인
→ 기존 BBox 확인
→ 대상 객체 누락 확인
→ Class 확인
→ 필요 시 추가·수정·삭제
```

### 정상 김치

```text
이미지 전체 확인
→ 정말 대상 객체가 없는지 확인
→ 기존 BBox가 없어야 하는지 확인
→ 정상이라면 Empty TXT 유지 가능
→ PASS
```

정상 이미지를 보고 억지로 BBox를 만들지 않습니다.

### 대상 객체 단독 이미지

```text
대상 객체 확인
→ 기존 BBox 위치 확인
→ Class 확인
→ 필요한 경우 보정
```

김치 배경이 없다는 이유로 제외하지 않습니다.

### 매우 중요한 구분

```text
"라벨 없음"
```

은 두 가지 의미가 있을 수 있습니다.

```text
정상 Negative Sample
        VS
라벨 누락 오류
```

따라서 Empty TXT는 사람이 이미지와 함께 확인해야 합니다.

---

## 6.3 3단계 — 수정·신규 라벨은 100% Cross Review합니다

100% 교차검수 대상:

- 새 BBox
- 기존 BBox 수정
- Class 변경
- BBox 추가·삭제
- REVIEW였던 이미지
- Class 4 발견 이미지
- Empty Label

검수 결과:

```text
정상
→ REVIEWED

오류
→ 수정 요청
→ 재수정
→ 다시 Review
```

---

## 6.4 4단계 — PASS 데이터도 표본검수합니다

기존 라벨을 그대로 PASS한 데이터도 일부 다시 봅니다.

권장: **최소 20~30%**

우선 검수:

- 작은 BBox가 많은 이미지
- 한 이미지에 BBox가 많은 경우
- 희소 Class
- 작업자가 판단하기 어려웠던 경우
- 특정 작업자 구간에서 오류가 반복된 경우

# 8. 필요할 때 찾아보는 기준 — 좌표

이 장은 처음부터 외우지 않습니다.

BBox가 화면에서 어긋나거나 Zoom/Pan을 구현할 때 다시 봅니다.

## 8.1 가장 중요한 원칙

> **정답 BBox 상태는 항상 원본 이미지 기준으로 관리합니다.**

화면 좌표는 표시용입니다.

```text
원본 이미지 좌표
        ↓
화면 크기에 맞게 변환
        ↓
Zoom / Pan
        ↓
Canvas 표시
```

마우스로 새 BBox를 만들면 반대로 처리합니다.

```text
Canvas 마우스 좌표
        ↓
Zoom / Pan 영향 제거
        ↓
원본 Pixel 좌표
        ↓
YOLO 정규화 좌표
        ↓
TXT 저장
```

## 8.2 Round-trip 확인

```text
기존 YOLO TXT
        ↓
원본 Pixel
        ↓
화면 표시
        ↓
다시 YOLO 저장
        ↓
프로그램 종료
        ↓
재실행
        ↓
같은 위치에 BBox
```

같은 위치에 돌아오지 않으면 본 라벨링을 중단합니다.

# 9. 필요할 때 찾아보는 기준 — Human QA와 REVIEW

자동 Validation을 통과해도 의미가 틀릴 수 있습니다.

예:

- 이물이 있는데 BBox 없음
- 잘못된 김치 조각에 BBox
- Class가 틀림
- BBox가 너무 큼
- 객체 일부가 잘림

Human QA 체크:

- 실제 이물 누락
- 불필요한 BBox
- Class 의미
- BBox 크기
- 작은 객체
- 겹친 객체
- 가장자리 객체
- REVIEW 사유 해결 여부

애매하면 추측하지 않습니다.

```text
애매함
→ REVIEW
→ 다른 작업자 확인
→ 2인 이상 합의
→ 최종 결정·기록
```

# 10. 필요할 때 찾아보는 기준 — 정상 이미지, Empty Label, 대상 객체 단독 이미지, Class 4

## 10.1 정상 이미지와 Empty Label

TXT가 비어 있다고 바로 오류는 아닙니다.

실제 데이터에는 정상 김치 이미지가 섞여 있을 수 있습니다.

```text
Empty TXT
        ↓
이미지 직접 확인
        ↓
대상 객체가 정말 없음
→ 정상 Negative Sample
→ Empty TXT 유지 가능
→ PASS

대상 객체가 보임
→ 라벨 누락
→ BBox + Class 추가
→ EDITED

판단 어려움
→ REVIEW
```

정상 이미지는 객체검출 모델이 **“검출하지 않아야 할 상황”**을 배우는 데 중요합니다.

따라서 “BBox가 없으니 학습에 쓸 수 없다”고 삭제하지 않습니다.

---

## 10.2 대상 객체 단독 이미지

단순한 배경 위에 대상 객체만 보이는 이미지도 데이터셋에 포함될 수 있습니다.

이 경우:

```text
대상 객체 존재
→ Class 확인
→ BBox 확인
→ 필요 시 수정
```

김치 배경이 없다는 이유로 교과 7에서 임의 삭제하지 않습니다.

다만 교과 8에서는 실제 제조환경과 배경 분포가 다르므로 별도 그룹으로 통계를 확인하여 학습·검증 용도를 판단합니다.

Manifest의 `scene_type = object_only`를 활용합니다.

---

## 10.3 장면 유형과 Class를 혼동하지 않습니다

```text
normal_kimchi
object_only
kimchi_with_target
```

은 이미지의 장면 유형입니다.

YOLO Class는 아닙니다.

Class ID `0~6` 체계에 새로운 ID를 추가하지 않습니다.

---

## 10.4 Class 4

`4 = 고무장갑`은 이번 프로젝트에서 사용하지 않는 항목입니다.

기존 TXT에서 발견하면:

1. 자동 삭제하지 않음
2. REVIEW
3. 이미지와 BBox 확인
4. 2인 이상 확인
5. 처리 근거 기록

# 11. 프로젝트 중단 신호 — 이 문제가 보이면 대량작업을 멈춥니다

다음 문제는 “나중에 고치자”고 넘기지 않습니다.

- 저장 후 BBox 위치가 바뀜
- Zoom 전후 BBox가 객체에서 벗어남
- 재실행 후 BBox가 사라짐
- Class ID가 저장 과정에서 변경됨
- 다른 이미지 TXT를 덮어씀
- RAW가 수정됨
- 저장하지 않은 수정이 자주 유실됨
- TXT가 빈 파일 또는 깨진 파일이 됨
- 다음 이미지에 이전 BBox가 남음

대응:

```text
대량작업 중지
→ 문제 재현
→ 영향 범위 확인
→ RAW와 WORK 비교
→ 기능 수정
→ Golden Sample 재시험
→ Pilot 재시험
→ 통과 후 재개
```
