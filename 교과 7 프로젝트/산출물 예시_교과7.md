# 1. 라벨링 프로그램 — 실행 결과 예시

첫 번째 산출물은 **900장의 조각김치 데이터를 실제로 검수·수정할 수 있도록 완성한 라벨링 프로그램**입니다.

단순히 Python 파일이 실행되는 것만으로는 완료가 아닙니다. 프로그램에서 실제 이미지를 열고 기존 YOLO 라벨을 불러온 뒤, BBox와 Class를 확인·수정하고 다시 저장할 수 있어야 합니다.

예를 들어 완성된 프로그램은 다음과 같은 형태입니다.

> **화면 예시:** 조각김치 이미지 위에 기존 BBox와 Class가 표시되고, 오른쪽에서 Class 선택·라벨 목록·검수 상태·작업자 정보를 확인할 수 있으며, 상단에서 저장·이동·Zoom/Pan·Validation 기능을 사용할 수 있습니다.

![[Pasted image 20260928150540.png]]

## 프로그램에서 실제로 할 수 있어야 하는 것

```
이미지 폴더 열기
        ↓
JPG 이미지 표시
        ↓
같은 이름의 기존 YOLO TXT 불러오기
        ↓
기존 BBox와 Class 화면에 표시
        ↓
BBox 추가 · 수정 · 삭제
        ↓
Class 변경
        ↓
이전 / 다음 이미지 이동
        ↓
4K 이미지 Zoom / Pan
        ↓
검수 상태 기록
PASS / EDITED / REVIEW
        ↓
YOLO TXT 저장
        ↓
저장한 파일 다시 열어 정상 복원 확인
        ↓
Validation 실행
```

즉 단순히 BBox를 그리는 프로그램이 아니라, 
**900장의 실제 라벨을 확인하고 수정하여 FINAL YOLO 데이터를 만들 수 있는 도구**를 완성해야 합니다.

## 이 산출물에서 ==실제로 제출==할 것

### ① 실행 가능한 라벨링 프로그램

프로그램 전체를 제출합니다.

예:

```
labeling_tool/
├── main.py
├── src/
├── config/
├── requirements.txt
└── ...
```

※ 세부 소스코드는 **2번 산출물 `소스코드`에서 별도로 평가**합니다.  
1번에서는 우선 **프로그램이 실제로 정상 동작하는지**를 확인합니다.

### ② 프로그램 실행 화면 캡처

완성된 프로그램이 실제 데이터에서 실행되는 화면을 **2~3장** 제출합니다.

예:

```
캡처 1
→ 기존 YOLO BBox가 정상적으로 Load된 화면

캡처 2
→ 잘못된 BBox 또는 Class를 수정한 화면

캡처 3
→ 저장 및 Validation까지 완료된 화면
```

### ③ 짧은 실행 시연 영상

발표 또는 최종 확인 시 다음 과정을 직접 보여줍니다.

```
이미지 열기
→ 기존 BBox 확인
→ BBox 하나 수정 또는 추가
→ 저장
→ 다음 이미지 이동
→ 다시 돌아오기
→ 수정한 BBox가 그대로 복원되는지 확인
→ Validation 실행
```

# 2. 소스코드 — 제출 예시

2번 산출물에서는 **라벨링 프로그램을 어떤 구조로 개발했는지와 Git으로 개발 과정을 관리했는지**를 확인합니다.

1번 산출물이 완성된 프로그램의 **동작 결과**를 확인하는 것이라면, 2번 산출물은 그 프로그램의 **코드 구조와 개발 이력**을 확인하는 것입니다.

## 1. 기능별로 정리된 소스코드

여기서 말하는 소스코드 구조는 **VS Code 왼쪽 탐색기에 보이는 프로젝트의 실제 폴더·파일 구조**를 말합니다.

예:

```
labeling_tool/
│
├── main.py
├── requirements.txt
│
├── src/
│   ├── ui/
│   │   ├── main_window.py
│   │   └── canvas.py
│   │
│   ├── bbox/
│   │   ├── bbox_manager.py
│   │   └── bbox_editor.py
│   │
│   ├── yolo/
│   │   ├── yolo_loader.py
│   │   └── yolo_writer.py
│   │
│   └── validation/
│       └── validator.py
│
├── configs/
│   └── classes.yaml
│
└── README.md
```

각 파일은 역할이 구분되어 있어야 합니다.

```
main.py
→ 프로그램 시작

ui/
→ 화면 구성과 버튼·이벤트 처리

bbox/
→ BBox 생성·수정·삭제

yolo/
→ YOLO TXT Load / Save

validation/
→ 파일·Class·좌표 검사

configs/
→ Class와 프로그램 설정
```

해야 할 일은 이 구조대로 **실제 Python 파일을 Git 저장소에 올리는 것**입니다.

VS Code 화면 캡처 자체가 산출물은 아닙니다.

다만 발표자료나 LMS 증빙이 필요한 경우에는 **VS Code Explorer의 전체 프로젝트 구조가 보이는 화면 1장**을 보조자료로 제출할 수 있습니다.

==소스코드에는 **실제 이미지 900장과 FINAL 데이터는 포함하지 않습니다.**==

```
필수
→ Git 저장소의 실제 소스코드

선택 증빙
→ VS Code 프로젝트 구조 캡처 1장
```

## 2. `requirements.txt` 실행환경 파일

`requirements.txt`는 프로그램 실행에 필요한 Python 패키지를 기록하는 파일입니다.

예:

```
opencv-python
numpy
Pillow
PyYAML
```

이 파일도 **소스코드와 함께 Git 저장소 최상위에 올립니다.**

```
subject7_kimchi_labeling/
├── main.py
├── requirements.txt   ← Git에 포함
├── src/
└── configs/
```

## 3. Class 설정 파일

이 파일은 프로그램에서 사용할 **Class 0~6의 이름과 사용 여부를 한곳에서 관리하는 설정 파일**입니다.

혼동하지 않도록 이번 프로젝트에서는 형식을 아래와 같이 작성하세요.

```
configs/classes.yaml
```

예:

```yml
classes:
  0:
    name: "나뭇잎·종이류"
    enabled: true

  1:
    name: "플라스틱류·돌·금속류"
    enabled: true

  2:
    name: "나뭇가지류"
    enabled: true

  3:
    name: "벌레류"
    enabled: true

  4:
    name: "고무장갑"
    enabled: false

  5:
    name: "병해·갈변"
    enabled: true

  6:
    name: "파·고추"
    enabled: true
```

즉 이것은 문서가 아니라 **프로그램이 실제로 읽어 사용하는 설정 파일**입니다.

프로그램에서는 이 파일을 읽어 오른쪽 Class 목록 등을 구성할 수 있습니다.

```
configs/classes.yaml
        ↓
프로그램 실행
        ↓
Class 0~6 목록 표시
        ↓
BBox에 Class 지정
```

`classes.yaml` 파일도 **Git 저장소에 함께 올립니다.**

## 4. Git Commit 이력

이것은 프로그램을 **한 번에 완성본으로 올린 것이 아니라 기능별로 개발하고 수정한 과정**을 확인하기 위한 것입니다.

```
feat: 프로젝트 기본 구조 생성
feat: 이미지 폴더 열기와 JPG 표시 구현
feat: 기존 YOLO TXT 불러오기 구현
feat: 기존 BBox 화면 표시 구현
feat: BBox 추가 기능 구현
feat: BBox 수정 및 삭제 기능 구현
feat: Class 선택 및 변경 기능 구현
feat: 이전/다음 이미지 이동 구현
feat: 4K 이미지 Zoom/Pan 구현
feat: YOLO TXT 저장 및 다시 불러오기 구현
feat: PASS/EDITED/REVIEW 상태 저장 구현
feat: Validation 기능 구현
fix: Zoom 상태에서 BBox 좌표가 어긋나는 오류 수정
fix: 저장 후 일부 BBox가 복원되지 않는 오류 수정
docs: README와 사용방법 작성
```

LMS에 별도의 파일을 제출해야 하므로 Git 이력을 TXT로 출력할 수 있습니다.

```bash
git log --oneline --graph --all > git_commit_history.txt
```

그러면 다음과 같은 파일이 만들어집니다.

```bash
git_commit_history.txt
```

내용 예:

```
* a92c014 docs: README 사용방법 추가
* 82ba911 fix: 저장 후 BBox 복원 오류 수정
* 123fab2 feat: Validation 기능 구현
* 6ac3120 feat: YOLO TXT 저장 구현
* ...
```

좀 더 상세하게 **어떤 파일이 변경되었는지까지** 남기고 싶으면 다음 명령을 사용합니다.

```bash
git log --oneline --name-status > git_change_history.txt
```

예:

```
a92c014 docs: README 사용방법 추가
M       README.md

82ba911 fix: 저장 후 BBox 복원 오류 수정
M       src/yolo/yolo_loader.py
M       src/yolo/yolo_writer.py

123fab2 feat: Validation 기능 구현
A       src/validation/validator.py
```

이렇게 하면 **Commit 내용 + 실제 변경된 파일**까지 확인할 수 있습니다.

# 3. FINAL YOLO 라벨 — 최종 제출 산출물

교과 7의 핵심 결과 중 하나는 **교과 8의 객체검출 모델 학습에 바로 사용할 수 있는 최종 YOLO 라벨 데이터**를 만드는 것입니다.

즉, 기존 900장의 이미지와 TXT를 확인한 뒤

```
맞는 라벨
→ 그대로 유지

잘못된 라벨
→ 수정

빠진 객체
→ BBox 추가

잘못 들어간 객체
→ 삭제

판단이 어려운 데이터
→ REVIEW 처리
```

과정을 거쳐 **최종 검수가 끝난 데이터만 `final/`에 저장**합니다.

---

## 1. 이미지와 TXT는 한 쌍입니다

예:

```
250410_144403911987.jpg
250410_144403911987.txt
```

두 파일은 기본 이름이 같아야 합니다.

TXT 한 줄은 객체 하나를 의미합니다.

실제 예:

```
6 0.8006198347107438 0.6231481481481481 0.03409090909090909 0.053703703703703705
6 0.6841425619834711 0.512962962962963 0.030991735537190084 0.06111111111111111
6 0.7161673553719008 0.7236111111111111 0.027892561983471075 0.06851851851851852
6 0.2993285123966942 0.37824074074074077 0.01652892561983471 0.06851851851851852
6 0.46952479338842973 0.28379629629629627 0.02169421487603306 0.046296296296296294
```

이 TXT는 **Class 6 객체 5개가 라벨링되어 있다**는 의미입니다. 250410_144403911987

YOLO 형식은 다음과 같습니다.

```
class_id  x_center  y_center  width  height
```

좌표는 pixel 값이 아니라 **이미지 전체 크기 대비 0~1 사이 비율값**입니다.

## 2. 실제로 해야 할 작업

900장을 모두 라벨링 프로그램에서 확인합니다.

```
이미지 열기
        ↓
같은 이름의 TXT 자동 Load
        ↓
BBox와 Class 확인
        ↓
맞으면 PASS
        ↓
틀리면 수정
        ↓
빠진 객체는 추가
        ↓
잘못된 객체는 삭제
        ↓
저장
        ↓
Reload하여 정상 저장 확인
```

최종적으로 다음 조건을 만족해야 합니다.

```
이미지와 TXT Pair 정상
Class 정상
BBox 위치 정상
누락 객체 없음
잘못된 BBox 없음
미해결 REVIEW 없음
Validation 오류 없음
```

## 3. FINAL 데이터는 이렇게 저장합니다

최종 검수가 끝난 데이터는 `data/final/`에 정리합니다.

```
data/
└── final/
    ├── images/
    │   ├── 250410_144403911987.jpg
    │   ├── ...
    │   └── 총 900장
    │
    └── labels/
        ├── 250410_144403911987.txt
        ├── ...
        └── 총 900개
```

즉,

```
FINAL Dataset
=
검수 완료 이미지 900장
+
검수 완료 YOLO TXT 900개
```

입니다.

이 데이터가 교과 8에서

```
FINAL Dataset
        ↓
Train / Validation / Test 구성
        ↓
YOLO Object Detection 학습
```

에 사용됩니다.

## 4. ==실제 제출==하는 3번 산출물

900장 전체 파일을 제출하는 것이 아니라, FINAL 데이터가 정상적으로 정리되었다는 폴더 구조·파일 수·대표 라벨 결과를 증빙으로 제출합니다.

대신 다음 증빙을 제출합니다.

```
1. final/ 전체 폴더 구조 캡처 1장

2. final/images/
   → 이미지 900장이 들어 있는 것이 보이도록 캡처

3. final/labels/
   → TXT 900개가 들어 있는 것이 보이도록 캡처

4. 대표 검수 완료 이미지 3~5장
   → BBox와 Class가 정상 표시된 화면

5. 대표 YOLO TXT 2~3개
   → 위 대표 이미지와 같은 이름의 TXT 내용
```

# 5. Class 기준서 — 작성 예시

Class 기준서는 라벨링할 때 **“이 객체를 몇 번 Class로 저장해야 하는가?”**를 팀원 모두가 같은 기준으로 판단하기 위한 문서입니다.

단순히 Class 번호와 이름만 적는 것이 아니라, 각 Class에 대해 다음을 정리합니다.

```
무엇을 이 Class로 보는가?
무엇은 포함하는가?
무엇은 제외하는가?
애매하면 어떻게 처리하는가?
```

### 실제 작성할 MD 파일 예시

파일명:

```
docs/class_guide.md
```

작성 예시는 다음과 같습니다.

```markdown
# Class Labeling Guide

## 공통 원칙

- 사용 Class: 0~6
- 판단이 명확한 객체만 해당 Class로 지정합니다.
- Class 판단이 어려우면 임의로 결정하지 않고 REVIEW 처리합니다.
- 김치 자체는 검출 대상 Class가 아닙니다.
- Class 4 고무장갑은 현재 프로젝트에서 사용하지 않습니다.

---

## Class 0 — 나뭇잎·종이류

### 대상
조각김치 사이에서 발견되는 나뭇잎 또는 종이 형태의 객체

### 포함
- 나뭇잎
- 잘린 잎 조각
- 종이 조각

### 제외
- 김치 잎
- 파
- 고추

### 애매한 경우
- 나뭇잎인지 김치 잎인지 명확하지 않으면 REVIEW

---

## Class 1 — 플라스틱류·돌·금속류

### 대상
플라스틱, 돌, 금속과 같이 제조 과정에서 이물로 판단되는 객체

### 포함
- 플라스틱 조각
- 돌
- 금속 조각

### 제외
- 나뭇가지
- 식물성 잎
- 파·고추

### 애매한 경우
- 재질을 이미지로 판단하기 어려우면 REVIEW

---

## Class 2 — 나뭇가지류

### 대상
막대 또는 가지 형태의 나무성 이물

### 포함
- 나뭇가지
- 작은 가지 조각
- 줄기 형태의 목질 이물

### 제외
- 파 줄기
- 고추 꼭지
- 일반 잎 조각

### 애매한 경우
- 나뭇가지와 채소 줄기의 구분이 어려우면 REVIEW

---

## Class 3 — 벌레류

### 대상
이미지에서 확인되는 벌레 또는 곤충 형태의 객체

### 포함
- 벌레
- 곤충 형태가 명확한 객체

### 제외
- 작은 검은 반점
- 김치 양념 덩어리
- 형태를 식별할 수 없는 이물

### 애매한 경우
- 벌레인지 단순 얼룩인지 판단하기 어려우면 REVIEW

---

## Class 4 — 고무장갑

### 현재 사용 여부
사용하지 않음

### 처리 기준
- 현재 교과 7 라벨링에서는 Class 4를 새로 생성하지 않습니다.
- 기존 TXT에서 Class 4가 발견되면 임의로 삭제하지 않고 REVIEW 처리합니다.

---

## Class 5 — 병해·갈변

### 대상
식재료에서 확인되는 병해 또는 갈변 형태

### 포함
- 갈색으로 변색된 부위
- 병해로 판단되는 이상 부위

### 제외
- 정상적인 김치 양념 색상
- 그림자
- 촬영 조명에 의한 색 변화

### 애매한 경우
- 실제 갈변인지 조명 차이인지 판단하기 어려우면 REVIEW

---

## Class 6 — 파·고추

### 대상
조각김치 이미지에서 검출 대상으로 지정된 파 또는 고추

### 포함
- 파 조각
- 고추 조각

### 제외
- 김치 잎
- 나뭇잎
- 나뭇가지

### 애매한 경우
- 파·고추와 다른 식물 조각을 구분하기 어려우면 REVIEW
```

### 작업 예시

예를 들어 이미지에서 다음 객체를 발견했다고 가정합니다.

```
이미지 확인

나뭇가지 형태 객체
        ↓
Class Guide 확인
        ↓
Class 2 — 나뭇가지류
        ↓
BBox 작성
        ↓
Class 2 지정
```

반대로 무엇인지 확실하지 않은 경우에는 이렇게 처리합니다.

```
작은 갈색 객체 발견
        ↓
나뭇가지인지
갈변인지 판단하기 어려움
        ↓
임의로 Class 지정하지 않음
        ↓
REVIEW 처리
        ↓
교차검수자가 최종 확인
```

Class 4가 발견된 경우도 마찬가지입니다.

```
기존 TXT에서 Class 4 발견
        ↓
현재 사용하지 않는 Class
        ↓
임의 삭제하지 않음
        ↓
REVIEW
        ↓
팀 기준에 따라 확인 후 처리
```

## 실제 제출하는 5번 산출물

다음 파일 하나를 작성하여 Git 저장소에 올립니다.

```
docs/class_guide.md
```

별도의 화면 캡처는 필요하지 않습니다.

> 5번 산출물의 핵심은 Class 이름을 외우는 것이 아니라, 팀원 모두가 같은 객체를 같은 Class로 판단할 수 있도록 기준을 문서로 남기는 것입니다.

# 6. BBox 기준서 — 작성 예시

BBox 기준서는 이미지 안의 객체를 **어디부터 어디까지 사각형으로 표시할 것인지**를 정하는 문서입니다.

작업자 마다 BBox 크기나 위치가 다르면 같은 객체를 라벨링해도 데이터 품질이 떨어질 수 있으므로, 팀에서 하나의 기준을 정해 사용합니다.

### 실제 작성할 MD 파일 예시

파일명:

```
docs/bbox_guide.md
```

작성 예시는 다음과 같습니다.

```markdown
# Bounding Box Labeling Guide

## 공통 원칙

- BBox는 객체의 실제 외곽에 최대한 밀착하여 작성합니다.
- 객체와 관계없는 배경을 지나치게 많이 포함하지 않습니다.
- 객체 일부가 가려져 있어도 보이는 범위를 기준으로 판단합니다.
- 하나의 BBox에는 가능한 한 하나의 객체만 포함합니다.
- 판단이 어려우면 임의로 처리하지 않고 REVIEW로 보냅니다.

---

## 1. 기본 BBox 작성 기준

객체의 외곽에 최대한 밀착하여 BBox를 작성합니다.

GOOD

┌─────────┐
│  객체   │
└─────────┘

BAD

┌──────────────────┐
│      객체        │
└──────────────────┘

BAD 예시는 객체 주변의 불필요한 배경이 너무 많이 포함된 경우입니다.

---

## 2. 객체가 이미지 경계에 걸린 경우

객체 일부가 이미지 밖으로 나간 경우에는
화면에 실제로 보이는 부분을 기준으로 BBox를 작성합니다.

예:

이미지 오른쪽 밖으로 일부가 잘린 나뭇가지
→ 보이는 부분까지만 BBox 작성

---

## 3. 객체가 서로 겹친 경우

두 객체가 서로 겹쳐 있어도
각각을 구분할 수 있다면 별도의 BBox를 작성합니다.

예:

나뭇가지 + 플라스틱 조각
→ 나뭇가지 BBox 1개
→ 플라스틱 BBox 1개

---

## 4. 객체가 매우 작은 경우

객체가 작더라도
Class를 식별할 수 있고 실제 검출 대상이면 BBox를 작성합니다.

단, 점이나 얼룩처럼 객체 여부를 판단하기 어려우면 REVIEW 처리합니다.

---

## 5. 객체 일부가 가려진 경우

객체 일부가 김치나 다른 객체에 가려져 있어도
Class를 식별할 수 있다면 보이는 범위를 기준으로 BBox를 작성합니다.

Class를 식별하기 어렵다면 REVIEW 처리합니다.

---

## 6. 하나의 객체를 여러 BBox로 나누지 않습니다

하나의 객체는 원칙적으로 하나의 BBox로 작성합니다.

예:

하나의 긴 나뭇가지
→ BBox 1개

잘린 것처럼 보인다고 해서
→ BBox 2개로 나누지 않음

단, 실제로 서로 떨어진 별개의 객체라면 각각 BBox를 작성합니다.

---

## 7. 판단이 어려운 경우

BBox 범위나 객체 구분이 애매하면 임의로 결정하지 않습니다.

Status = REVIEW

Reason 예:
- bbox_boundary_ambiguous
- object_separation_ambiguous
- too_small_to_identify
- occlusion_ambiguous
```

## 작업 예시

예를 들어 이미지에서 나뭇가지 하나를 발견했다고 가정합니다.

```
나뭇가지 확인
        ↓
객체 외곽 확인
        ↓
배경을 최소화하여
BBox 밀착 작성
        ↓
Class 2 지정
        ↓
저장
```

두 객체가 겹쳐 있는 경우에는 이렇게 처리합니다.

```
나뭇가지 + 플라스틱 조각
        ↓
두 객체를 각각 식별 가능
        ↓
BBox 2개 작성
        ↓
Class 2
Class 1
```

판단하기 어려운 경우에는:

```
작은 갈색 물체 발견
        ↓
객체인지 얼룩인지 불명확
        ↓
임의로 BBox 확정하지 않음
        ↓
REVIEW
        ↓
교차검수
```

## 실제 제출하는 6번 산출물

다음 파일 하나를 작성하여 Git 저장소에 올립니다.

```
docs/bbox_guide.md
```

별도의 화면 캡처는 필수가 아니나,

실제 팀에서 정한 GOOD / BAD 예시 이미지가 있다면 md문서 안에 1~2개 정도 추가해도 좋습니다.(커뮤니케이션을 위해서)

> 6번 산출물의 핵심은 “BBox를 어디까지 그릴 것인가?”를 팀원 모두가 같은 기준으로 판단할 수 있도록 문서화하는 것입니다.

# 7. Dataset Manifest — 작성 예시

Dataset Manifest는 **900장의 이미지가 현재 어떤 상태인지 한눈에 추적하기 위한 작업대장**입니다.

즉, 각 이미지마다

```
어느 데이터에서 왔는가?
누가 작업했는가?
현재 작업 상태는 무엇인가?
QA가 끝났는가?
REVIEW가 필요한 이유는 무엇인가?
```

를 기록합니다.

## 실제 작성할 파일

파일명은 다음처럼 작성합니다.

```
manifests/dataset_manifest.csv
```

CSV 파일은 Excel에서 열어도 되고, VS Code에서 열어도 됩니다.

### 실제 CSV 작성 예시

```
file_name,source_dataset,original_split,scene_type,worker,status,qa_status,review_reason
250410_144403911987.jpg,dataset2,train,kimchi_with_target,홍길동,DONE,PASS,
250410_144404112233.jpg,dataset2,train,normal_kimchi,김철수,DONE,PASS,
250410_144405445566.jpg,dataset1,train,object_only,이영자,REVIEW,WAIT,class_ambiguous
250410_144406778899.jpg,dataset2,validation,kimchi_with_target,박만수,EDITED,PASS,
250410_144407991122.jpg,dataset2,validation,other_review,홍길동,REVIEW,WAIT,bbox_boundary_ambiguous
```

### 각 항목은 무엇을 의미하나요?

|항목|의미|예시|
|---|---|---|
|`file_name`|이미지 파일명|`250410_144403911987.jpg`|
|`source_dataset`|원래 어느 데이터셋에서 왔는지|`dataset1`, `dataset2`|
|`original_split`|기존 train/validation 위치|`train`, `validation`|
|`scene_type`|이미지 전체 장면 유형|`kimchi_with_target`|
|`worker`|1차 검수 작업자|`홍길동`|
|`status`|현재 작업 상태|`DONE`, `EDITED`, `REVIEW`|
|`qa_status`|QA 완료 여부|`PASS`, `WAIT`|
|`review_reason`|REVIEW 이유|`class_ambiguous`|
원본 데이터의 출처와 기존 split 정보를 보존하는 것도 중요합니다

## 상태값은 이렇게 사용합니다

작업자 마다 임의로 여러 표현을 만들지 않도록 상태값은 간단히 통일하는 것이 좋습니다.

```
DONE
→ 기존 라벨이 맞아서 수정 없이 검수 완료

EDITED
→ 기존 라벨을 수정·추가·삭제한 뒤 저장 완료

REVIEW
→ 현재 판단이 어려워 추가 검수가 필요한 상태
```

QA 상태는 다음처럼 사용합니다.

```
PASS
→ 최종 검수 완료

WAIT
→ 아직 QA 또는 교차검수가 끝나지 않음
```

## scene_type은 무엇인가요?

`scene_type`은 YOLO Class가 아닙니다.

이미지 전체가 어떤 형태인지 기록하는 보조 정보입니다.

```
kimchi_with_target
→ 김치 + 검출 대상 객체

normal_kimchi
→ 정상 김치

object_only
→ 대상 객체만 단독으로 있는 이미지

other_review
→ 바로 분류하기 어려운 이미지
```

## 작업 예시

예를 들어 다음 행이 있다고 하겠습니다.

```
250410_144405445566.jpg,dataset1,train,object_only,이영자,REVIEW,WAIT,class_ambiguous
```

이 한 줄은 다음 의미입니다.

```
파일명
→ 250410_144405445566.jpg

원본 출처
→ dataset1 / train

이미지 유형
→ object_only

작업자
→ 이영자

현재 상태
→ REVIEW

QA 상태
→ WAIT

REVIEW 이유
→ Class 판단이 애매함
```

즉 이 이미지는 아직 FINAL에 넣으면 안 됩니다.

반대로 다음 행은:

```
250410_144403911987.jpg,dataset2,train,kimchi_with_target,홍길동,DONE,PASS,
```

다음 의미입니다.

```
검수 완료
+
QA 완료
+
REVIEW 없음
```

이므로 FINAL 대상으로 볼 수 있습니다.

## 작업 중에는 이렇게 사용합니다

```
900장 데이터
        ↓
각 이미지마다 Manifest 행 1개 생성
        ↓
작업자가 상태 기록
        ↓
REVIEW 데이터 표시
        ↓
교차검수
        ↓
QA PASS
        ↓
FINAL 데이터 확정
```

## 실제 제출하는 7번 산출물

작업후 다음 파일 하나를 제출합니다.

```
manifests/dataset_manifest.csv
```

Git 저장소에 올려도 됩니다.

단, CSV 안에는 이미지 파일 자체가 들어가는 것이 아니라 **파일명과 작업 상태 정보만 기록**되므로 데이터 보안문제는 거의 없습니다.

> 7번 산출물의 핵심은 900장의 이미지를 하나씩 열어보지 않아도, 어떤 파일이 완료되었고 어떤 파일이 REVIEW 상태인지 한눈에 확인할 수 있게 만드는 것입니다.

---

# 8. QA Summary — 작성 예시

QA Summary는 **900장의 라벨링 결과가 최종적으로 얼마나 정확하게 정리되었는지 요약하는 품질검사 결과 문서**입니다.

즉, 다음 내용을 한 문서에 정리합니다.

```
전체 900장 중
몇 장을 검사했는가?

자동 Validation에서
몇 건의 오류가 발견되었는가?

사람이 다시 확인해서
몇 건을 수정했는가?

최종적으로
FAIL이나 REVIEW가 남아 있는가?
```

### 실제 작성할 MD 파일 예시

파일명:

```
reports/qa_summary.md
```

작성 예시는 다음과 같습니다.

```markdown
# QA Summary

## 1. 전체 데이터

- 전체 이미지: 900장
- 전체 TXT: 900개
- 라벨 검수 완료: 900장

---

## 2. 자동 Validation 결과

- PASS: 887장
- FAIL: 13장

### 발견된 오류

- Class ID 오류: 3건
- BBox 이미지 경계 초과: 2건
- Empty TXT 확인 필요: 4건
- 좌표 형식 오류: 3건
- 이미지-TXT 파일명 불일치: 1건

총 오류: 13건

---

## 3. Human QA 결과

자동 Validation에서 발견된 13건을 사람이 다시 확인했습니다.

- 검토 대상: 13건
- 수정 완료: 13건
- 미해결: 0건

---

## 4. 최종 결과

- PASS: 900장
- FAIL: 0장
- REVIEW: 0장

최종 판정: QA 완료
```

### 자동 Validation은 무엇을 확인하나요?

프로그램이 기계적으로 찾을 수 있는 오류를 먼저 검사합니다.

예:

```
이미지와 TXT Pair가 있는가?
Class ID가 허용 범위인가?
YOLO 좌표가 0~1 범위인가?
BBox Width / Height가 정상인가?
파일 형식이 올바른가?
```

예를 들어 다음과 같은 TXT가 있다고 하겠습니다.

```
8 1.120 0.550 0.200 0.300
```

이번 프로젝트의 Class가 `0~6`인데 `8`이 들어 있고, `x_center`도 `1.120`으로 1을 넘었습니다.

따라서 Validation에서는:

```
Class ID 오류
+
좌표 범위 오류
→ FAIL
```

로 표시할 수 있습니다.

---

### Human QA는 무엇인가요?

자동검사만으로는 다음과 같은 문제를 판단하기 어렵습니다.

```
BBox가 실제 객체에 정확히 맞는가?
Class가 실제 객체와 맞는가?
빠진 객체는 없는가?
너무 큰 BBox가 그려져 있지는 않은가?
```

이런 부분은 사람이 직접 확인합니다.

예:

```
Validation
→ 형식상 문제 없음

하지만 사람이 이미지 확인
→ Class 2로 되어 있지만 실제로는 Class 6

수정
→ Class 6

재검수
→ PASS
```

즉,

```
자동 Validation
→ 형식과 좌표 검사

Human QA
→ 실제 이미지와 라벨 내용 검사
```

로 구분하면 됩니다.

---

### Empty TXT는 무조건 오류인가요?

아닙니다.

정상 김치처럼 검출 대상 객체가 없는 이미지라면 **빈 TXT가 정상일 수 있습니다.**

따라서:

```
Empty TXT 발견
        ↓
이미지 확인
        ↓
검출 대상 없음
→ 정상 PASS

검출 대상 있음
→ 누락 라벨
→ 수정
```

처럼 처리합니다.

---

### 작업 예시

예를 들어 Validation 결과가 다음과 같다고 하겠습니다.

```
전체 900장 검사

PASS 887
FAIL 13
```

그 다음 13건을 사람이 다시 확인합니다.

```
13건 Human QA
        ↓
Class 오류 수정       3건
BBox 오류 수정        2건
Empty TXT 확인        4건
좌표 오류 수정        3건
Pair 오류 수정        1건
        ↓
재검사
        ↓
13건 모두 PASS
```

최종적으로:

```
PASS   900
FAIL     0
REVIEW   0
```

가 되면 QA가 완료된 것입니다.

---

### 실제 제출하는 8번 산출물

다음 파일 하나를 작성하여 Git 저장소에 올립니다.

```
reports/qa_summary.md
```

별도의 화면 캡처는 필수가 아닙니다.

다만 Validation 프로그램에서 전체 결과가 표시되는 화면이 있다면 보조 증빙으로 1장 정도 추가할 수 있습니다.

> 8번 산출물의 핵심은 “900장을 모두 봤다”가 아니라, 어떤 오류가 발견되었고 그것을 어떻게 처리해서 최종적으로 오류와 REVIEW를 0건으로 만들었는지를 기록하는 것입니다.

Test Report는 **팀별로 만든 라벨링 프로그램이 실제 900장 작업에 사용해도 문제가 없는지 단계별로 시험한 결과를 기록하는 문서**입니다.

쉽게 말하면 다음 질문에 답하는 문서입니다.

```
이미지가 정상적으로 열리는가?

---

### 1. Golden Test는 무엇인가요?

처음부터 900장 전체를 작업하지 않습니다.

먼저 **20장 정도의 실제 데이터**로 프로그램의 핵심 기능을 확인합니다.

```
실제 이미지 20장
    ↓
이미지 Load
    ↓
YOLO TXT Load
    ↓
BBox 표시
    ↓
BBox 수정
    ↓
저장
    ↓
Reload
    ↓
Validation
```

여기에서 오류가 발생하면 900장 작업을 시작하지 않고 먼저 프로그램을 수정합니다.

즉 Golden Test의 목적은:

> **“기본 기능이 정상적으로 연결되어 있는가?”**

를 확인하는 것입니다.

---

## 2. Pilot Test는 무엇인가요?

Golden Test가 통과했다고 바로 900장을 작업하지 않습니다.

실제 데이터 **20~50장 정도**를 이용하여 작업 흐름 전체를 한 번 더 시험합니다. 
교과 7 가이드에서도 본 작업 전 Pilot Test를 20~50장 규모로 수행하도록 구성했습니다. 

예:

```
50장 작업

47장 정상
3장 문제 발견
        ↓
문제 원인 확인
        ↓
프로그램 수정
        ↓
3장 다시 테스트
        ↓
50장 모두 PASS
```

여기에서 중요한 것은 처음부터 전부 PASS가 나오는 것이 아닙니다.

**오류를 발견하고 수정한 과정까지 Test Report에 남기는 것**이 중요합니다.

---

### FAIL 기록은 어떻게 작성하나요?

복잡한 보고서를 작성할 필요는 없습니다.

다음 네 가지 정도만 기록하면 됩니다.

```
무슨 문제가 발생했는가?
        ↓
원인이 무엇이었는가?
        ↓
어떻게 수정했는가?
        ↓
다시 실행했을 때 PASS했는가?
```

예:

```
FAIL-01

문제
→ Zoom 상태에서 BBox 위치가 어긋남

원인
→ 화면 좌표를 원본 좌표로 변환하지 않음

수정
→ Zoom Scale을 반영한 좌표변환 적용

Retest
→ PASS
```

이 정도면 충분합니다.

---

### 3. Acceptance Test는 무엇인가요?

마지막 시험입니다.

900장의 작업이 끝난 뒤 **“이제 이 프로그램과 데이터 결과를 최종 산출물로 인정해도 되는가?”**를 확인합니다.

```
900장 작업 완료
        ↓
Critical Error 확인
        ↓
미처리 REVIEW 확인
        ↓
Validation 확인
        ↓
저장 / Reload 확인
        ↓
모두 정상
        ↓
ACCEPTED
```

여기서 `Critical Error`는 프로젝트 진행에 치명적인 문제를 의미합니다.

예:

```
저장이 안 됨
TXT가 손상됨
저장 후 BBox 위치가 달라짐
이미지와 TXT Pair가 깨짐
프로그램이 반복적으로 종료됨
```

이런 문제가 0건이어야 최종적으로 `ACCEPTED`로 판단합니다.

---

### QA Summary와 Test Report는 무엇이 다른가요?

이 부분은 초보자가 가장 헷갈릴 수 있으므로 명확하게 구분해 이해 합니다.

```
8번 QA Summary
→ 만들어진 라벨 데이터가 올바른가?

9번 Test Report
→ 그 라벨을 만들고 수정하는 프로그램이 제대로 동작하는가?
```

예를 들어:

```
BBox Class가 실제 객체와 다름
→ 데이터 문제
→ QA Summary

Zoom 후 저장하면 BBox 위치가 달라짐
→ 프로그램 문제
→ Test Report
```

### ==실제 제출==하는 9번 산출물

다음 파일 하나를 작성하여 Git 저장소에 올립니다.

```
reports/test_report.md
```

문서 안에는 최소한 다음 세 단계의 결과가 들어가면 됩니다.

```
1. Golden Test
   → 소수 데이터로 핵심 기능 확인

2. Pilot Test

> 9번 산출물의 핵심은 “프로그램이 실행됐다”가 아니라, 작은 데이터부터 실제 900장 작업까지 단계적으로 시험하고, 발견된 오류를 수정한 뒤 최종적으로 안정적인 상태임을 확인했다는 기록입니다.

## 6. 기본 사용 순서

1. 이미지 폴더를 엽니다.
2. 이미지와 기존 YOLO TXT가 자동으로 Load되는지 확인합니다.
3. 기존 BBox와 Class를 확인합니다.
4. 잘못된 BBox는 수정합니다.
5. 누락된 객체는 새로 추가합니다.
6. 잘못된 객체는 삭제합니다.
7. 판단이 어려운 경우 REVIEW로 기록합니다.
8. 수정 결과를 저장합니다.
9. 다시 Load하여 정상적으로 복원되는지 확인합니다.
10. Validation을 실행합니다.
