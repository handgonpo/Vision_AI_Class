## 0. 이 수업에서 구현할 최종 동작

원본의 학습 목표는 유지합니다. **04의 동기식 Create/Update**를 **06의 Celery 비동기식 Create/Update**로 바꾸고, 기존 `POST /predict/`는 동기식 비교용으로 남겨둡니다. Redis를 큐(Broker)와 캐시(Cache)로 활용하고, SQLAlchemy DB에 처리 상태를 기록합니다.

```text
[동기: HTTP 요청 안에서 완료]
브라우저 POST /predict/ → FastAPI → 모델 로딩·추론 → HTML 결과 (응답 대기)

[비동기: HTTP 요청은 접수만]
브라우저 POST /new/ → FastAPI → SQLite에 PENDING 저장 → Celery.delay(id,revision)
                                               ↓
                                        Redis DB2 (Broker)
                                               ↓
                                        Celery Worker
                                               ↓
                                   Redis DB1 Cache HIT/MISS
                                               ↓ MISS
                                        Hugging Face 추론
                                               ↓
                                     SQLite에 DONE 저장
                                               ↓
                                 상세 화면 2초마다 상태 조회
```

기존 `Django → Redis → Celery`에서 **웹 프레임워크만 FastAPI로 바뀌고**, Redis와 Celery의 역할은 같습니다. 이때 FastAPI의 `async def`와 Celery의 비동기 작업 큐를 혼동하면 안 됩니다. 수업에서는 **별도 Worker 프로세스에서 작업을 수행하기 때문에 HTTP 요청이 먼저 끝나는 구조**를 학습합니다.

## 2. Docker Desktop 처음 설치부터 Redis 실행까지

### 2-1. Windows PowerShell에서 WSL2 확인 (Docker 없을 때)

```powershell
wsl --status
wsl -l -v
wsl --update
```

Ubuntu가 `VERSION 2`여야 합니다. 없으면 관리자 PowerShell에서 `wsl --install -d Ubuntu-24.04`를 수행하고 재부팅·Ubuntu 계정 초기화를 완료합니다. 이미 WSL2를 사용한다면 재설치하지 않습니다.

### 2-2. Docker Desktop 설치 및 WSL 연동

1. **https://www.docker.com/products/docker-desktop/** 접속 후 Windows용 Docker Desktop 설치 파일을 받습니다.
2. 설치 프로그램을 실행하고 WSL2 백엔드 사용 옵션을 유지합니다. 설치 완료 후 재부팅이 요구될 수 있습니다.
3. **Docker Desktop을 실제로 실행**합니다. 단지 설치만 한 상태에서는 `docker ps`가 실패할 수 있습니다.
4. Settings → General에서 WSL 2 engine을 확인합니다(버전에 따라 기본값이거나 메뉴에서 숨겨질 수 있음).
5. Settings → Resources → WSL Integration에서 `Ubuntu-24.04`를 선택하고 Apply & Restart 합니다.
6. Ubuntu/VS Code 터미널에서 `docker --version`, `docker compose version`, `docker info`, `docker run --rm hello-world`를 확인합니다.

### 2-4. Redis를 위한 `compose.yaml` 생성

**왜 바로 `docker run`을 쓰지 않을까요?** 같은 옵션으로 다시 실행하기 쉽도록 Compose 파일에 포트·볼륨·헬스체크를 저장합니다. Docker 자체는 한 번만 설치합니다.

**`compose.yaml` — 신규 생성**

```yaml

# ============================================================
# ① Docker Compose 서비스 정의
# ============================================================
# services:
# Docker Compose가 관리할 컨테이너들을 정의하는 영역
#
# 현재 실습에서는 Redis 서비스 하나만 실행합니다.
# FastAPI와 Celery Worker는 별도 터미널에서 실행합니다.

services:

  # ==========================================================
  # ② Redis 서비스 이름 지정
  # ==========================================================
  # redis : Docker Compose에서 사용하는 서비스 이름
  #
  # 이후 docker compose 명령으로
  # redis 서비스를 선택하여 관리할 수 있습니다.

  redis:

    # --------------------------------------------------------
    # ③ Redis Docker 이미지 지정
    # --------------------------------------------------------
    # image : 컨테이너를 생성할 때 사용할 이미지
    #
    # redis:7-alpine
    # : Redis 7 버전의 Alpine Linux 기반 이미지
    #
    # 이미지가 로컬에 없으면 Docker가 다운로드합니다.
    # 별도의 Dockerfile을 작성할 필요는 없습니다.

    image: redis:7-alpine


    # --------------------------------------------------------
    # ④ Redis 컨테이너 이름 지정
    # --------------------------------------------------------
    # container_name :
    # 실제 생성되는 컨테이너의 이름을 지정합니다.
    #
    # 예: docker logs sentiment-redis

    container_name: sentiment-redis


    # --------------------------------------------------------
    # ⑤ 컨테이너 재시작 정책 설정
    # --------------------------------------------------------
    # restart: unless-stopped
    #
    # Redis 컨테이너가 종료되면
    # Docker가 자동 재시작하도록 설정합니다.
    #
    # 단, 사용자가 명시적으로 중지한 경우에는
    # 자동으로 다시 시작하지 않습니다.

    restart: unless-stopped


    # --------------------------------------------------------
    # ⑥ 포트 연결 설정
    # --------------------------------------------------------
    # ports : 로컬 PC와 컨테이너의 포트를 연결
    #
    # 127.0.0.1 : 로컬 호스트에서만 접근 허용
    # 6380      : 로컬 PC에서 사용하는 포트
    # 6379      : Redis 컨테이너 내부 포트
    #
    # FastAPI와 Celery는 다음 주소로 Redis에 접근합니다.
    #
    # redis://127.0.0.1:6380

    ports:
      - "127.0.0.1:6380:6379"


    # --------------------------------------------------------
    # ⑦ Redis 데이터 저장 공간 연결
    # --------------------------------------------------------
    # volumes :
    # Docker 볼륨을 컨테이너 내부 폴더와 연결합니다.
    #
    # redis_data : Docker가 관리하는 볼륨 이름
    # /data      : Redis 컨테이너 내부 저장 경로
    #
    # 컨테이너를 삭제하고 다시 생성해도
    # 볼륨이 남아 있으면 저장 데이터를 유지할 수 있습니다.

    volumes:
      - redis_data:/data


    # --------------------------------------------------------
    # ⑧ Redis 서버 실행 명령 설정
    # --------------------------------------------------------
    # command : 컨테이너 시작 시 실행할 명령
    #
    # redis-server :
    # Redis 서버 실행
    #
    # --appendonly yes :
    # AOF(Append Only File) 영속성 기능 활성화
    #
    # Redis의 데이터 변경 내용을 파일에 기록하여
    # 재시작 후 데이터를 복구할 수 있도록 합니다.

    command: ["redis-server", "--appendonly", "yes"]


    # --------------------------------------------------------
    # ⑨ Redis 서버 정상 동작 검사 설정
    # --------------------------------------------------------
    # healthcheck :
    # 컨테이너 내부 서비스의 정상 동작 여부를 검사
    #
    # redis-cli ping :
    # Redis 서버에 PING 명령을 보내 상태 확인
    #
    # 정상 응답 : PONG

    healthcheck:
      test: ["CMD", "redis-cli", "ping"]


      # ------------------------------------------------------
      # ⑩ 상태 검사 주기 및 실패 기준 설정
      # ------------------------------------------------------
      # interval: 5s
      # : 5초 간격으로 상태 검사
      #
      # timeout: 3s
      # : 검사 명령이 3초 안에 끝나지 않으면 실패
      #
      # retries: 10
      # : 연속 10회 실패하면 unhealthy 상태로 판단
      #
      # 주의:
      # unhealthy 상태가 되었다고 해서
      # Redis를 자동 재시작하는 설정은 아닙니다.

      interval: 5s
      timeout: 3s
      retries: 10


# ============================================================
# ⑪ Docker 볼륨 생성 및 관리 설정
# ============================================================
# services 내부의 volumes와는 역할이 다릅니다.
#
# 위의 redis_data:/data
# : Redis 컨테이너가 사용할 볼륨 연결
#
# 아래의 redis_data:
# : Docker Compose에서 해당 이름의 볼륨을 정의
#
# 저장된 데이터는 일반적인 컨테이너 재생성 시에도
# 볼륨이 유지되는 동안 보존될 수 있습니다.

volumes:
  redis_data:
```

## 3. Python 가상환경과 Redis/Celery 패키지 설치

Docker는 Redis 서버를 실행하는 것이고 Python 패키지를 설치하는 곳이 아닙니다. FastAPI와 Celery는 기존 Ubuntu `.venv`에서 실행할 예정입니다.

```bash
cd ~/fastapi_sentiment
source .venv/bin/activate
uv pip install "celery[redis]>=5.4,<6" "redis>=5,<7"
uv pip freeze > requirements.txt
python -c "import celery, redis; print('celery', celery.__version__, 'redis', redis.__version__)"
```

**모델은 웹 서버와 Celery Worker가 서로 다른 프로세스이므로 각자 메모리에 로딩할 수 있습니다.** 동기 처리(`/predict/`) 시 FastAPI 프로세스가 모델을, 비동기 처리(`/new/`) 시 Celery Worker가 모델을 사용합니다. 메모리가 부족하면 동기/비동기 측정을 별도 순서로 진행하세요.

## 5. Redis의 세 가지 용도를 설정합니다

`settings.py`는 **프로그램에서 공통으로 사용하는 설정값을 모아 관리하는 파일**입니다. 서버 주소나 포트가 변경되더라도 이 파일에서 설정을 관리할 수 있습니다.

이번 실습에서는 Docker로 실행한 Redis 서버를 다음 세 가지 용도로 사용합니다.

|구분|역할|
|---|---|
|**Cache (DB 1)**|이전 AI 분석 결과를 저장하고 재사용|
|**Broker (DB 2)**|FastAPI가 요청한 작업을 Celery Worker에 전달|
|**Result Backend (DB 3)**|Celery 작업의 상태와 반환 결과 저장|

DB 1·2·3은 서로 다른 서버가 아니라 **하나의 Redis 서버에서 데이터를 논리적으로 구분하는 번호**입니다.

이제 `sentiment/settings.py`에 각 용도의 Redis 연결 주소를 설정합니다. 이 파일은 Redis를 실행하는 것이 아니라, **FastAPI와 Celery가 Redis에 연결할 때 사용할 주소를 정의하는 파일**입니다.

`**sentiment/settings.py**` **— 신규 생성**

```python
import os

# FastAPI와 Celery Worker를 모두 호스트/WSL 가상환경에서 실행합니다.
# Docker에는 Redis만 띄우므로 localhost:6380을 공통으로 사용합니다.
REDIS_CACHE_URL = os.getenv("REDIS_CACHE_URL", "redis://127.0.0.1:6380/1")
CELERY_BROKER_URL = os.getenv("CELERY_BROKER_URL", "redis://127.0.0.1:6380/2")
CELERY_RESULT_BACKEND = os.getenv("CELERY_RESULT_BACKEND", "redis://127.0.0.1:6380/3")
CACHE_SECONDS = 600
```

| Redis DB | 용도 | 연결 설정 |
|---|---|---|
| `/1` | 감정분석 결과 캐시 | `REDIS_CACHE_URL` |
| `/2` | Celery 작업 대기열 Broker | `CELERY_BROKER_URL` |
| `/3` | Celery 결과 backend | `CELERY_RESULT_BACKEND` |

Redis DB 번호는 물리적으로 완전히 분리된 독립 서버가 아니라 하나의 Redis 인스턴스에 있는 논리 공간입니다.

## 6. Celery App 연결 파일

Django의 `mysite/celery.py`, `DJANGO_SETTINGS_MODULE`, `app.autodiscover_tasks()` 패턴을 제거하고 FastAPI에서 동작하도록 Celery 인스턴스를 직접 만듭니다.

아래 코드의 처리 과정

```text
Celery 객체 생성 → Broker URL(6379/2) 설정
→ 결과 저장소(6379/3) 설정 → JSON 직렬화 설정
→ sentiment.tasks 모듈을 Worker에 등록
```

**`sentiment/celery_app.py` — 신규 생성**

```python

# ============================================================
# ① Celery 라이브러리 가져오기
# ============================================================
# Celery : 시간이 걸리는 작업을 별도 Worker에서
#          비동기적으로 처리할 수 있도록 도와주는 도구

from celery import Celery


# ============================================================
# ② Redis 연결 주소 가져오기
# ============================================================
# settings.py에서 미리 설정한 Redis 주소를 가져옵니다.
#
# CELERY_BROKER_URL
# : 처리할 작업을 전달하는 Redis 주소 (DB 2)
#
# CELERY_RESULT_BACKEND
# : 작업 상태와 결과를 저장하는 Redis 주소 (DB 3)

from .settings import CELERY_BROKER_URL, CELERY_RESULT_BACKEND


# ============================================================
# ③ Celery 애플리케이션 생성
# ============================================================
# Celery("sentiment") : Celery 애플리케이션 이름 지정
#
# broker  : 비동기 작업을 전달할 Redis 연결 주소
# backend : 작업 상태와 결과를 저장할 Redis 연결 주소
# include : Worker가 불러올 작업 함수 파일
#
# sentiment.tasks는 이후 작성할 tasks.py를 의미합니다.
#
# 주의:
# 여기서는 Celery 실행 환경만 설정합니다.
# 실제 Worker는 별도 명령어로 실행해야 합니다.

celery_app = Celery(
    "sentiment",
    broker=CELERY_BROKER_URL,
    backend=CELERY_RESULT_BACKEND,
    include=["sentiment.tasks"],
)


# ============================================================
# ④ 작업 데이터와 결과의 형식 설정
# ============================================================
# conf.update() : Celery의 세부 설정을 적용하는 메서드
#
# task_serializer="json"
# : 작업을 전달할 때 데이터를 JSON으로 변환
#
# accept_content=["json"]
# : JSON 형식의 작업 메시지만 허용
#
# result_serializer="json"
# : 작업 결과도 JSON으로 변환하여 저장

celery_app.conf.update(
    task_serializer="json",
    accept_content=["json"],
    result_serializer="json",

    # --------------------------------------------------------
    # ⑤ Celery 시간대 설정
    # --------------------------------------------------------
    # Asia/Seoul : 한국 시간대 설정
    #
    # 주로 작업 스케줄 등의 시간 처리에 사용합니다.

    timezone="Asia/Seoul",

    # --------------------------------------------------------
    # ⑥ 작업 시작 상태 추적
    # --------------------------------------------------------
    # task_track_started=True
    #
    # Worker가 작업을 시작하면
    # STARTED 상태를 기록할 수 있도록 설정합니다.
    #
    # 예:
    # PENDING → STARTED → SUCCESS

    task_track_started=True,

    # --------------------------------------------------------
    # ⑦ Redis 연결 실패 시 재시도 설정
    # --------------------------------------------------------
    # broker_connection_retry_on_startup=True
    #
    # Celery Worker 시작 시 Redis에 연결하지 못하면
    # 연결을 다시 시도하도록 설정합니다.
    #
    # 재시도 횟수 등은 Celery의 다른 설정에도 영향을 받습니다.

    broker_connection_retry_on_startup=True,
)
```

## 7. 04 DB를 보존하면서 비동기 상태 필드 추가

원본의 `is_analyzing` 의미를 그대로 유지합니다. 추가로 `status`(PENDING / DONE / FAILED), `revision`(수정 차수), `error_message`(실패 표시)를 기록해 화면에서 상태를 읽을 수 있게 합니다.

**`sentiment/models.py` — 전체 교체**

```python

# ============================================================
# ① [04 유지] 날짜와 시간 처리 라이브러리 가져오기
# ============================================================
# datetime : 날짜와 시간을 표현하는 클래스
# timezone : 시간대 정보 설정
#
# timezone.utc : UTC(세계 표준시) 사용

from datetime import datetime, timezone


# ============================================================
# ② [06 수정] SQLAlchemy 컬럼 타입 가져오기
# ============================================================
# [04 기존]
# DateTime : 날짜 및 시간
# Float    : 실수
# Integer  : 정수
# String   : 문자열
# Text     : 긴 문자열
#
# [06 신규]
# Boolean  : 참(True) / 거짓(False) 저장
#
# 비동기 AI 분석이 진행 중인지 기록하기 위해
# Boolean 타입을 추가했습니다.

from sqlalchemy import (
    DateTime,
    Float,
    Integer,
    String,
    Text,
    Boolean
)


# ============================================================
# ③ [04 유지] ORM 모델 관련 기능 가져오기
# ============================================================
# Mapped        : Python 속성과 DB 컬럼의 타입 연결
# mapped_column : 실제 DB 컬럼의 상세 설정

from sqlalchemy.orm import Mapped, mapped_column


# ============================================================
# ④ [04 유지] 공통 ORM 부모 클래스 가져오기
# ============================================================
# db.py에서 정의한 Base를 가져옵니다.
#
# Base를 상속하면 SQLAlchemy ORM 모델을 만들 수 있습니다.

from .db import Base


# ============================================================
# ⑤ [04 유지] TextItem 모델과 테이블 이름 정의
# ============================================================
# TextItem : 감정분석 데이터를 관리하는 ORM 모델
#
# __tablename__ = "text_items"
# : 실제 SQLite에 생성되는 테이블 이름
#
# 06에서도 기존 text_items 테이블을 그대로 사용합니다.
# 새 테이블을 만드는 것이 아니라 컬럼을 추가합니다.

class TextItem(Base):

    __tablename__ = "text_items"


    # --------------------------------------------------------
    # ⑥ [04 유지] id : 데이터 고유번호
    # --------------------------------------------------------
    # Integer          : 정수형
    # primary_key=True : 기본키(PK)
    #
    # 각 감정분석 데이터를 구별하는 고유번호입니다.

    id: Mapped[int] = mapped_column(
        Integer,
        primary_key=True
    )


    # --------------------------------------------------------
    # ⑦ [04 유지] text : 사용자가 입력한 문장
    # --------------------------------------------------------
    # Text           : 긴 문자열 저장
    # nullable=False : NULL 저장 불가
    #
    # 예: "오늘 정말 기분이 좋아요."

    text: Mapped[str] = mapped_column(
        Text,
        nullable=False
    )


    # --------------------------------------------------------
    # ⑧ [04 유지] label : AI 감정분석 결과
    # --------------------------------------------------------
    # String(50)     : 문자열 컬럼
    # default=""     : 기본값은 빈 문자열
    # nullable=False : NULL 저장 불가
    #
    # 예: Positive, Negative, Neutral
    #
    # 06에서는 AI 분석이 완료되기 전까지
    # label이 빈 문자열일 수 있습니다.

    label: Mapped[str] = mapped_column(
        String(50),
        default="",
        nullable=False
    )


    # --------------------------------------------------------
    # ⑨ [04 유지] score : AI 감정분석 점수
    # --------------------------------------------------------
    # Float         : 실수형
    # float | None  : 실수 또는 None
    # nullable=True : NULL 허용
    #
    # 예: 0.95
    #
    # 06에서는 AI 분석이 완료되기 전까지
    # score가 None일 수 있습니다.

    score: Mapped[float | None] = mapped_column(
        Float,
        nullable=True
    )


    # --------------------------------------------------------
    # ⑩ [04 유지] created_at : 데이터 생성 시각
    # --------------------------------------------------------
    # DateTime(timezone=True) : 날짜와 시간 타입
    # datetime.now(timezone.utc) : 현재 UTC 시각
    #
    # 데이터가 처음 저장되는 시각을 기록합니다.

    created_at: Mapped[datetime] = mapped_column(
        DateTime(timezone=True),
        default=lambda: datetime.now(timezone.utc)
    )


    # --------------------------------------------------------
    # ⑪ [06 신규] is_analyzing : AI 분석 진행 여부
    # --------------------------------------------------------
    # Boolean       : True 또는 False
    # default=False : 기본값은 False
    # nullable=False: NULL 저장 불가
    #
    # True  : AI 분석 작업이 진행 중이거나 대기 중
    # False : 현재 분석 중인 작업이 없음
    #
    # 06의 router.py에서는 비동기 작업 등록 시
    # True로 설정하고, 작업 완료 시 False로 변경합니다.

    is_analyzing: Mapped[bool] = mapped_column(
        Boolean,
        default=False,
        nullable=False
    )


    # --------------------------------------------------------
    # ⑫ [06 신규] status : AI 작업의 처리 상태
    # --------------------------------------------------------
    # String(20)    : 상태 문자열 저장
    # default="DONE": 기본값은 DONE
    #
    # 예:
    # PENDING : 작업 등록 후 처리 대기
    # DONE    : AI 분석 완료
    # FAILED  : AI 분석 실패
    #
    # 초기값 DONE은 기존 동기식 완료 데이터와
    # 호환하기 위한 기본 설정입니다.
    #
    # 새 비동기 작업에서는 router.py에서
    # PENDING 상태를 명시적으로 설정합니다.

    status: Mapped[str] = mapped_column(
        String(20),
        default="DONE",
        nullable=False
    )


    # --------------------------------------------------------
    # ⑬ [06 신규] revision : 데이터 수정 버전
    # --------------------------------------------------------
    # Integer       : 정수형
    # default=1     : 최초 버전은 1
    # nullable=False : NULL 저장 불가
    #
    # 예:
    # 최초 작성 → revision = 1
    # 첫 수정   → revision = 2
    # 두 번째 수정 → revision = 3
    #
    # 비동기 AI 작업이 여러 개 발생할 때
    # 이전 작업의 결과가 최신 데이터를 덮어쓰지 않도록
    # 버전을 비교하는 데 사용할 수 있습니다.
    #
    # 실제 버전 증가와 비교는 router.py와
    # tasks.py의 코드에서 처리해야 합니다.

    revision: Mapped[int] = mapped_column(
        Integer,
        default=1,
        nullable=False
    )


    # --------------------------------------------------------
    # ⑭ [06 신규] error_message : AI 분석 오류 메시지
    # --------------------------------------------------------
    # String(255)   : 오류 내용을 저장할 문자열 컬럼
    # default=""    : 기본값은 빈 문자열
    # nullable=False : NULL 저장 불가
    #
    # AI 분석이 실패했을 때 오류 내용을 저장합니다.
    #
    # 예: "모델 추론 중 오류가 발생했습니다."
    #
    # 정상적으로 처리된 경우에는 빈 문자열을 사용합니다.

    error_message: Mapped[str] = mapped_column(
        String(255),
        default="",
        nullable=False
    )

```

## 기존 SQLite 테이블에 새로운 컬럼을 추가합니다 — `migrate_06.py`

### 마이그레이션(Migration)이란 무엇인가요?

앞의 04 실습에서는 SQLAlchemy의 `models.py`에 Python 코드로 테이블 구조를 정의했습니다.

이처럼 SQL문을 직접 작성하지 않고 Python 클래스로 데이터베이스 테이블을 다루는 방식을 **ORM(Object Relational Mapping)**이라고 합니다.

그런데 06 실습에서는 Celery 비동기 작업의 진행 상태를 저장해야 하므로 기존 `text_items` 테이블에 네 개의 컬럼을 추가해야 합니다.

|새로 추가할 컬럼|역할|
|---|---|
|`is_analyzing`|AI 분석이 대기 또는 진행 중인지 확인|
|`status`|AI 작업의 대기·완료·실패 상태 저장|
|`revision`|데이터 수정 버전 관리|
|`error_message`|AI 분석 실패 시 오류 내용 저장|

**이처럼 기존 데이터베이스의 테이블 구조를 변경하는 작업을 마이그레이션(Migration)이라고 합니다.**

### SQL로 배웠던 내용을 Python으로 처리합니다

SQL에서는 기존 테이블에 새로운 컬럼을 추가할 때 `ALTER TABLE`을 사용했습니다.

예를 들어 다음과 같이 작성할 수 있습니다.

```
ALTER TABLE text_items
ADD COLUMN status VARCHAR(20) NOT NULL DEFAULT 'DONE';
```

SQLAlchemy에서도 `models.py`에 컬럼을 추가할 수 있지만, **Python 모델을 수정했다고 실제 SQLite 테이블이 자동으로 변경되지는 않습니다.**

Django를 사용한다면 `makemigrations`로 변경 내용을 기록한 후 `migrate`로 데이터베이스에 적용할 수 있습니다.

하지만 현재 FastAPI + SQLAlchemy 실습에는 Django의 마이그레이션 명령어가 없습니다.

따라서 이번에는 `migrate_06.py`라는 Python 파일을 만들어 **SQLAlchemy로 기존 테이블을 확인하고, 필요한** `**ALTER TABLE**` **명령을 직접 실행**하겠습니다.

### `migrate_06.py`는 어떤 작업을 하나요?

이 파일은 기존 SQLite 데이터를 유지하면서 06 실습에 필요한 컬럼을 추가합니다.

```
04 실습에서 생성한 SQLite
       sentiment.db
             ↓
    text_items 테이블 확인
             ↓
   기존 컬럼 목록 가져오기
             ↓
  새로 필요한 4개 컬럼 검사
             ↓
    컬럼이 이미 있는가?
        │         │
       있음      없음
        │         │
        ▼         ▼
       유지    ALTER TABLE 실행
        │         │
        └────┬────┘
             ▼
     06 실습 DB 구조 준비
```

이미 존재하는 컬럼은 다시 만들지 않으므로 같은 코드를 반복 실행해도 컬럼이 중복 추가되지 않도록 작성했습니다.

이 작업이 완료되면 04에서 저장한 감정분석 데이터를 유지하면서, 06에서 필요한 **AI 작업 상태·수정 버전·오류 정보**까지 저장할 수 있게 됩니다.

### 이제 마이그레이션 코드를 작성합니다

`migrate_06.py`는 기존 테이블을 삭제하고 새로 만드는 파일이 아닙니다. **현재 테이블에 부족한 컬럼이 있는지 검사하고 필요한 컬럼만 추가하는 교육용 마이그레이션 파일**입니다.

실무에서는 Alembic 같은 마이그레이션 도구를 사용하지만, 이번 실습에서는 SQL의 `ALTER TABLE`이 Python 코드로 어떻게 실행되는지 이해하기 위해 직접 작성합니다.

**`sentiment/migrate_06.py` — 신규 생성**

```python
"""04단계 SQLite 테이블을 06단계로 확장합니다 (교육용, 반복 실행 가능)."""
from sqlalchemy import inspect, text
from .db import Base, engine
from . import models

NEW_COLUMNS = {
    'is_analyzing': 'BOOLEAN NOT NULL DEFAULT 0',
    'status': "VARCHAR(20) NOT NULL DEFAULT 'DONE'",
    'revision': 'INTEGER NOT NULL DEFAULT 1',
    'error_message': "VARCHAR(255) NOT NULL DEFAULT ''",
}

def upgrade_schema():
    Base.metadata.create_all(bind=engine)
    existing = {col['name'] for col in inspect(engine).get_columns('text_items')}
    with engine.begin() as connection:
        for column, definition in NEW_COLUMNS.items():
            if column not in existing:
                connection.execute(text(f'ALTER TABLE text_items ADD COLUMN {column} {definition}'))
                print(f'added: {column}')
    print('06 DB schema ready')

if __name__ == '__main__':
    upgrade_schema()
```


다음 명령을 한 번 실행합니다. 여러 번 실행해도 이미 있는 컬럼을 중복 추가하지 않습니다.

```bash
python -m sentiment.migrate_06
```

`04` 데이터를 버리고 새 SQLite DB를 만드는 방법은 가장 쉬워 보이지만, 이전 수업의 기록을 지우므로 이번 교재에서는 권장하지 않습니다. 이 스크립트는 특정한 교육용 필드 추가만 처리합니다. 실무에서는 **Alembic** 마이그레이션으로 관리합니다.

## 8. Redis 캐시가 들어간 서비스 함수

`services.py`의 역할은 04와 같습니다. **입력 → 처리 → 결과**만 담당하고 HTML·DB 저장을 직접 수행하지 않습니다.

**서비스 코드의 사고 패턴 (원본 학습 개념 유지)**

```text
1) 입력 정리 / 검사
2) 캐시 조회: 있으면 곧바로 반환 (Cache HIT)
3) 캐시에 없으면 get_classifier() 로딩 후 HF 추론 (Cache MISS)
4) 출력 구조를 label/score로 정리
5) 새 결과를 Redis에 TTL 10분으로 저장
6) 결과 반환
```

**`sentiment/services.py` — 전체 교체**

```python
import hashlib
import json
from redis import Redis
from .hf_model import MODEL_ID, get_classifier, normalize_prediction
from .settings import REDIS_CACHE_URL, CACHE_SECONDS

# Redis 연결은 Python 프로세스별로 생성합니다. 서버 실행시 연결을 강제하지 않습니다.
redis_cache = Redis.from_url(REDIS_CACHE_URL, decode_responses=True, socket_connect_timeout=3)

def cache_key(text: str) -> str:
    key_input = (MODEL_ID + "\n" + text.strip()).encode("utf-8")
    return "sentiment:analysis:" + hashlib.sha256(key_input).hexdigest()

def analyze_text(text: str, use_cache: bool = False) -> dict:
    """동기 API에선 use_cache=False, Celery 워커에선 True로 실행합니다."""
    cleaned = (text or "").strip()
    if not cleaned:
        raise ValueError("빈 문장은 분석할 수 없습니다.")
    key = cache_key(cleaned)
    if use_cache:
        cached = redis_cache.get(key)
        if cached is not None:
            return json.loads(cached)
    classifier = get_classifier()
    output = classifier(cleaned, truncation=True, max_length=512)
    result = normalize_prediction(output)
    if use_cache:
        redis_cache.setex(key, CACHE_SECONDS, json.dumps(result, ensure_ascii=False))
    return result
```


### 8-1. 각 코드가 하는 일

- `text.strip()`은 양끝 공백을 제거하여 같은 문장의 캐시 키가 일관되게 나오도록 합니다.
- `sha256`은 원문을 Redis 키에 직접 넣지 않도록 합니다. 같은 문장도 **모델 ID가 바뀌면 다른 캐시 키**가 되어 오래된 모델 결과와 구분됩니다.
- `redis_cache.get(key)`가 있다면 모델 추론을 건너뜁니다.
- `get_classifier()`와 `classifier(text)`는 느린 계산을 수행합니다.
- `normalize_prediction()`이 결과를 정해진 `{label, score}` 형태로 통일합니다.
- `setex(key, CACHE_SECONDS, ...)`가 10분 후 사라질 캐시 결과를 저장합니다.

중요: 캐시 키의 해시화는 개인정보를 완전히 익명화하는 기술이 아닙니다. 원문은 SQLite에 저장되어 있으므로 수업에서는 개인 민감정보를 넣지 않습니다.

`use_cache=False`는 **동기 예측의 순수한 추론 시간을 비교**하기 위해 사용하고, Celery Worker에서는 `use_cache=True`로 캐시의 HIT/MISS를 확인합니다. 두 방식의 전체 작업 완료 시간까지 비교할 때는 동일 조건으로 측정해야 합니다.

## 9. Celery Worker가 실행할 `tasks.py`

원본의 6단계 패턴을 그대로 사용합니다.

```text
[1] Import: Celery·DB·서비스를 불러온다.
[2] Task 등록: 데코레이터로 Worker 실행 함수를 등록한다.
[3] Input: 큰 원문 대신 DB id와 수정 차수(revision)만 전달한다.
[4] Fetch: SQLite에서 TextItem 1건을 읽는다.
[5] Work: services.analyze_text(text, use_cache=True)를 수행한다.
[6] Save: 결과를 DB에 저장하고 분석중 상태를 DONE으로 변경한다.
```

**실수 방지:** 이전 작업이 처리 중인데 사용자가 문장을 수정하면 오래된 결과가 최신 내용을 덮어쓰지 않도록 `revision`을 확인합니다. 글을 삭제한 뒤 도착한 작업은 무시합니다. 추론 실패 시 DB를 FAILED로 기록하고 Worker 로그에 예외를 남깁니다.

**`sentiment/tasks.py` — 신규 생성**

```python
from .celery_app import celery_app
from .db import SessionLocal
from .models import TextItem
from .services import analyze_text

@celery_app.task(bind=True, name="sentiment.tasks.analyze_textitem_task")
def analyze_textitem_task(self, item_id: int, revision: int):
    """ID로 DB 조회 → Redis 캐시/모델 → DB 갱신. 오래된 수정 작업은 무시합니다."""
    with SessionLocal() as db:
        item = db.get(TextItem, item_id)
        if item is None or item.revision != revision:
            return {"status": "ignored", "reason": "deleted_or_old_revision"}
        text = item.text
    try:
        result = analyze_text(text, use_cache=True)
    except Exception as exc:
        with SessionLocal() as db:
            current = db.get(TextItem, item_id)
            if current is not None and current.revision == revision:
                current.is_analyzing = False
                current.status = "FAILED"
                current.error_message = type(exc).__name__  # 내부 오류 세부정보는 화면에 노출하지 않습니다.
                db.commit()
        raise
    with SessionLocal() as db:
        current = db.get(TextItem, item_id)
        if current is None or current.revision != revision:
            return {"status": "ignored", "reason": "deleted_or_old_revision"}
        current.label = result["label"]
        current.score = result["score"]
        current.is_analyzing = False
        current.status = "DONE"
        current.error_message = ""
        db.commit()
    return {"status": "DONE", **result}
```


`@celery_app.task`는 이 함수를 Celery가 호출할 수 있는 작업으로 등록합니다. FastAPI 라우터에서 `.delay(item.id, item.revision)`을 실행하면 실제 모델을 즉시 수행하지 않고 **Redis에 작업 메시지를 등록**합니다. Celery Worker는 별도 터미널에서 이를 가져옵니다.

## 10. FastAPI 라우터를 비동기로 바꿉니다

04의 `/predict/`는 그대로 **요청-응답 동기식**으로 유지합니다. 04의 `/new/`와 `/items/{id}/edit/`만 작업 등록 방식으로 변경합니다.

**비동기 생성의 의사코드**

```text
POST /new/ → text 1~500자 검사
→ DB에 text, status=PENDING, is_analyzing=True 저장
→ 생성된 item.id 와 revision=1 확보
→ analyze_textitem_task.delay(id, revision)
→ 303 Redirect /items/{id}/ 반환 (추론 완료를 기다리지 않음)
```

**수정(Update)의 의사코드**

```text
id 조회 → 새 문장 저장 → 기존 label/score 초기화
→ revision 1 증가 → PENDING → Celery 작업 등록
→ Worker가 같은 revision인지 확인 후 결과 반영
```

**`sentiment/router.py` — 전체 교체**

```python
from fastapi import APIRouter, Depends, Form, HTTPException, Request
from fastapi.responses import HTMLResponse, RedirectResponse
from fastapi.templating import Jinja2Templates
from sqlalchemy import select
from sqlalchemy.orm import Session
from .db import get_db
from .models import TextItem
from .services import analyze_text
from .tasks import analyze_textitem_task

router = APIRouter()
templates = Jinja2Templates(directory="templates")

def render(request, name, **context):
    return templates.TemplateResponse(request=request, name="sentiment/"+name, context=context)

def checked(text):
    cleaned = (text or "").strip()
    return cleaned if 1 <= len(cleaned) <= 500 else None

def enqueue_or_mark_failed(item: TextItem, db: Session):
    try:
        analyze_textitem_task.delay(item.id, item.revision)
    except Exception:
        item.status = "FAILED"
        item.is_analyzing = False
        item.error_message = "BROKER_UNAVAILABLE"
        db.commit()

@router.get("/", include_in_schema=False)
def home():
    return RedirectResponse("/items/", status_code=303)

@router.get("/predict/", response_class=HTMLResponse, name="predict_page")
def predict_page(request: Request):
    return render(request, "predict.html", text="", result=None, error=None)

@router.post("/predict/", response_class=HTMLResponse, name="predict")
def predict(request: Request, text: str = Form(default="")):
    value = checked(text)
    if value is None:
        return templates.TemplateResponse(request=request, name="sentiment/predict.html",
            context={"text": text, "result": None, "error": "문장은 1~500자로 입력하세요."}, status_code=400)
    # HTTP 요청 안에서 모델이 끝날 때까지 기다림: 동기 방식
    result = analyze_text(value, use_cache=False)
    return render(request, "predict.html", text=value, result={"input":value, **result}, error=None)

@router.get("/items/", response_class=HTMLResponse, name="item_list")
def item_list(request: Request, db: Session = Depends(get_db)):
    items = db.scalars(select(TextItem).order_by(TextItem.id.desc())).all()
    return render(request, "textitem_list.html", items=items)

@router.get("/new/", response_class=HTMLResponse, name="item_create_page")
def item_create_page(request: Request):
    return render(request, "textitem_form.html", item=None, text="", error=None)

@router.post("/new/", name="item_create")
def item_create(request: Request, text: str = Form(default=""), db: Session = Depends(get_db)):
    value = checked(text)
    if value is None:
        return templates.TemplateResponse(request=request, name="sentiment/textitem_form.html",
            context={"item":None, "text":text, "error":"문장은 1~500자로 입력하세요."}, status_code=400)
    # 먼저 저장 → Celery에는 ID만 전달 → 즉시 redirect
    item = TextItem(text=value, label="", score=None, status="PENDING", is_analyzing=True, revision=1)
    db.add(item)
    db.commit()
    db.refresh(item)
    enqueue_or_mark_failed(item, db)
    return RedirectResponse(request.url_for("item_detail", item_id=item.id), status_code=303)

@router.get("/items/{item_id}/", response_class=HTMLResponse, name="item_detail")
def item_detail(request: Request, item_id: int, db: Session = Depends(get_db)):
    item = db.get(TextItem, item_id)
    if item is None:
        raise HTTPException(status_code=404, detail="해당 글이 없습니다.")
    return render(request, "textitem_detail.html", item=item)

@router.get("/items/{item_id}/status", name="item_status")
def item_status(item_id: int, db: Session = Depends(get_db)):
    item = db.get(TextItem, item_id)
    if item is None:
        raise HTTPException(status_code=404)
    return {"id": item.id, "status": item.status, "is_analyzing":item.is_analyzing,
            "label": item.label, "score":item.score}

@router.get("/items/{item_id}/edit/", response_class=HTMLResponse, name="item_update_page")
def item_update_page(request: Request, item_id: int, db: Session = Depends(get_db)):
    item = db.get(TextItem, item_id)
    if item is None:
        raise HTTPException(status_code=404)
    return render(request, "textitem_form.html", item=item, text=item.text, error=None)

@router.post("/items/{item_id}/edit/", name="item_update")
def item_update(request: Request, item_id: int, text: str = Form(default=""), db: Session = Depends(get_db)):
    item = db.get(TextItem, item_id)
    if item is None:
        raise HTTPException(status_code=404)
    value = checked(text)
    if value is None:
        return templates.TemplateResponse(request=request, name="sentiment/textitem_form.html",
            context={"item":item,"text":text,"error":"문장은 1~500자로 입력하세요."}, status_code=400)
    item.text = value
    item.label = ""
    item.score = None
    item.status = "PENDING"
    item.is_analyzing = True
    item.error_message = ""
    item.revision += 1  # 이전 Celery 작업이 수정 후의 결과를 덮어쓰지 못하도록 구분
    db.commit()
    db.refresh(item)
    enqueue_or_mark_failed(item, db)
    return RedirectResponse(request.url_for("item_detail", item_id=item_id), status_code=303)

@router.get("/items/{item_id}/delete/", response_class=HTMLResponse, name="item_delete_page")
def item_delete_page(request: Request, item_id: int, db: Session = Depends(get_db)):
    item = db.get(TextItem, item_id)
    if item is None:
        raise HTTPException(status_code=404)
    return render(request,"textitem_confirm_delete.html",item=item)

@router.post("/items/{item_id}/delete/", name="item_delete")
def item_delete(item_id: int, db: Session = Depends(get_db)):
    item = db.get(TextItem, item_id)
    if item is None:
        raise HTTPException(status_code=404)
    db.delete(item)
    db.commit()
    return RedirectResponse("/items/", status_code=303)
```


여기서 `def`로 작성된 라우트 함수는 HTTP 요청 처리용입니다. **Celery Worker에 작업을 넘기는 비동기 구조**와 Python 문법 `async def`는 서로 다릅니다. 수업에서 보여주려는 차이는 HTTP 요청이 모델 완료를 기다리는가 아니면 작업 등록 후 먼저 반환하는가입니다.

## 13. 실제 실행 순서: Docker → Celery → FastAPI

**반드시 서로 다른 터미널을 3개 사용합니다.** Docker Desktop은 Windows에서 실행 중이어야 합니다. Docker 이미지 추가와 Python 패키지 설치는 별개입니다.

### 터미널 A — Redis Docker 컨테이너 실행

```bash
cd ~/fastapi_sentiment
docker compose up -d
docker compose ps
docker compose exec redis redis-cli ping
```

결과 `PONG`이면 다음으로 이동합니다. `6380` 포트가 충돌한다면 `docker compose ps`, `ss -lntp | grep 6380`으로 사용 프로세스를 확인하고 중복 컨테이너를 정리합니다. **기존 프로젝트의 Docker 컨테이너를 지우지 마세요.**

### 터미널 B — Celery Worker 실행 (독립 프로세스)

```bash
cd ~/fastapi_sentiment
source .venv/bin/activate
celery -A sentiment.celery_app:celery_app worker --loglevel=info --pool=solo
```

정상일 때 등록된 작업 이름 `sentiment.tasks.analyze_textitem_task`가 로그에 나타나며 대기 상태에 들어갑니다. 이 터미널은 닫지 않습니다. Windows/WSL2에서 `--pool=solo`는 실습용으로 이해하기 쉽지만 대량 병렬처리에는 적합하지 않습니다.

### 터미널 C — FastAPI 서버 실행

```bash
cd ~/fastapi_sentiment
source .venv/bin/activate
python -m sentiment.migrate_06
python -m uvicorn main:app --reload
```

로그에 Uvicorn이 `http://127.0.0.1:8000`에서 실행 중이라는 메시지가 나오면 브라우저 테스트를 시작합니다.

### 터미널이 각각 맡는 일

| 터미널 | 프로그램 | 기능 |
|---|---|---|
| A | Docker Redis | 작업 메시지 큐·캐시·결과 저장소 |
| B | Celery Worker | DB 조회·캐시 확인·AI 추론·DB 갱신 |
| C | Uvicorn/FastAPI | 폼·라우팅·DB 저장·작업 등록·HTML 응답 |

### 15-2. 비동기식 (`/new/`)

브라우저: `http://127.0.0.1:8000/new/` → 문장 입력 → 저장. 우선 DB에 `PENDING`이 저장되고, 라우터가 Celery에 작업을 등록한 뒤 상세 페이지로 이동합니다. 워커가 처리하면 `DONE`, 문제가 생기면 `FAILED`로 표시됩니다. `/items/`에서 목록을 확인할 수도 있습니다.

속도 향상
동기식 감정분석 화면은 781ms, 비동기식 결과 상세 화면은 3ms로 표시되어 있습니다.

| 측정 항목                | 동기 `/predict/` | 비동기 `/new/`          |
| -------------------- | -------------- | -------------------- |
| HTTP POST 응답시간       | 직접 기록 (ms)     | 직접 기록 (ms)           |

## 18. 자동 테스트(모의 모델·모의 작업 실행)

실제 모델 파일을 매번 다운로드하지 않고 먼저 HTTP 연결, DB 작업 등록, 작업 완료 상태 반영을 확인합니다. 이 테스트는 *실제 Redis 브로커에 작업을 보내지 않고* Task의 `.run()`을 직접 호출하는 단위/통합 테스트입니다. Redis, Docker 및 Celery 워커를 이용한 전체 실행은 13~17단계에서 실제 PC로 확인해야 합니다.
